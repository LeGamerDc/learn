# 24 - 经济安全与作弊治理

> **本章目标**：理解作弊对经济的破坏路径，学会从流水数据里识别异常账号，以及知道封号和回档的经济后果。
> **本章有模型**：`models/m24_anomaly.py`

---

## 1. 作弊的四条经济破坏路径

作弊对游戏的伤害，很多人以为是"公平性"问题。**从经济视角看，它的伤害更直接：**

| 路径 | 机制 | 后果 |
|---|---|---|
| **超额投放** | 脚本 24 小时刷、多开、外挂加速 | 相当于凭空增加了 faucet（第 07 章），且不在你的预算表里 |
| **绕过 sink** | 卡 bug 免费获得、复制道具 | 回收失效（第 08 章） |
| **纯 faucet 无 sink** | 工作室只产出不消费，全部变现 | 产出的资源不参与任何回收，直接进入 RMT 市场 |
| **扭曲数值反馈** | 市场价被机器供给压低 | 你以为某材料不稀缺，其实只是被刷多了 → **导致你做出错误的数值决策** |

**第四条最隐蔽也最危险**：它污染了你用来做决策的数据。第 23 章讲的所有指标，在有大规模作弊的服上都会失真。

## 2. 服务端的经济校验

**第一原则：客户端上报的任何数值都不可信。**

对 Go 服务端开发来说这是常识，但游戏项目里仍然常见"为了性能，把战斗结算放在客户端"这类妥协。

**三层防线：**

### 第 1 层：不可能性校验（硬上限）

对每一种资源，服务端必须知道"单位时间内理论上最多能获得多少"：

```
日产出理论上限 = Σ(各渠道的单日上限)
```

**这个上限本来就在你的日产出预算表里**（第 07 章）——预算表不只是设计文档，它同时是**风控规则的数据源**。

任何超过理论上限的账号，直接告警。**注意上限要按玩家等级/进度分层计算**，否则要么误伤高级玩家，要么放过低级作弊号。

### 第 2 层：一致性校验（对账）

第 09 章讲过流水日志要记"变动后余额"。它的作用就在这里：

```
对每个玩家：Σ(所有流水的变动量) 是否等于 (当前余额 − 初始余额)？
```

**不等就说明有变动没走正规接口**——要么是 bug，要么是被利用了。**建议每日跑一次全量对账**，这是发现"未知漏洞"最有效的手段，因为它不需要你事先知道漏洞长什么样。

### 第 3 层：行为校验（统计异常）

前两层抓的是"越界"，第 3 层抓的是"合规但不像人"。见下一节。

## 3. 从流水里揪出异常账号

```bash
cd models && python m24_anomaly.py
```

模型造了 4000 个正常玩家 + 三类异常：

```
群体        日均产出   产出变异系数  日均活跃小时   消费比   转出比
--------------------------------------------------------------
正常玩家     12,417      0.46       3.0       0.85    0.04
刷金脚本    106,025      0.34      14.0       0.29    0.55
工作室       31,316      0.06      20.9       0.20    0.70
搬砖小号     14,375      0.40       4.0       0.11    0.80
```

**注意"搬砖小号"这一行：它的日均产出（14,375）和正常玩家（12,417）几乎一样。** 它的异常之处不在产出，而在**几乎不消费（0.11）、几乎全部转出（0.80）**。

检测效果的递进：

```
① 只看产出总量（>正常P99.9）      召回  23.2%   漏掉：搬砖号60、工作室32、脚本4
② 加上活跃时长（>12h）            召回  52.0%   漏掉：搬砖号60
③ 再加：低消费 + 高转出           召回 100.0%   精确率 96.9%
④ 再加：产出规律性（CV<0.15）     召回 100.0%   （③ 已抓全，无额外收益）
```

**三个结论：**

**① 只看产出总量只能抓到 23%。** 这是最常见的做法，也是最没用的做法——它只能抓到最蠢的那批脚本。

**② 最难抓的是"搬砖小号"，因为它的产出完全正常。** 它的破绽在于**资源的去向**：只进不出、全部转给别人。

> **所以经济风控的核心不是"产出监控"，是"资金流向监控"。**
> 你要看的不是"谁赚得多"，是"资源最后流到哪去了"。

**③ 单个指标都会漏，组合才有效。** 这是模型最重要的教学点——四个维度（产出量、活跃时长、消费比、转出比）里，任何一个单独用都不够。

### 3.1 更强的手段：资金流网络

上面是账号级别的特征。**更强的是把转账关系画成一张图：**

- 工作室的资源最终会汇聚到少数几个"收货号"上；
- 在图上，这些收货号是**高入度、低出度的枢纽**；
- 从收货号反向追溯，能一次性揪出整条产业链上的几百个号。

**这比逐个账号检测有效得多**，因为工作室可以让每个小号都"看起来正常"，但**资金必须汇聚**——汇聚点是他们无法隐藏的结构性破绽。

**如果你的游戏有交易系统，资金流网络分析是必做项。** 需要的埋点就是第 09 章那张流水表里的"关联ID"和转账双方。

## 4. 治理手段与它们的代价

| 手段 | 效果 | 代价 |
|---|---|---|
| **提高生产成本** | 需要人工操作、行为验证、限制多开 | 影响正常玩家体验 |
| **提高转移成本** | 交易税、绑定、额度限制、等级门槛（第 10 章） | 抑制正常交易 |
| **官方化需求** | 官方点卡换游戏币（EVE 的 PLEX，第 10 章） | 改变游戏的价值观 |
| **检测 + 封禁** | 见第 3 节 | **误伤的代价极高** |
| **降低需求** | 让付费路径比 RMT 更划算 | 需要调整定价 |

### 4.1 误伤的代价是不对称的

- 放过一个作弊号：损失有限，且可以后续再抓；
- **误封一个正常玩家（尤其是大 R）：几乎必然流失，还会在社群引发信任危机。**

模型里方案 ③ 的精确率是 96.9%，也就是 **4 个误伤**。在真实项目里，4000 个玩家里误伤 4 个是不可接受的——尤其如果其中有大 R。

**所以实践中的做法是分级处置：**

| 置信度 | 处置 |
|---|---|
| 极高（多维度同时越界 + 资金流枢纽） | 直接封禁 |
| 高 | 限制功能（禁交易、禁上榜），观察 |
| 中 | 加验证（人机验证、实名/设备核验） |
| 低 | 只记录，进观察名单 |

> **绝大多数账号应该走"限制"而不是"封禁"。** 限制交易对工作室来说等于判死刑（他们无法变现），但对被误伤的正常玩家来说只是不便，且可申诉恢复。

## 5. 封号与回档的经济后果

**这一节讲的是很多团队没想过的事：封禁本身会冲击经济。**

### 5.1 封号的经济影响

封掉一批工作室账号，等于**从经济体里抽走了一批资源存量**。如果规模够大：

- 全服货币总量骤降 → 短期通缩（第 09 章）；
- 市场供给骤减 → 物价飙升；
- **正常玩家会感到"东西突然买不起了"**，尽管你做的是好事。

**处理建议**：大规模封禁前后，准备好平抑物价的手段（临时增加供给、NPC 商店托底），并**主动公告**——玩家能接受"因为封号导致物价波动"，但接受不了"莫名其妙涨价"。

### 5.2 回档的代价

回档（把服务器数据恢复到某个时间点）是最后手段：

- **所有玩家在回档窗口内的进度都消失**，包括没作弊的；
- **付费订单必须单独处理**（不能让玩家花的钱消失）；
- 玩家的信任损失远大于经济损失。

> **能不回档就不回档。** 更常见的做法是**定向修正**——只回收作弊获得的资源，保留正常进度。这需要精确的流水日志才能做到（第 09 章）——**没有原因码和完整流水，你无法定向修正，只能全服回档。**

**这是"埋点做好"的最大价值之一**：它决定了出事故时你有没有精细处置的能力。

## 6. 设计层面的预防

**最好的治理是让作弊不划算。** 几条设计层面的建议：

| 设计 | 抗作弊效果 |
|---|---|
| **产出上限（体力、次数）** | 直接封死"24 小时刷"的收益上限（第 06 章） |
| **产出需要博弈而非重复** | 脚本能刷怪，但打不赢需要判断的仗（第 07 章：SLG 把产出放到城外） |
| **关键产出与社交挂钩** | 联盟产出无法用小号刷 |
| **绑定核心资源** | 刷了也转不走（第 10 章） |
| **无自由交易** | 从根上消灭 RMT 变现路径 |

**这解释了为什么 SLG 的作弊问题普遍轻于传统 MMO**：它的核心产出需要博弈和组织，且资源大多不可交易——**脚本可以帮你采集，但不能帮你打赢一场需要协调的攻城战。**

> **反过来说：任何"重复劳动就能获得高价值产出"的设计，都是在给工作室发工资。**
