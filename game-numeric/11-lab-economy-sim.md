# 11 - 建模实战：SLG 经济仿真

> **本章是实验课**，没有多少新知识。你要做的是：跑一套**故意设计得不合格**的参数，看懂体检报告，然后逐项修到全绿。
> **本章有模型**：`models/m11_slg_full.py`
> **前置**：第 04~10 章全部内容。

---

## 1. 模型结构

`m11_slg_full.py` 把前十章的东西合成了一个完整的 SLG 经济体：

| 模块 | 实现 | 来自 |
|---|---|---|
| 玩家分层 | 免费 75% / 小 R 18% / 中 R 6% / 大 R 1%，付费作为**独立投放渠道** | 第 07 章 |
| 货币隔离 | 金币 → 城建，粮食 → 兵，互不抢占 | 第 06 章 |
| 时间货币 | 体力有上限、**付费买不到** | 第 06 章 |
| 层级型 sink | 城建升级，成本 `1.32^L` | 第 08 章 |
| 深度 sink | 城建 15 级后开放"高阶强化"，成本 `1.55^n`，专吃大 R | 第 08 章 |
| 比例型 sink | 金币日损耗、兵损（按参战比例） | 第 08 章 |
| 战力 | `√(EHP × DPS)` | 第 05 章 |
| 诊断 | 回收率、存量/日产、差距发散、体力溢出 | 第 08、09 章 |

**注意模型只跑"每个分层的代表玩家"，不是逐个玩家模拟。** 对经济诊断来说这就够了，而且快得多。什么时候需要真的逐玩家模拟？当你要看**分布**（基尼系数、分位数）而不只是均值时——第 10 章那个模型就是逐玩家的。

## 3. 逐项诊断

这一节教的是**方法**，不是答案。真实项目里你拿到的也是这样一份报告。

### 病症一：四个分层的存量/日产都在 30 天左右（健康区间 5~20）

**推理链**：

1. 回收率 90% 说明每天有 10% 的投放没被回收 → 存量在累积；
2. 但存量并没有无限发散（第 360 天稳定在 30 天左右）→ 说明**存在比例型 sink，只是力度不够**；
3. 第 08 章的稳态公式：`存量/日产 = (1−d)/d`。反解：`30 = (1−d)/d` → `d ≈ 3.2%`。
4. 查参数：`gold_decay=0.03`。**完全吻合。**

> **这就是有理论模型的好处**——你不需要试参数，直接反解就知道该调到多少。
> 要让存量落到 15 天：`15 = (1−d)/d` → `d ≈ 6.25%`。

**注意这里的一个诊断陷阱**：如果你只看"回收率 90%，挺高的"，你会觉得没问题。**回收率和存量水位是两个不同的指标，必须同时看**——90% 的回收率听起来很高，但剩下的 10% 常年累积，照样能堆出 30 天的浮财。

### 病症二：付费战力差距在发散（9.9× → 17.7×）

**这是三个病里最严重的一个**，因为它意味着服务器生态会随时间恶化（第 07 章图 ④ 的那条判据：对数坐标下各层的线应当平行）。

**找发散源的方法：看哪个变量在分层之间的差异随时间拉大。**

对照表格：末城建 13 / 14 / 17 / 22，深度强化 0 / 0 / 2 / 5。

**两个嫌疑：**

1. **城建等级差** → 产能是 `1.06^level`，大 R 比免费玩家高 9 级 → 额外产能 `1.06^9 ≈ 1.69×`。**这是一个正反馈回路**（第 03 章 5.1 节）：付费 → 城建高 → 产能高 → 更多资源 → 城建更高。
2. **深度强化** → 战力里有 `(1 + deep × 0.12)` 这一项，大 R 有 5 层 = +60%，免费玩家 0 层。**而深度 sink 是专门为大 R 设计的**，所以它天然只放大头部。

**第 2 条是主因，而且它揭示了一个重要的设计矛盾：**

> **深度 sink 的目的是回收大 R 的资源（第 08 章），但如果它同时给战力加成，它就变成了付费差距的放大器。**

**这正是第 08 章说"炫耀性消费和组织性消耗是大 R 的最优 sink"的原因**——它们回收资源但**不放大战力差距**。

修法有三种，代价不同：

| 修法 | 效果 | 代价 |
|---|---|---|
| 降低深度强化的战力加成（0.12 → 0.04） | 直接有效 | 大 R 会觉得投入产出比低 |
| 深度 sink 改为不给战力（外观/称号/联盟建设） | 最彻底 | 需要有对应的系统承载 |
| 给城建产能加软上限 | 治正反馈那条 | 影响所有玩家的后期成长 |

### 病症三：体力溢出 15.8%

**最简单的一个**：`stamina_regen=30`，`battles_per_day=25`，每天净剩 5 点 → 溢出率约 `5/30 ≈ 17%`。

第 03 章讲过，5%~15% 的溢出是健康的（制造"要勤快点"的驱动力），超过就变成浪费和打工感。

## 4. 参考答案

<details>
<summary>先自己修，改不动再展开</summary>

三处改动：

```python
gold_decay=0.06,        # 0.03 → 0.06   （由 (1−d)/d = 15 反解）
stamina_regen=26.0,     # 30 → 26       （净剩 1 点/天）
# 战力公式里：
ehp = troops * (1 + level * 0.05) * (1 + deep * 0.04)   # 0.12 → 0.04
dps = troops * (1 + level * 0.05) * (1 + deep * 0.04)
```

结果：


### 4.1 一个值得停下来看的结果

修好之后，**四个分层的「存量/日产」全部是 15.7 天**——一模一样。

这不是巧合。第 08 章推导过比例型 sink 的稳态：

```
存量/日产 = (1 − d) / d = (1 − 0.06) / 0.06 = 15.67
```

**这个值只取决于损耗率 `d`，与投放量完全无关。** 所以不管是免费玩家还是投放高 7 倍的大 R，水位都一样。

> **这就是比例型 sink 最了不起的性质：它对所有分层自动生效，不需要你为大 R 单独设计一套参数。**
>
> 对比一下：如果你用的是固定额度的 sink（"每天扣 1000 金币"），免费玩家会被扣光，大 R 毫无感觉。

**记住这个结论。** 当你以后审到任何"按固定数额"设计的经济机制时，都该问一句：换成按比例会不会更好？

### 4.2 一个没修的问题

注意大 R 的**粮食回收率只有 75.8%**（其他分层都是 100%）。

原因：练兵产能是 `15 × 城建等级`，而大 R 的粮食投放是免费玩家的 7 倍。**他的粮食产出超过了兵营的消化能力**，多出来的粮食堆在仓库里。

这就是第 03 章讲的"瓶颈转移"和第 08 章讲的"大 R 资源溢出"的合体。**留给你作为练习**（第 5 节任务 D）。

## 5. 扩展实验

### 任务 A：模拟内容断供

给城建加一个上限 `max_level`，从第 90 天起每 30 天才提升 3 级（模拟版本更新跟不上玩家推进）。看回收率和存量怎么变。

**这是真实项目里最常见的经济事故形态**——不是参数错了，是内容产能跟不上。

### 任务 B：模拟活动失控

从第 60 天起，每 30 天有一次"当日投放 ×2"的活动。跑 360 天，看：
- 累计投放超了多少？
- 存量/日产被推到多少？
- 比例型 sink 能不能自动吸收掉？

（提示：这个实验会让你对第 08 章"比例型 sink 自动伸缩"有更深的体会。）

### 任务 C：找出付费差距的临界值

保持其他参数不变，二分搜索深度强化的战力加成系数，找出让 360 天差距倍率恰好等于 1.5 的临界值。

然后思考：**如果产品要求"大 R 必须明显强"，你还有哪些不会造成发散的手段？**（提示：回到第 05 章第 6 节和第 07 章第 4 节。）

### 任务 D：修掉大 R 的粮食溢出

三种思路，各实现一种并对比：

1. 兵营产能改成与付费挂钩（大 R 能练更多兵）——会加剧战力差距吗？
2. 给粮食加一个比例型 sink（军粮消耗：兵越多每天吃得越多）——这会不会同时解决别的问题？
3. 给粮食加仓库上限，超出部分直接溢出——玩家会怎么反应？

**第 2 种是真实 SLG 的做法**（部队维护需要粮食）。做完你会发现它一举三得：回收粮食、给兵力加了负反馈、还让"扩军"有了持续成本。

### 任务 E：加入流失

给每个分层加一个日流失率，且流失率与"体验"挂钩（比如与单级停留天数正相关，第 04 章）。看服务器的人口结构怎么演化。

**这是通向第 19 章（服务器生态）的桥梁。**

## 7. 把模型用到你自己的项目上

这个脚本是可以直接改造使用的。改造步骤：

1. **改分层**：`TIERS` 换成你的真实付费分布（从数据里拿 P50/P90/P99 的付费额）；
2. **改投放**：`gold_base` / `food_base` 换成你的日产出预算表（第 07 章导出的 CSV 可以直接读进来）；
3. **改 sink**：把你的实际回收项一条条加进去，**每一条都要能对应到一个原因码**（第 09 章 5.1 节）；
4. **改战力**：换成你的真实战力公式；
5. **加判定**：把你们团队认可的健康标准写成 `check()`。

然后把它接到 CI 里——**每次数值表变更，自动跑一遍体检**。这是我见过的最有性价比的数值质量保障手段：改一个配置就知道它对 360 天后的经济有什么影响，而不是等上线三个月后才发现。
