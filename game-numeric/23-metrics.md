# 23 - 数据体系与指标树

> **本章目标**：设计一套制作人能用的指标体系。学完你应该能画出自己产品的指标树、说清楚服务端该埋什么、以及知道 A/B 测试在数值上的适用边界。

---

## 1. 指标树：从一个数往下拆

**指标不该是一个列表，该是一棵树。** 树的作用是：当顶层指标动了，你能顺着树找到原因。

```
                        ┌───────────────┐
                        │   月流水       │  ← 北极星（商业）
                        └───────┬───────┘
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
       ┌────────────┐                      ┌────────────┐
       │    DAU      │                      │  ARPDAU     │
       └──────┬─────┘                      └──────┬─────┘
        ┌─────┴─────┐                    ┌────────┴────────┐
        ▼           ▼                    ▼                 ▼
   ┌────────┐  ┌────────┐          ┌─────────┐      ┌───────────┐
   │ 新增    │  │ 留存    │          │ 付费率   │      │  ARPPU     │
   └───┬────┘  └───┬────┘          └────┬────┘      └─────┬─────┘
       │           │                     │                 │
   买量/自然量   D1/D7/D30           首充转化率        客单价 × 频次
                   │                     │                 │
              ┌────┴────┐           付费点触达率      深度付费占比
              ▼         ▼
        节奏健康度   社交绑定率
              │         │
        单级停留天数  入盟率/联盟活跃
```

**每一层的用法不同：**

| 层级 | 谁看 | 频率 | 用途 |
|---|---|---|---|
| 顶层（流水、DAU） | 制作人、老板 | 每日 | 判断整体健康 |
| 二层（留存、付费率、ARPPU） | 制作人、主策 | 每日/每周 | 定位问题在哪一支 |
| 三层（各阶段留存、各付费点转化） | 数值、运营 | 每周 | 定位到具体系统 |
| 四层（单级停留、入盟率、卡点通过率） | 数值 | 按需 | 定位到具体参数 |

> **一个可执行的规矩：任何一个顶层指标的异常，都必须能沿着树追到某个四层指标。**
> 追不到，说明你的指标树缺了一支。

## 2. 制作人的日常看板

**不要看几十个数。** 一个够用的看板大约十来个数，分四组：

### 组 1：规模与健康（4 个）

| 指标 | 看什么 |
|---|---|
| DAU / 新增 / 流失 | 净增是正是负 |
| D1 / D7 / D30 留存 | 分买量渠道看 |
| 月流水 + ARPDAU | 趋势，不看单日 |
| 付费率 | **这是基本盘的指标**（第 12 章） |

### 组 2：经济健康（4 个）—— 本课程的重点

| 指标 | 看什么 | 章节 |
|---|---|---|
| **各资源的「存量 ÷ 日产出」** | 5~20 天为健康，**分层看** | 第 08 章 |
| **各资源的累计回收率** | ≥85%，看趋势不看绝对值 | 第 08 章 |
| **物价指数 / 达标时长** | 购买力是否下降 | 第 09 章 |
| **货币流速** | 下降是先行警报 | 第 09 章 |

### 组 3：生态健康（3 个）—— SLG 必看

| 指标 | 看什么 | 章节 |
|---|---|---|
| **大 R 占全服有效战力比** | **持续上行 = 警报** | 第 19 章 |
| **联盟数量与规模分布** | 头部联盟 >60% = 干预 | 第 19 章 |
| **免费玩家的战斗参与率与胜率分布** | 有多少人常年挨打 | 第 19 章 |

### 组 4：节奏健康（2 个）

| 指标 | 看什么 | 章节 |
|---|---|---|
| **各阶段的单级停留天数** | 有没有突变的柱子 | 第 04、20 章 |
| **各卡点的通过率与通过耗时** | 卡点是否过强/过弱 | 第 20 章 |

**组 2 和组 3 是本课程独有的贡献**——大多数团队的看板只有组 1 和一部分组 4，结果是**经济和生态出问题时看板上一片绿**，等到组 1 的数字掉下来，已经晚了三个月。

## 3. 服务端埋点设计

第 09 章 5.1 节讲过经济流水日志，这里补齐完整清单。

### 3.1 三类必须埋的事件

**① 经济流水**（每一笔资源变动）

字段见第 09 章。**核心是"原因码"**——它必须和第 07 章日产出预算表里的渠道一一对应。

> **一个工程上的强建议**：把资源变动收敛到一个统一的接口，不允许任何模块直接改数据库里的余额。
> 这正是第 03 章 `econ.py` 里"所有池变动必须经过 `_give`/`_take`"那个设计的现实版本——**没有这个约束，你的经济日志永远是不完整的，而不完整的日志等于没有日志。**

**② 玩家行为事件**

| 事件 | 关键字段 |
|---|---|
| 登录/登出 | 时长、设备、渠道 |
| 战斗结算 | 双方战力、结果、损失、耗时 |
| 系统解锁/首次使用 | 用于算漏斗 |
| 卡点相关 | 尝试次数、失败次数、最终解决方式（肝/氪/社交） |
| 社交行为 | 入盟、退盟、援助、聊天量 |

**"卡点的最终解决方式"这个字段值得单独强调**——它直接告诉你第 12 章那三条出路的实际使用比例。没有它你只能猜。

**③ 付费事件**

订单、商品、金额、触发场景（**在哪个界面/哪个卡点弹出的**）、是否首充。

**"触发场景"同样是最容易漏埋、又最有价值的字段**——它是优化付费点位置的唯一依据（第 20 章）。

### 3.2 日终快照

流水算流量，快照算存量。每日固定时间对全服做一次：

- 各资源的总量、P10/P50/P90/P99；
- 各分层的战力、等级、进度分布；
- 联盟结构（数量、规模、领土占比）。

**为什么必须要分位数**（第 09 章讲过）：经济数据极度长尾，均值会被少数大 R 完全带偏。**P50 代表典型玩家，P99 反映头部，两者的比值本身就是分化指标。**

## 4. 两个必须避开的分析陷阱

### 4.1 幸存者偏差

第 17 章 2.1 节遇到过一次：**连败保护让本来会流失的弱者留下来，结果"低胜率玩家占比"反而上升了。**

如果只看这个比例，会得出"保护机制让体验变差"的错误结论。

> **规则：任何按"当前活跃玩家"计算的指标，都被幸存者偏差污染了。**

**正确做法**：用**固定同期群（cohort）**。选定某天注册的一批人，追踪他们的指标随时间的变化，分母始终是这批人的初始人数。

典型的例子：
- ✗ "当前玩家的平均战力在上升" —— 可能只是弱者走了；
- ✓ "第 30 天注册的这批人，第 60 天时的战力中位数是 X" —— 这才有意义。

### 4.2 均值陷阱

第 12 章讲过：付费额的中位数 36 元、均值 212 元，差 6 倍。

> **在长尾分布上，均值几乎总是错的那个数。**

**规则：所有涉及付费、资源、战力的指标，默认看中位数和分位数，均值只用来算总量。**

## 5. A/B 测试：在数值上的适用边界

A/B 测试在 UI、引导、文案上非常有效。**但在数值上，它的适用范围比大多数人以为的窄得多。**

### 5.1 能测的

| 场景 | 为什么能测 |
|---|---|
| 新手期的引导节奏、首个奖励的大小 | 影响快速显现（1~3 天），且局部 |
| 付费点的位置、文案、价格档位 | 转化率是即时指标 |
| 单个卡点的强度 | 通过率可以立刻观测 |
| 礼包内容组合 | 同上 |

### 5.2 不能测的

| 场景 | 为什么不能测 |
|---|---|
| **经济参数（投放/回收）** | 效果要几十天才显现（第 03 章：存量是流量的积分），而 A/B 组通常跑不了那么久 |
| **数值膨胀速度** | 影响周期以月为单位 |
| **生态相关的一切** | **A/B 组的玩家在同一个服里互相影响**，实验组和对照组不独立 |
| **社交/联盟机制** | 同上，且社交网络无法拆分 |
| **PvP 平衡** | 两组玩家会互相匹配，污染彼此 |

**第三条是最关键也最容易被忽略的**：

> **在同一个服务器里做涉及玩家互动的 A/B 测试，实验组和对照组之间存在干扰（interference），标准的 A/B 分析方法会给出错误结论。**

**正确的替代方案：**

| 方案 | 说明 |
|---|---|
| **按服分组** | 整个服作为一个实验单元。代价是样本量小、服间本身有差异 |
| **时间序列对比** | 同一个服的前后对比 + 用其他服作为对照（合成控制法） |
| **仿真** | **本课程的方法**——先在模型里跑，再上线 |
| **灰度放量** | 新服先上，观察一个完整周期 |

> **这就是为什么这门课花了这么多篇幅教建模。** 经济和生态的参数，你**没有办法**用 A/B 测出来——只能靠模型预判 + 小心的灰度。

## 6. 数据周报该怎么写

第 09 章讲过 CCP 的 EVE 月报的一个好习惯：**会解释异常波动的原因**。

一份有用的经济/数值周报应该包含：

1. **三条核心指标的趋势**（不是当期值）；
2. **异常项及其解释**——"本周金币存量上升 12%，因为周年活动投放超预算 3%"；
3. **预警项**——"大 R 有效战力占比连续 4 周上行，需要关注"；
4. **上周措施的效果验证**；
5. **下周计划的干预**。

> **光有数字没有解释，看的人不会有行动。** 这是数据团队和业务团队之间最常见的断层。

## 7. 动手

### 7.1 画你的指标树

给你在第 01 章选的那款游戏（或你自己的项目），画一棵完整的指标树。要求：

- 顶层一个北极星指标；
- 每个叶子节点都是**可以直接从埋点算出来的**；
- 标出哪些是本课程组 2（经济）和组 3（生态）的指标。

然后做一次演练：假设月流水下降 15%，沿着树往下追，列出你会依次检查哪些指标。

### 7.2 设计埋点

给"抽卡"这一个系统设计完整的埋点。要求覆盖：

- 经济流水（消耗了什么、获得了什么、原因码）；
- 行为事件（在哪个界面进入、抽了几次、保底进度）；
- 付费事件（如果是付费抽，触发场景是什么）；
- 合规要求（第 13 章：随机种子和结果必须可追溯）。

### 7.3 判断题

下面五个问题，哪些能用 A/B 测试？不能的说明替代方案。

1. 首充礼包定价 6 元 vs 12 元
2. 金币日产出提高 20%
3. 新手引导的第一个奖励给 100 还是 500
4. 集结人数上限从 20 改成 40
5. 抽卡软保底从 74 抽改成 68 抽

<details>
<summary>参考答案</summary>

1. **能测**。转化率是即时指标，且不涉及玩家互动。
2. **不能测**。经济效果要几十天显现（第 03 章），且会通过市场/战力影响其他玩家。替代：仿真 + 新服灰度。
3. **能测**。局部、即时、不涉及互动。
4. **绝对不能测**。这是第 18 章的 α 参数，直接改变玩家之间的力量对比——实验组和对照组会互相打，完全污染。替代：仿真（m18/m19）+ 按服分组。
5. **可以测转化率，但不能测长期影响**。抽卡消耗的即时变化能测；但它对经济存量、玩家挫败感、长期留存的影响需要更长周期。建议：转化率用 A/B，长期影响用仿真 + 灰度。
</details>
