# 01 - 部署的演进史：我们到底在解决什么问题

> 本章目标：理解容器和 Kubernetes 是**被什么痛点逼出来的**。
> 这章没有实验，但它是全课程最重要的一章——后面每个复杂概念，你都要能追溯回这里的某个痛点。
> 预计用时：45 分钟。

---

## 1. 从你熟悉的地方出发

你写了一个 Go 服务：

```go
func main() {
    http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok"))
    })
    http.ListenAndServe(":8080", nil)
}
```

`go build` 产出一个二进制。现在的问题是：**怎么让它在生产环境 7×24 跑起来，并且在流量涨 10 倍时不挂？**

这个问题的答案，就是过去 25 年整个基础设施行业的演进史。

---

## 2. 第一阶段：物理机时代（~2000 年前后）

### 做法

买服务器 → 装 Linux → `scp` 二进制上去 → `nohup ./myapp &` → 写个 init 脚本开机自启。

### 痛点

**① 环境不一致（"在我机器上是好的"）**

你的 Mac 是 glibc 2.39，生产机是 CentOS 7 的 glibc 2.17。Go 静态编译还算幸运（`CGO_ENABLED=0` 时几乎无依赖），但只要你用了 `net` 包的 CGO 解析器、SQLite、或任何 C 库，就会遇到：

```
./myapp: /lib64/libc.so.6: version `GLIBC_2.28' not found
```

Python/Java/Node 的世界更惨——运行时版本、系统包、环境变量，全是隐式依赖。

**② 资源利用率极低**

一台 32C64G 的机器，为了"隔离"只跑一个服务，CPU 常年 5%。因为你不敢把两个服务放一起：

- 服务 A 内存泄漏 → 把服务 B 一起 OOM 掉
- 服务 A 需要 OpenSSL 1.0，服务 B 需要 1.1 → 装谁的？
- 服务 A 打满了磁盘 IO → 服务 B 延迟飙升

**③ 扩容以周计**

采购 → 上架 → 装机 → 配网络 → 部署。大促前扩容要提前一个月准备。

**④ 单机故障 = 服务中断**

机器挂了，得有人半夜爬起来手工把服务迁到备机，改 DNS 或 LVS 配置。

---

## 3. 第二阶段：虚拟机时代（2001~2013）

VMware / Xen / KVM 出现，后来演化成公有云（AWS EC2，2006）。

### 解决了什么

- **隔离**：每个 VM 有独立内核、独立文件系统，A 崩溃不影响 B。
- **资源切分**：32C64G 切成 8 个 4C8G，利用率上去了。
- **弹性**：云上开一台机器从"一个月"变成"3 分钟"。
- **环境固化**：可以做黄金镜像（AMI），装好一切再克隆。

### 剩下的痛点

**① 太重**

每个 VM 一个完整 OS：
- 磁盘：一个最小 Linux 镜像也要 1~2 GB，你的应用可能只有 10 MB
- 内存：内核 + systemd + sshd + 各种 daemon，起步 300~500 MB
- 启动时间：30 秒 ~ 2 分钟（要走完整的内核引导 + init）

如果你的服务只需要 50MB 内存，用 VM 隔离的开销比业务本身还大。微服务架构（一个系统拆成 50 个服务）在 VM 上成本无法接受。

**② 镜像迭代慢**

改一行代码 → 重新烤一个 2GB 的 AMI → 分发。Packer 烤一次镜像要 10 分钟起。

**③ 开发环境仍不一致**

开发者不会在自己的 Mac 上跑一个 VMware 虚拟机来开发（太重了），所以"我机器上是好的"依然存在。

---

## 4. 第三阶段：容器（2013 Docker 发布）

Docker 的技术其实**没有一样是新的**：

| 技术 | 出现时间 |
|---|---|
| chroot | 1979 |
| FreeBSD Jails | 2000 |
| Linux namespaces | 2002 起陆续合入 |
| cgroups | 2007（Google 贡献） |
| LXC | 2008 |
| Google Borg（内部大规模容器编排） | 2003 起，2015 才公开论文 |

Docker 做对的是两件**产品层面**的事：

**① 镜像格式 + 分层文件系统**

把"应用 + 它的整个用户态依赖"打包成一个可寻址、可分发、**不可变**的东西。而且用分层（union filesystem）让它增量传输：base 层大家共享，你的应用层只有几 MB。

**② 极其顺手的开发者体验**

```bash
docker build -t myapp .
docker run -p 8080:8080 myapp
docker push myapp
```

三条命令，从源码到"能在任何 Linux 上跑"。对比 Packer + Ansible + VMware 的一整套工具链，这是降维打击。

### 容器 vs 虚拟机（本质区别）

```
   虚拟机                              容器
┌─────────────────┐            ┌─────────────────┐
│  App A │ App B  │            │  App A │ App B  │
├────────┼────────┤            ├────────┼────────┤
│ 系统库 │ 系统库  │            │ 系统库 │ 系统库  │   ← 各自打包在镜像里
├────────┼────────┤            ├────────┴────────┤
│ 内核A  │ 内核B   │            │   共享宿主机内核  │   ← 关键区别
├────────┴────────┤            ├─────────────────┤
│    Hypervisor   │            │  容器运行时       │
├─────────────────┤            ├─────────────────┤
│    宿主机内核     │            │    宿主机内核     │
└─────────────────┘            └─────────────────┘
   隔离：硬件级                     隔离：内核特性级
   开销：GB / 分钟                  开销：MB / 毫秒
```

**一句话**：容器不是"轻量虚拟机"，它就是**宿主机上的一个普通进程**，只不过内核用 namespace 骗它"你看到的就是全世界"，用 cgroup 限制"你只能用这么多资源"。

这句话你要一直记住。它解释了后面所有的行为：
- 为什么容器里 `ps` 只看得到自己的进程（PID namespace）
- 为什么容器里 `free -h` 显示的是宿主机内存（`/proc` 没被完全隔离，这是坑，第 4 章讲）
- 为什么容器"启动"只要几毫秒（就是 `fork` + `exec`）
- 为什么容器不能跑不同内核的系统（Linux 容器跑不了 Windows 程序）
- 为什么容器隔离性**弱于** VM（共享内核 = 共享攻击面，所以有了 gVisor、Kata、user namespace）

## 5. 第四阶段：编排（2014 Kubernetes 发布）

有了容器后，新问题立刻出现。假设你有 3 台机器、20 个服务、每个服务 3 个副本 = 60 个容器：

| 新问题 | 手工方案 | 为什么不行 |
|---|---|---|
| 60 个容器分别放哪台机器？ | 人肉规划 Excel | 机器一多就算不过来，且资源碎片严重 |
| 机器挂了怎么办？ | 人肉重新拉起 | 半夜 3 点 |
| 容器 OOM 退出了怎么办？ | `--restart=always` | 只能救本机，机器挂了没救 |
| 服务 A 怎么找到服务 B 的 IP？ | 手工维护配置文件 / Consul | 容器 IP 每次重启都变 |
| 怎么滚动更新不断服务？ | 写脚本：停一个、起一个、健康检查 | 脚本会越写越复杂，且各团队重复造 |
| 流量涨了怎么扩容？ | 人肉 `docker run` | 慢，且扩完还要改负载均衡配置 |
| 配置和密码怎么下发？ | scp 配置文件 | 无版本、无审计、易泄漏 |
| 怎么知道 60 个容器都健康？ | 挨个 `docker ps` | 不可扩展 |

**这些问题的集合，就叫"容器编排"（Container Orchestration）。**

### 编排系统之争（2014~2017）

| 系统 | 出身 | 结局 |
|---|---|---|
| **Docker Swarm** | Docker 官方 | 简单但能力弱，2017 后基本退场 |
| **Apache Mesos + Marathon** | Twitter/Airbnb 大规模验证 | 太底层（是"数据中心内核"），2021 归档 |
| **Kubernetes** | Google，源自内部 Borg 15 年经验 | 胜出 |
| Nomad (HashiCorp) | | 小众但仍活跃，简单场景不错 |

Kubernetes 赢的原因：
1. **Google 的 Borg 经验**——它不是设计出来的，是从十几年生产教训里提炼出来的。
2. **声明式 API + 控制器模式**——可扩展性远超竞品（见第 6 章，这是它的灵魂）。
3. **CNCF 中立治理**——不属于任何一家公司，云厂商都愿意支持。
4. **可扩展点设计**：CRI（运行时）、CNI（网络）、CSI（存储）、CRD（自定义资源）都是插件化的。生态因此爆炸。

2017 年 Docker 官方宣布 Docker EE 支持 Kubernetes，战争结束。

## 6. 第五阶段：K8s 之上的问题（2018 至今）

K8s 解决了编排，但引入了新问题——**它太复杂了**。

| 新痛点 | 应对 | 本课程章节 |
|---|---|---|
| 一个服务的 YAML 有 500 行，5 个环境要维护 5 份 | **Helm**（模板化）/ **Kustomize**（叠加） | 15、16 |
| 谁在什么时候改了集群？改回去？ | **GitOps / Argo CD**（Git 是唯一真相源） | 18 |
| 手工 `kubectl apply` 需要给 CI 集群管理员权限 | Argo CD 的拉模型 | 18 |
| 一次性全量替换风险太大 | **Argo Rollouts**（金丝雀 + 指标自动回滚） | 19 |
| 有状态中间件（MySQL/Kafka）在 K8s 上怎么运维？ | **Operator 模式**（把运维知识写成控制器） | 6、21 |
| 服务间的重试/熔断/mTLS/流量切分 | **Service Mesh**（Istio / Linkerd）/ 现在更多用 Gateway API + 库 | 10、19 |
| 100 个集群怎么管？ | 多集群管理、Cluster API、平台工程 | 21 |
| 开发者不该被迫学 K8s | **平台工程 / IDP**（内部开发者平台） | 21 |

## 7. 关键洞察：每一层都在解决"上一层的抽象泄漏"

把整条链路排一下，你会发现一个清晰的模式——**每一层都是在把"人肉重复劳动"固化成"声明 + 自动化"**：

```
物理机   →  "机器"是手工管理的实体
  VM     →  "机器"变成可编程资源（API 创建/销毁）        [解决：隔离、利用率、弹性]
 容器     →  "应用+依赖"变成可编程资源（镜像）            [解决：环境一致性、密度、启动速度]
 K8s     →  "应用的运行状态"变成可编程资源（声明式 API）    [解决：调度、自愈、服务发现、更新]
 Helm    →  "一组 K8s 对象"变成可版本化的包               [解决：多环境复用]
 GitOps  →  "集群的期望状态"变成 Git 里的代码             [解决：审计、协作、回滚]
```

**贯穿始终的两个理念**，请刻进脑子：

### ① 不可变基础设施（Immutable Infrastructure）

**永远不要修改正在运行的东西，要改就换一个新的。**

- ❌ 传统：登上服务器，`vim` 改配置，`systemctl restart`
- ✅ 现代：构建新镜像 → 起新容器 → 流量切过去 → 销毁旧容器

好处：可重复、可回滚、无"雪花服务器"（每台机器因为历次手工修改变得各不相同、无法重建）。

这也是为什么后面你会看到：改一个 ConfigMap 通常要触发 Pod 重建；为什么镜像 tag 不该用 `latest`；为什么 Argo CD 会把你手工改的东西改回去。

### ② 声明式 > 命令式

- 命令式："先起 3 个容器，然后把第 2 个杀掉，再起 1 个新的"——描述**过程**
- 声明式："我要 3 个 v1.2 的副本"——描述**结果**，系统自己算差异

用 Go 的话说：

```go
// 命令式
startContainer(); startContainer(); startContainer()

// 声明式：你只提供 desired，系统跑一个永不停止的调谐循环
type Desired struct { Replicas int; Image string }

for {
    actual := observe()
    diff := compare(desired, actual)
    apply(diff)          // 少了就补，多了就删，版本不对就换
    time.Sleep(interval)
}
```

声明式的杀手锏是**幂等 + 自愈**：你说一遍"我要 3 个"，之后不管是节点挂了、容器崩了、还是有人手工删了一个，系统都会自动补回来。**你不需要写任何异常处理代码。**

这就是 K8s 的全部灵魂，第 6 章会把它彻底展开。
