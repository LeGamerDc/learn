# 设计评审清单（Design Review Checklist）

> 用法：第 26 章。评审别人的案子时按顺序问；写自己的案子前先自问一遍。
> 顺序很重要：**先目标，再系统，最后细节**。在目标没对齐之前讨论细节是浪费所有人的时间。

## 第一层：目标（5 分钟内必须回答清楚）

- [ ] 这个系统要让玩家感受到什么？（说不出一句话 = 案子没成熟）
- [ ] 它服务于哪条核心 / 元循环？在循环图上指出来
- [ ] 它解决的是一个真实存在的问题，还是"别的游戏有所以我们也要有"？
- [ ] 删掉它游戏会怎样？（答案是"没什么影响"就该删）
- [ ] 成功指标是什么？上线后怎么知道它做对了？

## 第二层：系统（体验目标对齐后再问）

- [ ] 玩家在这里做的决策有意思吗？有没有明显最优解？（第 05 章）
- [ ] 反馈回路是正是负？会不会让强者恒强 / 弱者退游？（第 06 章）
- [ ] 与现有系统的接口列全了吗？改动影响评估了吗？（第 15 章）
- [ ] 新手什么时候接触到它？他们那时能理解吗？（第 18 章）
- [ ] 成熟玩家一个月后还会用它吗？（第 22 章）
- [ ] 它的付费点是体验的延伸还是拦路？（第 21 章）
- [ ] 社交面：会不会制造社交压力或被工作室利用？（第 11 章）
- [ ] 随机性用对地方了吗？玩家会觉得公平吗？（第 10 章）

## 第三层：规格（系统对齐后再问）

- [ ] 规则有没有歧义？两个程序读了会实现成一样的东西吗？
- [ ] 边界与异常写全了吗？（并发、掉线、跨天、跨服、回滚）
- [ ] 数值接口列出来了吗？哪些参数谁定？
- [ ] 表现需求与资源量估过吗？
- [ ] 埋点能回答第一层的"成功指标"吗？
- [ ] 范围：不做什么写清楚了吗？

## 评审礼仪

- 先复述对方的目标，确认理解一致再提意见
- 意见要指向"体验目标 / 系统 / 规格"三层里的哪一层
- 每个反对意见附一个可执行的替代方案，或明确说"我没有替代方案，只是提示风险"
- 给每条意见定级（按顺序问，第一个命中的就是它的类型）：硬约束（可用性 / 无障碍 / 合规 / 伦理 / 安全 / 技术可行）→ 不符合目标或支柱 → 证据强度与风险严重度 → 个人偏好。**不要用"目标换了还成不成立"当唯一判据**
- 评审结论只有四种：
  - **通过**
  - **修改后通过**（列出修改项与负责人，并说明由谁确认修改完成）
  - **暂缓决策**（必须写清：缺什么证据 / 谁去补 / 什么时候补完 / 到期补不出来的默认动作；说不出"知道了什么就能定"的，不是暂缓，是打回）
  - **打回**（说明是哪一层没过，以及下次只看什么）
