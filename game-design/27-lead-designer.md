# 27 - 主策的工作

> **本章目标**：学完你应该能写出一套可以用来**否决功能**的设计支柱，用价值/成本/风险/支柱四个维度做优先级判断，在该砍功能的时候砍掉并把代价记录下来，以及知道主策和制作人、主程、主美、数值、运营、发行分别在什么边界上交接。
> **前置**：[第 26 章](./26-design-critique.md)（评审的三层顺序，支柱是第一层的判断依据）、[第 14 章](./14-design-process.md)（迭代与砍功能）、[第 15、16 章](./15-system-design-method.md)（你带的人交给你的东西长什么样）。

## 1. 主策每天在做的其实只有一件事

版本封版前两周，三件事在同一个上午落到主策桌上：

- **运营**：下个赛季想加一个"公会出勤排行"，数据部门估算能拉动 7 日留存，开发量两周。
- **主程**：战斗多解验证需要一套 AI 模拟器，三人月。不做的话，我们没法保证每关真的有三种打法，只能靠策划手动试。
- **一个系统策划**：他的角色养成案第三版了，写得很认真，但主策看完的直觉是"这个系统不该存在"。

三件事的表面形态完全不同：一个是排期问题，一个是技术投入问题，一个是设计质量问题。但它们要求主策做的其实是**同一件事**：拿出一个标准，说明为什么这个可以、那个不可以，并且这个标准要能被团队复述、下次不用再问他。

**主策的工作不是做设计决定，是提供做设计决定的标准，然后在标准之外的地方拍板。** 如果每个决定都要主策亲自做，团队的吞吐量上限就是主策一个人的吞吐量；如果标准清楚，十个人可以各自做出方向一致的决定。

这一章讲的就是这套标准是什么（设计支柱）、怎么用它做取舍和砍功能、以及主策在组织里的其他几件事：跨职能交接、带人、建立设计文化。

## 2. 主策对什么负责，不对什么负责

### 2.1 与制作人的分工

[第 01 章](./01-what-designers-do.md)给过一句话版本：**主策对"这个游戏好不好玩"负责，制作人对"这个项目能不能按时按预算上线并赚钱"负责。** 展开成表：

| | 主策 | 制作人 |
|---|---|---|
| 对什么负责 | 体验质量、设计一致性、设计团队的产出 | 项目交付、预算、人员、商业结果 |
| 典型决定 | 这个功能符不符合我们要做的游戏 | 这个功能这个版本做不做得完 |
| 典型产出 | 设计支柱、功能优先级、评审结论、砍功能的决定 | 排期、预算、人员配置、里程碑、对外沟通 |
| 失败的样子 | 游戏做出来了，但没有人说得清它好在哪 | 游戏很好玩，但晚了一年，钱花光了 |
| 手里的权力 | 设计上的否决权 | 资源上的决定权 |

**冲突时谁拍板：多数项目是制作人**【行业口径】。这一条要说清楚，因为很多新任主策在这里受挫。制作人对项目的存续负责，当排期和体验冲突时，最终选择权通常在他手上。但**组织权责并不统一**：有的公司主策同时是制作人；有的公司创意总监或工作室负责人握有最终设计权；也有主策与制作人平级、由更上一级仲裁的。**上岗第一周就该问清楚这个项目的 RACI 与汇报线：设计决定谁负责（R）、谁拍板（A）、谁必须被咨询（C）、谁只需被告知（I）。** 拍板权写不清楚的项目，冲突最后会以人际的方式解决。

但这不意味着主策只能接受。**主策在冲突里的义务是把代价说清楚，说到制作人可以负责任地做决定的程度。** 差别在于两种说法：

- 弱的说法："砍掉这个功能体验会变差。"（这句话没有信息，任何功能砍掉体验都会变差）
- 强的说法："砍掉多解验证之后，我们的第一支柱（用脑子赢，不用数值碾）在实际游戏里会失守。表现形式是：玩家卡关时的第一反应会变成'去练级'而不是'换阵容'，我们的差异化就没了，商店页上写的那句话就不成立。我建议要么保留验证但把关卡数砍半，要么承认我们这个版本做的是一款普通卡牌。"

第二种说法把"体验会变差"翻译成了**项目层面的后果**（差异化、市场定位），这才是制作人能拿来做决定的东西。**主策向上沟通的核心技能，就是把设计语言翻译成项目语言。**

### 2.2 主策不负责的三件事

**不负责替下属写案子。** 这是新任主策最常见的塌陷方式：看到案子不行，自己动手改，改着改着变成了自己写。结果是主策成为瓶颈、下属不成长、而且团队会逐渐停止思考（反正主策会改）。第 8 节讲介入的分寸。

**不负责所有细节。** 一个五十人的项目，主策不可能读完每一条规则。他要读的是每份案子的第一层（体验目标、循环位置、成功指标），第二层选择性读，第三层由写案子的策划和主程共同兜住。**注意 QA 在这里的位置**：QA 验证的是"实现和规格一致"，不是"规格本身对不对"——**第三层的设计所有权不会因为交给 QA 就转移出去**，写案子的人仍然是那些边界规则的作者。**主策把时间花在第三层，等于放弃了第一层。**

**不负责让所有人满意。** 设计支柱的作用就是排除一部分可能性，而每一条被排除的可能性背后都有一个喜欢它的人。一个让所有人都满意的主策，通常没有支柱。

## 3. 设计愿景与设计支柱

### 3.1 愿景是一个画面，不是一句口号

**设计愿景（design vision）**是对"这个游戏做成之后是什么样"的描述。它的检验标准很简单：**团队里的任何一个人读完，脑子里出现的画面是不是同一个。**

写愿景的一个可用格式是"目标玩家 + 时刻 + 感受"：

> 让一个每天只有半小时的上班族，在每周有一次"我靠脑子赢了一场本来打不过的仗"的时刻。

这句话的每一部分都在排除东西：目标玩家排除了重度肝帝，"每周一次"排除了"每天都有高光"（那意味着高光廉价），"靠脑子赢"排除了数值碾压，"本来打不过"排除了无难度。**一个不排除任何东西的愿景是废话。**

### 3.2 支柱是愿景的可执行版本

**设计支柱（design pillars）**是把愿景拆成 3~5 条可以用来**做判断**的原则。好支柱有三个特征：

**特征一：可以用来否决。** 这是唯一的硬标准。拿一条支柱去对一个具体功能，如果它永远给出"可以"，那它不是支柱，是口号。测试方法：**为每条支柱写出一个"它会否决掉的、看起来不错的功能"**。写不出来就删掉这条。注意这个测试问出来的是支柱里**不可破的那一句**（见本节末尾的"三种强度"）——一条支柱可以有红线之外的部分，但完全没有红线的支柱是口号。

**特征二：互相有张力。** 好的支柱之间应该拉扯。"每天 25 分钟就够"和"内容要有深度"是互相拉扯的，"策略取胜"和"卖养成"是互相拉扯的。**张力不是缺陷，是支柱的价值所在**：正因为它们互相拉扯，你才需要在具体场景里做判断，而判断的过程就是设计。一组彼此毫无冲突的支柱，说明它们都太软了。

**特征三：3~5 条。** 少于 3 条覆盖不了决策；多于 5 条没人记得住，而记不住的支柱在会议现场用不上。**支柱的使用场景是会议中间的三十秒，不是文档。**

**三种强度：把"不能碰的"和"要权衡的"分开。** 特征一和特征二合在一起有一个必须说清的地方：如果"每条支柱都能否决"加上"支柱之间互相拉扯"，再加上"支柱不能折衷"，那么任何一个同时触到两条支柱的提案都会无解——而真实项目里几乎每个提案都是这样。**解开的办法不是把支柱写软，是把每条支柱拆成三种强度**：

| 强度 | 它是什么 | 运算方式 | 谁能改、怎么改 |
|---|---|---|---|
| **红线（不可破）** | 破了这一条，这款游戏就不再是我们要做的那款。**数量要少：一条支柱最多一句红线**（可以点名几个同类功能，但必须是同一件事） | **布尔否决**：踩到即出局，不进加权，不谈折中 | 只能开一个"只讨论支柱"的会公开改，改完广播全团队 |
| **原则（可权衡）** | 方向明确，但强弱是连续的。**绝大多数正常取舍发生在这一层** | 不否决，但提案必须说清：往哪个方向拉了多少、拿什么补、代价记在哪 | 主策在具体场景里判断，判断连同代价写进决策记录 |
| **阶段目标（可分期）** | 这个版本要把这条支柱兑现到什么程度 | 写出本版本的实现程度 + 下一步的触发条件 | 随版本调整，写进决策记录即可 |

**一条支柱通常三层都有**：一句红线（"不做战力评分"）+ 一个方向（"越靠脑子赢越好"）+ 一个本版本的程度（"8 场硬仗验证三种解法"）。**写支柱时红线那一句必须单独拎出来写**，否则整条支柱都会被当成红线用，团队要么被卡死，要么索性整体绕过支柱——后者更常见也更糟。

张力的位置因此也清楚了：**张力发生在原则层和阶段目标层，红线不参与拉扯。** 如果两条红线真的会同时否决掉一个必需功能，那不是张力，是支柱写错了，必须回去改其中一条。这种情况应该极少——这正是把红线压到"每条支柱一句"的理由：红线越多，互相撞车的概率越高，而红线撞车是没有出口的。

### 3.3 坏支柱长什么样

| 坏支柱 | 为什么坏 | 改法 |
|---|---|---|
| "好玩" | 不可否决。没有任何功能会被"好玩"排除 | 说清是哪种好玩：策略的、收集的、社交的、手感的 |
| "画面精美" | 不是设计决定，是品质要求。它约束不了系统设计 | 如果美术风格真的是差异化的一部分，写成"我们的战斗必须在静帧截图里就能看懂"这种可否决的形式 |
| "留存和付费都要好" | 业务目标不是设计支柱。支柱是达成业务目标的手段 | 写成"我们靠什么留住人"：靠每周一次的高光？靠公会里的位置？ |
| "既硬核又休闲" | 张力没有被承认，于是变成了什么都要 | 把张力写进支柱本身："上手三分钟，精通三百小时"（Pardo 的 easy to learn, hard to master 就是这个句式的原型） |
| "对标《XX》并超越" | 竞品不是支柱，而且这条会让团队抄机制而不是抄意图 | 写清你想要《XX》的哪一部分体验，以及你**不要**它的哪一部分 |

一个好用的句式是 **"我们是 X，不是 Y"**。强制写出 Y，可以逼出否决力：

- "我们是**考策略**的，不是**考养成度**的。"
- "我们尊重时间，**不做出勤考核**。"
- "社交是互相看见，**不是互相占用**。"

### 3.4 三套假想手游的支柱

先给两套短的做对照，再给本章贯穿案例的完整版。

**假想 SLG《九州鼎》的支柱**：

1. 你的城不是你一个人的：任何重要目标都需要 5 人以上协作才能达成。
2. 每次出兵都是有去无回的承诺：行军有时间，伤兵有代价，命令发出后不能撤回。
3. 赛季结束一起清零：任何优势都不跨赛季继承。
4. 付费买的是**质量**不是**数量**：行动力对所有人相同。

**假想 IAA 休闲小游戏《叠叠塔》的支柱**：

1. 三秒内玩家必须做出第一个动作。
2. 一局不超过 90 秒，失败不惩罚、不打断。
3. 广告是玩家自己要的：只在玩家想要更多的那一刻出现。

注意这两套的形态差异：SLG 的支柱大多是**约束**（不能撤回、不跨赛季、行动力相同），休闲小游戏的支柱大多是**指标化的体验承诺**（三秒、90 秒）。品类不同，支柱的语法也不同，但共同点是：**每一条都能拿来当场否决一个具体提案。**

### 3.5 本章贯穿案例：《归墟》的设计支柱

《归墟》是本章虚构的一款**战棋卡牌手游**：格子战场、回合制、角色技能有位移和地形交互，主打阵容构筑的深度。

> **愿景**：让一个每天只有半小时的上班族，每周有一次"我靠脑子赢了一场本来打不过的仗"的时刻。

**支柱**（按 3.2 节的三种强度，每条都拆成"红线 / 原则 / 本版本的阶段目标"三格）：

| # | 支柱 | **红线**（踩到即出局） | **原则**（可权衡的方向） | **v1.0 阶段目标** |
|---|---|---|---|---|
| **P1** | **用脑子赢，不用数值碾** | 不做战力评分、推荐战力提示、"战力不足"拦截、付费直购战力 | 养成度对硬仗结果的影响越小越好，但**不为零**——它是打不过时的下限保障 | 8 场硬仗做到"同等养成度下能靠换阵容通过" |
| **P2** | **阵容是玩家的表达，不是攻略的复制** | 不做"官方推荐阵容"一键编队 | 解法数量与解法之间的优劣差距都是连续量，越多越平越好 | 8 场硬仗各验证过三套人工阵容能通关；普通关不保证多解，但不允许出现只有一种阵容能过的关卡 |
| **P3** | **每天 25 分钟就是完整的一天** | 不做出勤考核（连续登录考核、每日必做的定时活动） | 日常时长越短越好；"当日核心收益"的边界可以随版本调整 | 25 分钟内能拿到当日全部核心收益，之后玩是因为想玩 |
| **P4** | **社交是互相看见，不是互相占用** | 不做要求多人同时在线的必做玩法、不做把个人产出摊派到集体的考核 | 社交可以做深，但方向只能是"看见"（观摩、求助、炫耀），不能是"占用" | v1.0 只做观摩与求助；公会玩法延后到 v1.1 再评估 |

**注意红线那一列全部是"不做某个具体功能"的形式**——这是它和原则的最大区别：**红线必须能被一个具体提案直接命中**（有人提"加个战力评分"，当场出局），而原则只能给出方向，需要判断。

**张力检查**（张力发生在原则层与阶段目标层，红线不参与拉扯）：

| 张力 | 谁和谁 | 这个张力逼我们做什么 |
|---|---|---|
| P1 ↔ 商业化 | 卡牌手游的主要付费驱动是养成度，P1 直接限制了它 | 逼我们把付费卖成"新解法"（新角色 = 新的打法可能）而不是"新数值" |
| P2 ↔ 内容成本 | 多解意味着每关要验证多条路线，成本高 | 逼我们区分"硬仗"（保证多解）和"普通关"（不保证），并投入工具 |
| P3 ↔ 时长指标 | 25 分钟封顶等于放弃"用肝度换在线时长" | 逼我们靠"想玩"而不是"必须玩"来撑活跃，也就是逼我们把战斗本身做好 |
| P4 ↔ 公会留存 | 不做出勤考核，等于放弃了业界最有效的一类留存工具 | 逼我们找到不摊派的社交价值：观摩别人的解法、求助、炫耀 |

### 3.6 演示：用支柱否决一个看起来不错的功能

**提案**：加一个**战力评分**系统。玩家阵容有一个综合战力数值，每个关卡有推荐战力；战力不足时，进入前提示"你的战力低于推荐值，建议先提升实力"。

这个提案看起来非常合理：几乎所有卡牌手游都有；它降低了玩家的挫败（避免反复撞墙）；它给养成线一个清晰的目标；它还顺便是一个天然的付费引导。四条理由，条条成立。

**用 P1 的红线否决**（"战力评分"就写在 P1 红线那一格里，所以这是布尔否决，不进入权衡）：战力评分是一个**把策略问题翻译成数值问题的装置**。它对玩家说的话是"打不过是因为你不够强"，而 P1 说的是"打不过是因为你没找到打法"。玩家会照着系统告诉他的做——**你放一个战力数字在那里，玩家的第一反应就永远是去练级，不是去换阵容。**

**P2 也反对，但方式不同**（这一条是原则层：评分不在 P2 的红线里，它是把 P2 的方向拉反了，所以严格说它是"要记账的代价"而不是第二次否决）：一个单一的评分数字会把多解压平。当阵容 A 战力 12000、阵容 B 战力 9000 时，即使 B 才是这一关的解法，绝大多数玩家也会用 A 并在失败后去练级。**评分制造了一个虚假的偏序，而 P2 要的恰恰是"无严格优劣"。**

**否决之后要给替代**（[第 26 章](./26-design-critique.md)的 critique 第四步同样适用于主策）：提案想解决的真实问题是"玩家撞墙时不知道该干什么"。这是个真问题。替代方案是：**不显示"你够不够强"，显示"这一关会考什么"**——把敌方的机制做成可读的标签（远程压制、召唤、地形封锁、多段位移），失败结算时高亮"你被什么打败了"。这样玩家撞墙后的第一反应变成"我需要一个能处理召唤的角色"，正好是 P1 和 P2 想要的行为。

**这段推理值得记住的地方**：支柱否决的不是"这个功能不好"，而是"这个功能会把玩家的行为导向我们不要的方向"。**功能塑造行为，行为塑造玩家对游戏的认知。** 这是主策必须比所有人都看得远的一层。

### 3.7 支柱与一页纸的关系

`templates/one-pager.md` 里有一栏是"体验目标"。**支柱是全局的，一页纸的体验目标是支柱在一个具体系统上的投影。** 两者的关系可以写成一条流程规则：

> 任何一页纸概念在进入评审第一层时，必须回答："它服务于哪条支柱？它和哪条支柱有张力？"

第二问比第一问重要。所有提案都能声称自己服务于某条支柱（很容易），但只有认真想过的提案能说清自己在和哪条支柱拉扯。**"这个提案不和任何支柱冲突"通常意味着提案人没有理解支柱，或者这个提案太无关紧要。**

支柱在评审里的位置也因此确定了：它是[第 26 章](./26-design-critique.md)第一层的**判断依据**。第一层问"为什么要做"，支柱回答"我们做什么样的游戏"，两者一对，第一层就有了客观标准，而不是靠谁的资历高。**支柱最大的组织价值，是把设计争论从"人的对抗"变成"提案对标准"。**

## 4. 优先级与取舍

### 4.1 四个维度

一个候选功能进入排期之前，主策要给它四个判断：

| 维度 | 问什么 | 谁能回答 |
|---|---|---|
| **价值** | 它解决什么问题？对哪一类玩家？影响面多大？ | 主策 + 数据 |
| **成本** | 开发、美术资源、测试、后续维护、教学成本 | 主程 + 主美 |
| **风险** | 最坏情况是什么？失败了能不能回滚？它会不会污染别的系统？ | 主策 + 主程 |
| **对支柱的贡献** | 加强了哪条？和哪条冲突？ | 主策 |

前三个维度是通用的项目管理，第四个是主策独有的。而且它和前三个的**运算方式不一样**：

**红线不是加分项，是否决项。** 常见的错误做法是给四个维度打分加权求和，算出一个优先级排序。这套方法在红线上会失效：一个高价值、低成本、低风险但踩了红线的功能，会在加权求和里得到很高的分数——**因为"踩红线"这件事被平均掉了**。

按 3.2 节的三种强度，正确的运算顺序是三步：

```
   第一步：红线筛（布尔）
   ┌──────────────────────────────┐
   │ 踩到任何一条红线？            │
   │   是 → 出局（除非公开改红线） │
   │   否 → 进入第二步            │
   └──────────────────────────────┘
                 ↓
   第二步：原则层记账（不否决，但必须写下来）
   ┌────────────────────────────────────────┐
   │ 它把哪条原则往哪个方向拉了多少？        │
   │ 拿什么补？代价写进决策记录              │
   │ 说不清 → 打回补写，这不是否决           │
   └────────────────────────────────────────┘
                 ↓
   第三步：价值 / 成本 / 风险排序（连续）
```

**第二步是新任主策最容易跳过的一步**，跳过的后果是两种极端：要么把所有原则当红线用，团队发现什么都做不了，于是开始整体绕过支柱；要么因为"这条不是红线"就不记账，半年后回头看，每条原则都被拉走了一点点，加起来这款游戏已经不是当初那款。**原则不否决提案，但原则的每一次让步都必须留下一行记录**——这一行记录就是半年后你唯一能拿出来的证据。

**"除非公开改红线"这条出口必须存在，但它的门槛要高。** 红线不是不可修改的教条，项目会学到新东西。但改红线是一个**独立的、公开的决定**，要重新过一遍全团队，而不是在某个功能的排期会上顺手改掉。区分方法：如果一个提案要求改红线，那就先开一个只讨论支柱的会，然后再回来评这个提案。**顺手改红线的团队，三个月后会发现自己没有支柱。**（原则和阶段目标不需要走这套流程，它们本来就是拿来在具体场景里调的——但同样要记账。）

### 4.2 三个桶和一张不做清单

通过筛选的功能分三个桶：

| 桶 | 含义 | 判断句 |
|---|---|---|
| **必须做** | 没有它，支柱不成立 | "如果不做这个，P1 在实际游戏里就是一句空话" |
| **值得做** | 它加强某条支柱，但支柱没有它也成立 | 排序靠价值/成本比 |
| **有空做** | 打磨、便利、锦上添花 | 默认不排期，有空档才做 |

三个桶之外还要有第四份文件：**不做清单（won't-do list）**。它记录被否决的提案、否决的理由、以及**什么条件下会重新讨论**。

不做清单的价值有三条：

1. 同一个提案会被不同的人反复提出（尤其是"竞品有"类的提案），有清单就不用每次重新论证；
2. 它是新人理解支柱最好的教材——**看被否决的东西比看被通过的东西更能学到判断标准**；
3. "什么条件下会重新讨论"这一栏把否决变成了可撤销的判断，而不是权力表态，这对团队氛围很重要。

工程类比：这就是架构决策记录（ADR）里的"Rejected alternatives"一节。你写服务设计文档时记录"为什么不用消息队列"，是同一件事。

## 5. 砍功能

### 5.1 三个该砍的信号

kill your darlings（杀死你的心头好）这句话的重点在 darlings：**最难砍的从来不是明显没用的功能，是那些做得很用心、团队投入了感情、但已经不服务于游戏的东西。**

三个信号，出现任何一个就该认真考虑砍掉：

| 信号 | 表现 | 为什么是砍的信号 |
|---|---|---|
| **它需要另一个功能来拯救** | "这个系统玩家用得少，我们加个引导 / 加个日常任务 / 加个红点" | 用新功能给旧功能续命，是在为沉没成本追加投资 |
| **它在测试里需要解释** | 每次给人试玩，都得先说明"这个是这样用的" | [第 26 章](./26-design-critique.md)的第 14 条谬误：引导补不了设计 |
| **它不再服务于任何支柱** | 支柱迭代过了，或者这个功能是在支柱确定之前立项的 | 它现在是纯粹的复杂度 |

还有一个不是信号但常被误当成信号的：**"我们已经投入了三个月"**。投入是沉没成本，它对"该不该继续"这个问题没有信息量。它唯一的合法用途是估算"砍掉的话我们能回收多少"（通常是：美术资源可以复用，代码不行）。

### 5.2 什么时候砍最便宜

按[第 14 章](./14-design-process.md)的阶段划分：

```
 概念 → 原型 → 垂直切片 → alpha → beta → 上线 → 运营
  ↑砍最便宜                          ↑砍开始伤人      ↑砍伤玩家
```

**垂直切片阶段是砍功能的最后一个便宜窗口。** 过了这个点，功能开始互相咬合（别的系统开始依赖它、UI 开始为它留位置、数值开始为它配表），砍它的成本从"删掉它"变成"删掉它并修好所有依赖"。

上线后的砍更麻烦，因为它涉及玩家已经投入的资源。上线后砍功能的可选做法（【行业口径】）：直接下线并全额返还投入资源；保留入口但停止更新（"冷冻"）；把它合并进另一个系统。第三种最贵但对玩家最友好。**关键是：无论哪种，都要提前公告并给出补偿方案，因为玩家愤怒的来源通常不是"功能没了"，是"我投进去的东西没了"。**

### 5.3 怎么沟通

砍功能的沟通有三个对象，说法完全不同：

**对作者**：单独说，先说结论再说理由，理由要落到支柱上而不是质量上。

> "这个系统我决定砍掉。不是因为你写得不好——第二版的边界处理比我写的干净。是因为它和 P3 冲突：它要求玩家每天上线三次，而我们承诺了 25 分钟一次搞定。这个冲突在立案的时候我就该看出来，是我的问题。你在这个案子里做的耦合矩阵我要拿去给别人当范例。"

三个要点：**结论在前**（不要用五分钟铺垫让人猜）、**理由是支柱不是质量**（否则等于说他能力不行）、**承认自己的责任**（如果确实是立案时该发现的）。

**对团队**：公开说，写进不做清单，说明这是什么类型的决定。团队最怕的不是功能被砍，是**不知道砍的标准是什么**——那意味着自己的东西下次也可能被莫名其妙砍掉。**每一次公开的、有理由的砍功能，都是在给支柱增加可信度。**

**对上（制作人 / 老板）**：说清楚砍掉之后省下的资源去哪了。"砍掉 A，把两周挪给 B 的多解验证"比"砍掉 A"容易通过得多，因为前者是一个资源调度决定，后者听起来像是认赔。

### 5.4 砍不掉的三种情况

| 情况 | 为什么砍不掉 | 对策 |
|---|---|---|
| 老板的功能 | 权力，不是论证 | 不要正面对抗。把它做成可降级、可下线的独立模块，并且**显式记录它对支柱的伤害**，等数据说话 |
| 已经对外宣传过的功能 | 承诺成本 | 缩范围而不是砍（把"完整系统"降级成"一个活动"），保住承诺的形式 |
| 团队有情感投入的功能 | 人 | 不要靠说服，靠证据。安排一次[第 20 章](./20-playtesting-and-validation.md)的目标用户测试，让作者自己去看玩家的反应 |

第三条尤其有效，也是[第 20 章](./20-playtesting-and-validation.md)那一整章在主策工作里的用途：**测试的作用不只是发现问题，还是把"主策的判断"变成"团队共同看到的事实"。** 一个看过五个真实玩家在自己系统前卡住的作者，不需要被说服。

## 6. 跨职能协作

主策的时间有很大一块花在和其他职能的负责人对齐。每个职能有自己的语言和自己的怕，你要给他的东西也不同：

| 对象 | 他的语言 | 你必须给他 | 典型冲突 | 怎么谈 |
|---|---|---|---|---|
| **主程** | 成本、可行性、风险 | 功能的分级（体验必需 vs 可降级）、早期的技术风险清单 | "这个做不了" vs "这个必须有" | 不要问"这个多贵"，问"**什么是便宜的**"。然后在便宜的东西里找能达成体验目标的组合 |
| **主美** | 资源量、风格一致性、排期 | 数量级早给、细节晚给；复用规则；"这一屏最重要的是什么" | 资源量在实现时翻倍 | 先给"这个系统大概需要多少个新图标 / 多少套动作"的量级，再谈具体；把"必须新做"和"可以复用"分开 |
| **数值** | 曲线、投放回收、参数 | 参数清单 + **体验要求，不写数字**（"新手第 3 天该解锁""一周攒够一次") | 数值配出来的曲线和体验目标对不上 | 用"玩家在第几天应该感觉到什么"描述，让数值反推曲线形状；然后你验收的是**感觉**不是数字。数值方法见 [game-numeric](../game-numeric/README.md) |
| **运营** | 节奏、活动、玩家情绪 | 这个系统的**可运营参数**清单（哪些开关、哪些倍率、哪些内容位可以被活动使用） | 运营想用系统做一个它没设计过的活动 | 在系统案里就写"这个系统能被活动怎么用"（[第 22 章](./22-live-ops-design.md)）。没写清楚，运营就会去找程序改代码 |
| **发行** | 买量、素材、市场定位、竞品 | 一句话卖点、目标用户画像、差异化说明、可做成素材的高光时刻 | 发行要求加一个"市场上都有"的功能 | 把要求翻译回用户问题（"你担心的是买来的用户第一天看不到熟悉的东西吗"）；如果翻译不了，就明确它是市场决定而不是设计决定，并记录代价 |

### 6.1 一个具体的例子：和主程谈成本

回到第 1 节的第二件事：多解验证要三人月的 AI 模拟器。

**错误的谈法**是在"做还是不做"上拉锯。主策说"P2 是我们的支柱，必须做"，主程说"这个版本没有三人月"，两个人都对，谁也说服不了谁。

**正确的谈法**从主程的语言开始：

> **主策**：先不谈做不做。我想知道，如果我们要在这个版本里对**8 场关卡**（不是全部 60 场）验证"至少三种解法能通关"，最便宜的做法是什么？
> **主程**：8 场的话，不用做完整模拟器。我可以把战斗逻辑抽出来做个命令行的批量跑分工具，给定阵容和关卡跑一千次，输出通关率。大概两周。但它不会自动搜索阵容，得你们给候选阵容。
> **主策**：候选阵容我们手动出，一场出五套。那我们能验证的是"这五套里有几套能过"，不是"是否存在三种解法"。
> **主程**：对。要自动搜索就得上 AI，那是三人月。
> **主策**：够了。我们这个版本的承诺降级成"**每场硬仗，我们验证过至少三套阵容能过**"，这个承诺对玩家是够的。完整模拟器排到下个版本，理由是关卡数上到 100 之后手工出阵容不可行。

发生了三件事：**范围被缩小**（60 场 → 8 场硬仗）、**承诺被降级但没有取消**（"存在三种解法"→"验证过三套能过"）、**完整方案被排期而不是被拒绝**（并且给了触发条件）。

这就是取舍的实际形态。注意主策**没有放弃 P2**：P2 的红线（不做"官方推荐阵容"一键编队）没有被碰，被降级的是 P2 的**阶段目标**——本版本兑现到什么程度。**红线不能折衷；原则的强弱和阶段目标的实现程度可以谈。** 这个区别是主策最需要练的判断之一：如果这次的降级是"8 场硬仗也不保证多解，先上线看数据"，那就是把 P2 的阶段目标降到了零，等于这个版本没有 P2——**阶段目标可以低，不能为零**，那才是该拒绝的。

## 7. 设计团队的组织形态

三种典型形态，各有适合的项目：

| 形态 | 怎么运作 | 适合 | 优点 | 失败模式 |
|---|---|---|---|---|
| **Cabal**（Valve） | 临时组成的跨职能小组（策划 + 程序 + 美术 + 关卡），共同对一段体验负责，轮换；没有固定的"设计师"角色 | 强创意、体验驱动、团队规模中等、成员资深 | 设计决定由实现者共同做出，几乎没有传递损耗 | 新人无法快速上手；决策慢；规模上去之后会分裂成派系 |
| **小 cell**（Supercell 式，【行业口径】） | 独立小团队完整负责一个产品，高自主权，失败快速关停 | 需要多方向试错的公司层面；单产品团队 10 人以内 | 决策极快；责任清晰 | 需要公司层面容忍高失败率；不适合已经上线的大 DAU 产品 |
| **传统金字塔** | 主策 → 若干资深策划（各带一条线）→ 系统/数值/关卡/文案策划 | 大团队、长线运营手游、需要稳定产能 | 可扩展、职责清晰、便于培养新人 | 传递损耗大；信息在层级间失真；主策容易脱离一线 |

Valve 的 cabal 有一手资料：Ken Birdwell 在 1999 年写过《The Cabal: Valve's Design Process for Creating Half-Life》【实证】，描述了他们如何用一个跨职能小组反复推敲每一段关卡体验。它值得读的地方不在于组织图，而在于它揭示了一件事：**设计的传递损耗主要发生在"想出来的人"和"做出来的人"之间，cabal 的解法是让这两拨人是同一拨。**

Supercell 的小 cell 模式在业内被大量引用，但公开的一手材料主要是访谈和媒体报道，具体做法各处说法不一，所以本课标【行业口径】。

**国内手游团队大多是金字塔**【行业口径】；至于原因，本课的解释是长线运营手游需要稳定、可预测的产能，而 cabal 和 cell 都是为不确定性优化的组织形态——**这个因果解释是【推导】，没有公开研究支持，你完全可以有别的解释（比如它只是从端游时代沿袭下来的路径依赖）。**但金字塔可以**局部借用** cabal：在做一个高风险的新玩法时，临时抽一个跨职能小组关起门来做垂直切片，做完再回到金字塔里量产。**这是本课推荐给你的实际做法**：组织形态不是二选一，是分场景使用。

## 8. 带人：怎么评审新人的案子而不是替他写

主策评审下属案子时有三个介入层次，**越靠前越好**：

| 层次 | 做法 | 什么时候用 | 对成长的影响 |
|---|---|---|---|
| **一：问问题** | 只问[第 26 章](./26-design-critique.md)第一层的五个问题，不给任何方向 | 默认。案子的问题在"没想清楚" | 最好。他自己找到答案 |
| **二：给约束** | 不给方案，给边界："这个方案不能要求玩家每天上线三次""这个系统不能读公会数据" | 他反复卡在同一个地方，或者时间不允许再迭代 | 中等。他在你划的框里自己解 |
| **三：给方案** | 直接说该怎么做 | 紧急，或者这条设计线的一致性必须由你保证 | 最差。用一次要说明"这次我直接给方案，因为 X" |

**判断标准是"这个问题他自己能不能想出来"，不是"我能不能更快"。** 主策永远更快，这不构成理由。

一条很实用的自查：**如果你在评审时说的话超过作者说的话，你就在替他写案子。**

### 8.1 怎么分配系统

分配系统的默认思路是"谁擅长给谁"，这在短期最优、长期最差。更好的思路是按**这个人下一步该长什么能力**来分：

| 他现在的短板 | 给他什么系统 |
|---|---|
| 只会写规则，不会说体验目标 | 一个体验目标很明确但机制很自由的系统（比如"让玩家愿意看别人的阵容"） |
| 只想着自己的系统 | 一个耦合很多的系统（活动、公会），逼他画耦合矩阵 |
| 不敢做减法 | 一个明确要求"只能做三条规则"的系统 |
| 从不验证 | 一个必须做纸面原型才能定的系统（[第 14 章](./14-design-process.md)） |

同时保留一条纪律：**风险最高的系统不要给正在长能力的人**。培养和交付是两个目标，一个系统只能服务一个。

### 8.2 主策最常见的两个带人错误

**第一，自己写所有关键案子。** 症状是主策成了项目里唯一理解全局的人。这在短期看起来效率最高，长期的代价是：主策变成瓶颈、无法休假、团队不成长、而且**主策自己的案子没有人敢真正评审**。解法是强制把至少一个关键系统交出去，并且接受第一版会比自己写的差。

**第二，只在评审会上出现。** 主策如果只在评审会上给意见，下属拿到的全是"事后的否定"。更有效的介入点是**一页纸阶段**：花 20 分钟和作者过一次一页纸，能省掉后面两周的返工。**主策的时间应该往前放，不是往后放。**

## 9. 设计文化

文化不是标语，是**几条被反复执行的具体做法**。三条最值得建立的：

### 9.1 决策记录

每一个重要的设计决定，记录四样：决定是什么、当时的理由、被否决的替代方案、什么条件下重新讨论。这就是第 4.2 节的不做清单的扩展版，和你写服务架构决策记录是同一回事。

它解决的问题很具体：**手游项目的生命周期是三到五年，而人员流动是一到两年。** 两年后没有人记得"为什么体力不能买"，于是有人提出来加，于是整个论证要重做一遍——或者更糟，没人论证就加了。

### 9.2 失败复盘不追责

版本上线后的复盘会，只要出现"这是谁的问题"，这个团队的复盘就结束了：从那次起，所有人在复盘会上说的都是防御性的话。

具体做法：**复盘的对象是"当时的决定和当时可得的信息"，不是人。** 关键提问是"我们当时掌握的信息，能不能推出这个结论"——

- 能，但我们没推出来 → 这是流程问题（评审清单缺了一条？），改流程；
- 不能，信息不够 → 这是验证问题，下次这类决定前要先做原型或测试；
- 能，也推出来了，但被覆盖了 → 这是决策问题，回去看"未解决的分歧"那一栏（[第 26 章](./26-design-critique.md)）。

三种结论对应三种改进，没有一种需要指认某个人。

### 9.3 玩自己的游戏

听起来是废话，实际上是手游团队最常失守的一条。原因很具体：**开发者账号有 GM 权限、跳过引导、无限资源，所以开发者玩的从来不是玩家玩的那个游戏。**

可执行的做法：

- 每个策划有一个**纯净账号**（无 GM 权限、从头开始、不用内部渠道），并且每个版本至少用它玩满一次日常流程；
- 主策每个版本必须**从零开一个新号走完前三天**（这是发现 FTUE 问题最有效的手段，见[第 18 章](./18-onboarding.md)）；
- 定期玩竞品，并且是**认真玩**（充一点钱、进一个公会），不是"看看"。

### 9.4 用原则做决定：暴雪的例子

Rob Pardo 在 GDC 2010 的演讲《Making a Standard (and Trying to Stick to It!): Blizzard Design Philosophies》里讲了暴雪当时的一批设计原则【实证】，其中两条流传最广：

- **"concentrated coolness"**（浓缩的酷）：与其做一百个平庸的东西，不如做十个非常好的东西。这条直接对抗[第 26 章](./26-design-critique.md)的第 1 条谬误（more is better）。
- **"easy to learn, hard to master"**（易于上手，难于精通）：这是第 3.3 节推荐的"把张力写进支柱"的经典范例——它不是两个要求的并列，而是承认了一个张力并要求同时满足。

这个演讲对本章的价值不在于这两句话本身（它们已经被引用到失去意义了），而在于它展示了**一个组织如何把设计判断沉淀成可复述的原则，并在具体决定中援引它们**。你的支柱不需要写得像暴雪那样漂亮，但它需要具备同一个属性：**在会议中间，有人能说出"这不符合我们的第 X 条"，并且所有人都知道那是什么意思。**

## 10. 主策的一周

一个长线运营手游项目的主策，典型一周大致长这样（【行业口径】，项目阶段不同差异很大；研发期评审多，运营期数据和活动多）：

| 工作 | 时间占比 | 说明 |
|---|---|---|
| 评审别人的案子与一页纸 | 25~30% | 本课第 26 章那一套。**这是主策产出最高的时间** |
| 跨职能沟通（程序/美术/数值/运营/发行/制作人） | 20~25% | 第 6 节 |
| 玩自己的游戏 + 玩竞品 | 10~15% | 第 9.3 节。这一块最容易被会议吃掉，要主动锁进日程 |
| 看数据与复盘 | 10% | 上一版本的成功指标 vs 实际（[第 20 章](./20-playtesting-and-validation.md)、[第 22 章](./22-live-ops-design.md)） |
| 自己写文档（支柱、优先级、少量关键案子） | 10~15% | 注意这一栏很小 |
| 带人（一对一、案子辅导） | 10% | 第 8 节 |
| 救火 | 剩下的 | 永远有 |

对照[第 01 章](./01-what-designers-do.md)给的系统策划一周（写文档 30~40%，沟通 25~35%），差别很清楚：**从系统策划到主策，最大的变化是"自己写"的比例大幅下降，"评审 + 沟通 + 判断"的比例大幅上升。**

这个转变对工程师背景的人有个特定的陷阱：你擅长的是"自己写清楚"，而这项能力在新岗位上占比只剩 10~15%。**很多技术出身的主策会不自觉地把时间挪回自己写文档**，因为那是他有掌控感的事。识别信号：如果你这周写的字比读的字多，你可能没在做主策的工作。

## 11. 贯穿案例：用《归墟》的支柱处理三个取舍

现在回到第 1 节的三件事，用 3.5 节的四条支柱各处理一次。注意每次处理的**输出物**都是三样：一个决定、一条记录、一个可能的反悔条件。

### 11.1 场景 A：多解验证要三人月

**提案**：主程说，要保证 P2（每场硬仗至少三种解法）真的成立，需要一套 AI 模拟器自动搜索阵容，三人月。这个版本没有三人月。

**支柱判断**：这不是"要不要 P2"的问题——P2 的红线不参与投票。能谈的是"这个版本 P2 的**阶段目标**定在哪"。

**决定**（过程见第 6.1 节）：

- 本版本范围缩到 **8 场硬仗**，用两周的批量跑分工具验证"每场至少三套人工候选阵容能通关"；
- 普通关不做多解保证，但也**不做单解设计**（不允许出现"只有一种阵容能过"的关卡，这是可以靠评审拦住的）；
- 完整 AI 模拟器排进下一个版本，触发条件写清楚：**关卡数超过 100 之后人工出阵容不可行**。

**记录**（写进决策记录）：

> P2 在 v1.0 的阶段目标：8 场硬仗人工验证三解。降级理由：工具成本。**红线未被触碰，被限制的是覆盖范围。** 反悔条件：如果上线后玩家攻略社区自发收敛到单一阵容（可观测：某阵容在硬仗通关分享中占比 > 70%），说明人工验证不足以支撑 P2，AI 模拟器提前立项。

### 11.2 场景 B：运营要"扫荡券"

**提案**：运营希望加一个付费道具"扫荡券"，可以直接跳过已通关关卡的战斗过程拿到奖励。理由充分：玩家有重复刷图需求、这是卡牌品类的标配、它是一个健康的付费点（卖时间不卖战力）、而且它服务于 P3（尊重时间）。

**这个提案比第 3.6 节的战力评分难判断得多**，因为它确实服务于一条支柱。**注意它没有踩到任何一条红线**——付费扫荡券不是战力评分、不是一键编队、不是出勤考核、也不要求多人在线。**它是一次纯粹的原则层冲突，而原则层冲突不能靠"否决"解决，只能靠找第三方案或者记账。**

**支柱判断**：

- **P3 支持它**：跳过重复战斗确实是在尊重时间。
- **P1 的方向反对它，反对的方式很微妙**：扫荡这个需求存在，本身说明**有一批战斗玩家不想打**。而 P1 说的是"战斗是这个游戏的核心乐趣"。如果核心乐趣需要被跳过，那不是一个付费机会，**那是 P1 的失败信号**。把它做成付费点，等于把一个诊断信息变成了收入来源——这正好是[第 26 章](./26-design-critique.md)的第 8 条谬误（用付费掩盖设计问题）。

**决定**：

- **不做付费扫荡券。**
- 做**免费的一键扫荡**，条件是该关卡已通关（这直接兑现 P3，而且不收钱）。
- 关键动作：把"**哪些关卡被大量扫荡**"做成一个常规监控指标，当成 **P1 的反指标**。某个关卡扫荡率高，意味着那一关的战斗没有提供决策，该重做或删掉。

**记录**：

> 扫荡功能免费。放弃的收入：卡牌品类里扫荡类道具通常有稳定流水（【行业口径】）。换来的：一个持续可用的 P1 诊断信号。反悔条件：如果免费扫荡导致核心战斗的日均场次跌破某个阈值（说明玩家在逃避战斗而不是节省时间），重新讨论——但那时该讨论的是战斗设计，不是扫荡定价。

**这个场景的教学点**：当两条支柱的**原则层**指向相反方向时，先不要在两者之间取中点，**先花力气找那个能同时满足两条的第三方案**。免费扫荡 + 扫荡率当反指标，就是这个第三方案。取中点（"扫荡券卖便宜一点"）会同时损失两条原则，而且不留下任何记录。**找不到第三方案时才做取舍，取舍的形式是"往一边拉多少 + 拿什么补 + 写进记录"，不是投票。**

### 11.3 场景 C：公会出勤排行

**提案**：加公会 Boss 的每日出勤 + 出勤排行，公会长可以看到谁没打。数据部门给的估算是能拉动 7 日留存，开发量两周。

**支柱判断**：

- **踩到 P4 的红线**："不做把个人产出摊派到集体的考核"。出勤排行是一个**给公会长的催人工具**——你提供了它，公会长就会使用它（[第 26 章](./26-design-critique.md)第二层清单：同盟长可以用这个系统要求成员做什么）。
- **也踩到 P3 的红线**："不做出勤考核"。每日出勤就是出勤考核，字面命中。

两条红线同时被命中，这是最干净的情况：布尔否决，不进入原则层的讨论。

**但决定不是简单地说"不做"**，因为提案背后的问题（公会缺少共同做的事）是真的。**决定**：

- 否决"每日出勤"和"出勤排行"；
- 保留公会 Boss，改成**每周一次、异步、任何时间打都算**、只显示公会总伤害不显示个人排名；
- 增加一个 P4 正面的功能：公会成员可以**观摩别人打硬仗的录像**，并且可以"求助"（贴出自己卡住的关卡，别人贴阵容）。这是"互相看见"的正面形态。

**记录**（这一条最重要）：

> 否决公会出勤排行。**明确放弃的收益：数据部门估算的 7 日留存提升。** 理由：同时踩 P3、P4 的红线。反悔条件：如果 v1.0 上线三个月后 7 日留存持续低于目标线，且归因分析显示公会活跃是主要缺口，则**重新讨论 P3/P4 的红线本身**（开一个只讨论支柱的会），而不是在这个功能上开口子。

**为什么"明确放弃的收益"必须写下来**：三个月后如果留存不好，一定会有人说"当初那个出勤排行要是做了就好了"。有这条记录，讨论的起点就是"我们当时知道会损失这部分，选择了保住 P3/P4，现在要不要改变这个选择"——这是一个可以理性讨论的问题。没有这条记录，讨论的起点是"当初谁拍板不做的"，那是一个找人的问题。

**三个场景的共同结构**：

```
 提案 → 红线筛（布尔）
          ├─ 踩线 → 出局或整体改造（场景 C：两条红线同时命中）
          └─ 不踩线 → 原则层记账 → 三种结果之一
                  ├─ 不拉扯任何原则：直接进入价值/成本/风险排序
                  ├─ 拉扯但找到第三方案：改造提案（场景 B）
                  └─ 拉扯且无第三方案：按代价决定做不做，
                     写下"往哪边拉了多少 / 放弃的收益 / 反悔条件"
     （阶段目标的程度可以谈——场景 A；红线不在这一层谈）
```

## 12. 常见误区

| 误区 | 为什么错 | 正确的想法 |
|---|---|---|
| "设计支柱就是游戏的卖点" | 卖点对外，支柱对内；卖点用来吸引人，支柱用来否决功能 | 支柱的唯一硬标准是"能不能用来否决一个看起来不错的功能" |
| "支柱之间不该互相冲突" | 没有张力的支柱都太软，覆盖不了真实决策 | 张力是支柱的价值所在；但张力只发生在原则层和阶段目标层，红线之间不该互相否决 |
| "每一条支柱都是不能碰的红线" | 支柱全是红线，任何同时触到两条的提案都无解，团队要么卡死要么整体绕过支柱 | 红线全部加起来 1~3 条，做布尔否决；其余是可权衡的原则和可分期的阶段目标，**原则的每次让步要记账** |
| "把价值、成本、风险、支柱加权求和排优先级" | 加权会把"踩红线"平均掉 | 红线是布尔筛选（第一步），原则层记账（第二步），价值/成本/风险排序（第三步） |
| "主策要对每个细节负责" | 一个人读不完所有第三层，读了就没时间读第一层 | 主策读第一层，选择性读第二层，第三层由写案子的策划和主程兜住；QA 验证实现与规格一致，不承担规格本身的设计所有权 |
| "案子不行我改一下更快" | 短期最快，长期让自己成为瓶颈、让团队停止思考 | 优先"问问题"，其次"给约束"，"给方案"要说明为什么这次直接给 |
| "砍功能是承认失败" | 砍功能是支柱在起作用的证据；不砍才是没有支柱 | 每次公开的、有理由的砍功能都在增加支柱的可信度 |
| "都投入三个月了，做完再说" | 沉没成本对"该不该继续"没有信息量 | 投入只能用来估算"能回收多少"，不能用来论证"该继续" |
| "跟主程谈就是问这个多少人日" | 只谈价格，你永远只能在贵和不做之间选 | 问"什么是便宜的"，然后在便宜的组合里找达成体验目标的路径 |
| "支柱定了就不能改" | 项目会学到新东西，教条化的支柱会被绕过而不是被遵守 | 红线可以改，但必须是独立的、公开的决定，不能在某个功能的排期会上顺手改；原则和阶段目标本来就是拿来在场景里调的 |
| "我们是小团队，不需要写支柱" | 小团队的口头共识在第一次意见分歧时就会暴露它并不存在 | 越是靠默契的团队，越需要把默契写成 3~5 条能被援引的话 |

## 13. 动手

### 13.1 拆解 / 阅读任务：反推你公司项目的设计支柱

你所在的项目大概率没有明确写下来的支柱，或者写了但没人用。这个练习是**从已经做出的决定反推支柱**：

1. 列出你们项目最近半年做的 **10 个功能**和你知道的 **3 个被否决的提案**（否决的更有价值，去问策划要）。
2. 找出这些决定背后隐含的判断标准，尝试归纳成 **3~5 条支柱**，每条用"我们是 X，不是 Y"的句式写。
3. **一致性检查**：拿这 3~5 条去对那 13 个决定，有几个能被解释？解释不了的那些，说明要么支柱写漏了一条，要么那个决定本身是没有标准的（这个发现本身很有价值）。
4. **最近功能检查**：拿最近上线的一个功能，逐条对你反推出来的支柱，判断它是加强、无关还是冲突。如果是冲突，写下"如果当初有这条支柱，这个功能会被怎么改"。

把结果写进 `notes/作业/27-反推支柱.md`。

### 13.2 写作作业：一份设计支柱文档

给一款你想做的手游（可以是你公司项目的假想续作，也可以是全新的）写一份设计支柱文档，放进 `notes/作业/27-设计支柱.md`。要求：

- **愿景**一段，包含目标玩家 + 时刻 + 感受，且必须排除掉一些东西
- **3~5 条支柱**，每条用"我们是 X，不是 Y"的句式
- **每条支柱附一个"它会否决掉的、看起来不错的功能"**。写不出来的那条删掉——这是本作业最关键的检验
- **把每条支柱拆成红线 / 原则 / 本版本阶段目标三格**（3.2 节）。每条支柱最多一句红线，且必须是"不做某个具体功能"的形式；写成方向（"越……越好"）的一律归到原则列
- **一张张力表**：至少写出两组支柱之间的拉扯，以及每组张力"逼我们做什么"
- **用支柱处理两个取舍场景**，每个场景给出：决定、记录（含明确放弃的收益）、反悔条件
- 附一份 **不做清单**的开头，至少 3 行，每行有"否决理由"和"什么条件下重新讨论"

### 13.3 思考题

1. 第 11.2 节里，扫荡券的提案同时被一条支柱支持、被另一条支柱反对。除了文中给的"免费扫荡 + 扫荡率当反指标"，你还能想出别的第三方案吗？你的方案会损失什么？
2. 第 2.1 节说"冲突时制作人拍板"。如果制作人反复否决主策的设计判断，主策还剩下什么？（提示：想想不做清单里的"明确放弃的收益"和反悔条件在这里的作用。）
3. 你所在的项目如果引入"不做清单"，最先被写进去的三条会是什么？为什么它们至今没有被正式否决过？
4. 第 10 节说"如果你这周写的字比读的字多，你可能没在做主策的工作"。这条对你现在的服务端工作成立吗？如果你成为技术负责人，它会不会成立？
