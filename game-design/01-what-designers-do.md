# 01 - 策划是干什么的

> **本章目标**：建立对"策划"这个职业的准确认识。学完你应该能说出策划的六个岗位各自交付什么、一个案子从想法到上线经过哪些人手、以及站在服务端开发的位置上你已经拥有了策划的哪一半能力、缺的是哪一半。
> **本章不需要拆解游戏**，但第 8 节要求你去读一份自己公司的案子。

---

## 1. 从你的位置看：策划交付的到底是什么

你写服务端，一定收到过策划的"案子"。回想一下你对案子的典型抱怨：

- 规则写得有歧义，两个程序读出两种实现
- 边界没写：跨天怎么算、并发怎么裁、掉线了怎么补
- 改了三版，每版改的是什么没记录
- 问"为什么要做这个"，答案是"竞品有"

这些抱怨都指向同一件事：**策划交付的不是"想法"，是"决定"。** 一份好案子是一组已经做完的决定：这个系统要给玩家什么感受（体验目标），用什么规则制造这种感受（机制），玩家在里面做什么选择（决策），和别的系统怎么接（接口），哪些数字由谁定（数值接口），上线后怎么知道它做对了（指标）。你抱怨的那些案子，是决定没做完就交付了。

反过来说，策划这个职业的核心能力就两条：

1. **做出正确的设计决定**：知道玩家想要什么、知道什么机制能给他们、知道这些机制放在一起会跑成什么样
2. **把决定写清楚**：让程序、美术、数值、QA、运营都能照着做，而且做出来的是同一个东西

第一条是本课阶段零和阶段一（第 02~13 章）的内容，第二条是阶段二（第 14~22 章）的内容。第 26~28 章讲的是当你要为别人的决定负责时（评审、主策、立项）怎么办。

你作为服务端开发已经具备了第二条的大半：写接口文档、定义状态机、列举异常分支，这些你每天都在做。**你缺的是第一条的词汇和判断**，以及第二条里"给非工程师看"的那部分（美术需要什么、QA 需要什么、运营需要什么）。

## 2. 岗位图谱

国内手游公司的策划岗位通常分成下面六种。名字各公司略有差异，职责边界也常常模糊，但交付物是稳定的：

| 岗位 | 交付什么 | 核心能力 | 对应本课 |
|---|---|---|---|
| **系统策划** | 系统案：一个玩法或功能系统的完整规则、流程、接口、边界 | 系统思维、规则形式化、接口意识 | 第 05~16 章，**本课主线** |
| **数值策划** | 数值案与配置表：成长曲线、经济投放回收、战斗公式、概率、定价 | 数学建模、数感、Excel/Python | [game-numeric](../game-numeric/README.md) 整门课 |
| **关卡策划** | 关卡案与关卡数据：空间、敌人配置、节奏、引导、Boss | 空间感、节奏感、教学设计 | 第 17、18 章 |
| **文案 / 剧情策划** | 世界观、剧情、角色设定、对白、文本 | 写作、叙事结构、与系统的耦合意识 | 第 12 章 |
| **活动 / 运营策划** | 活动案、版本内容排期、玩家反馈处理 | 玩家生命周期理解、经济影响意识、复盘 | 第 21、22 章 |
| **主策 / 制作人** | 设计愿景、设计支柱、优先级、砍功能的决定、立项文档 | 判断、取舍、沟通、带人 | 第 26~29 章 |

几个补充说明：

**系统策划是这张表的中心。** 数值给系统配数、关卡在系统的规则里造内容、文案给系统的实体写故事、活动用系统的能力组合出运营内容。系统策划不一定是最资深的，但他的案子是其他人工作的输入。这也是为什么本课的终点定在"主策 / 系统策划路径"：系统设计能力是通往主策的必经之路。

**"主策"和"制作人"经常是两个人，也经常是一个人。** 大致分工是：主策对"这个游戏好不好玩"负责，制作人对"这个项目能不能按时按预算上线并赚钱"负责。两者冲突的时候（永远会冲突），主策负责说清楚砍掉什么会损失什么体验，制作人负责拍板。第 27 章会专门讲这个分工。

**小团队里一个人兼多个岗位是常态。** 小游戏团队可能只有一个策划，他同时是系统、数值、关卡和运营。本课的岗位划分是为了讲清楚"有哪些不同性质的工作"，不是在说你必须只做其中一种。

**没有列进表里但你会遇到的**：战斗策划（动作游戏里专门做打击感、技能、AI 的，属于系统策划的一个高度专业化分支，本课只在第 13 章涉及一部分）、UE/交互策划（第 19 章会讲它和系统策划的分工）、技术策划（懂脚本和引擎的策划，是策划和程序之间的桥）。

## 3. 一个案子的一生

下面这条流水线是手游公司里一个系统从想法到上线的典型路径。各公司的流程名字不同，但阶段是稳定的。这张图值得你花五分钟看清楚，因为**你对策划的绝大多数抱怨，都能定位到这条线上的某一步没做好**。

```
 ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
 │ 1 需求    │ →  │ 2 概念    │ →  │ 3 系统案  │ →  │ 4 评审    │ →  │ 5 拆分    │ →  │ 6 实现    │
 │ 从哪来    │    │ 一页纸    │    │ 完整规则  │    │ 三层      │    │ 数值/关卡 │    │ 程序/美术 │
 └──────────┘    └──────────┘    └──────────┘    └──────────┘    │ /文案/UI  │    └──────────┘
                                                                └──────────┘         │
 ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐         │
 │ 12 复盘   │ ←  │ 11 上线   │ ←  │ 10 调优   │ ←  │ 9 测试    │ ←  │ 8 验收    │ ←  │ 7 配置    │
 │ 指标 vs   │    │ 灰度/全量 │    │ 数值/体验 │    │ QA + 玩法 │    │ 策划走查  │    │ 配表/埋点 │
 │ 目标      │    │           │    │ 迭代      │    │ 测试      │    │           │    │           │
 └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

逐步解释每一步策划在做什么、产出什么、常在哪里出问题：

| 步 | 策划做什么 | 产出物 | 常见的翻车 | 本课哪章 |
|---|---|---|---|---|
| 1 需求 | 确认"为什么要做"：来自数据（次留低）、来自玩家反馈、来自版本规划、来自老板 | 一句话的问题定义 | 需求来源是"竞品有"，没有自己的问题定义 | 26、28 |
| 2 概念 | 写一页纸：体验目标、核心规则、一张图、一个典型体验故事、风险 | 一页纸概念（`templates/one-pager.md`） | 跳过这一步直接写系统案，写到一半发现方向不对 | 14、16 |
| 3 系统案 | 把概念展开成完整规则：参与者、状态、动作、边界、接口、数值接口、埋点 | 系统案（`templates/system-spec.md`） | 只写了"玩家视角的流程"，没写规则的形式定义 | 15、16 |
| 4 评审 | 主策 / 相关策划 / 主程 / 主美评审；先目标再系统再规格 | 评审意见与修改项 | 评审直接跳到细节吵起来，目标没对齐 | 26 |
| 5 拆分 | 把系统案里的数值接口交给数值、表现需求交给美术、文本交给文案、界面交给 UI | 各专业的子案子 | 接口没写清楚，数值配出来的曲线和系统的体验目标对不上 | 15、16 |
| 6 实现 | 程序开发期间策划答疑、补边界、记录变更 | 变更记录 | 边界在实现时才发现没定义，程序自己拍板 | 16 |
| 7 配置 | 配表、埋点确认 | 配置表 | 埋点没配，上线后没数据复盘 | 16、20 |
| 8 验收 | 策划自己走一遍，确认实现 = 案子 | 验收记录 | 策划没走查，QA 按案子测，但案子本身有歧义 | 16 |
| 9 测试 | QA 测功能；玩法测试测"体验目标达成了吗" | 测试报告 | 只做了功能测试没做玩法测试，上线才知道不好玩 | 20 |
| 10 调优 | 根据测试改规则和数值 | 新版本案子 | 改规则不改文档，文档和实现分叉 | 14、20 |
| 11 上线 | 灰度、观察、全量 | 上线数据 | 无灰度直接全量，经济事故收不回来 | 22 |
| 12 复盘 | 指标 vs 第 3 步写下的"成功标准" | 复盘报告 | 第 3 步根本没写成功标准，复盘变成讲故事 | 20、22 |

**这条流水线上，程序在第 6 步才进场，但程序的抱怨多数来自第 3 步。** 这也是为什么本课把第 15、16 章（系统案怎么写）当成重点：写好第 3 步，后面九步的大部分问题都会消失。

## 4. 策划与各职能的接口

系统策划的案子有五种读者，每种读者要的东西不一样。你只当过其中一种读者，下面这张表让你看到另外四种：

| 读者 | 他要从案子里得到什么 | 他最怕案子里缺什么 | 你的案子该给他什么 |
|---|---|---|---|
| **程序**（你熟悉的） | 形式化的规则、状态定义、边界与异常、接口、数据结构暗示 | 歧义、没定义的边界、上线后才改的规则 | 系统案第 3、4 节：可以直接翻译成代码的规则 |
| **数值** | 需要哪些参数、每条曲线的体验要求（"第 3 天解锁""一周攒够一次"） | 系统策划自己拍了数字但没说要什么体验；或者只说"你看着配" | 系统案第 5 节：参数清单 + 体验要求，不写具体数字 |
| **美术 / UI** | 玩家视角的流程、界面层级、需要的资源清单、哪些动作要强反馈 | 案子只有规则没有玩家看到什么；资源量在实现时才发现翻倍 | 系统案第 2、6 节：流程图、界面草图、资源清单 |
| **QA** | 明确的预期行为（包括异常）、测试点、验收标准 | 规则里的"应该""一般来说"这类词 | 系统案第 3.6 节：边界与异常逐条列出 |
| **运营 / 数据** | 这个系统上线后看什么指标、埋了哪些点、活动怎么用它 | 没有成功标准；没有埋点；系统能力不知道怎么组合成活动 | 系统案第 1、7 节：成功标准与埋点表 |

`templates/system-spec.md` 的章节划分就是按这五种读者组织的。第 16 章会详细讲每一节怎么写，但你现在就可以看出来：**一份案子不是一篇文章，是五份面向不同读者的说明书拼在一起。** 这和你写一个服务的设计文档给上下游、SRE、测试各看一部分是一回事。

## 5. 一天的时间都花在哪

"策划整天在干什么"这个问题，工程师最常见的误解是"想点子"。一个系统策划的典型一周大致是这样（【行业口径】，不同公司和项目阶段差异很大）：

| 工作 | 时间占比 | 说明 |
|---|---|---|
| 写和改文档 | 30~40% | 系统案、变更记录、评审后的修改、给各职能的拆分 |
| 沟通 | 25~35% | 答程序的疑问、和数值对接口、和美术过资源、评审会、和运营对活动 |
| 走查与测试 | 10~15% | 验收实现、玩法测试、看测试报告 |
| 玩游戏与拆解 | 10% | 竞品、新品、自己的游戏 |
| 想点子 | < 10% | 真的 |

**沟通占三分之一。** 这是策划和程序工作性质最大的不同：程序的产出是代码，可以独立完成；策划的产出是"大家做出同一个东西"，本质上是协调。这也解释了为什么第 16 章（文档与沟通）和第 26 章（评审）在本课里占的分量：策划的文档能力就是策划的沟通能力。

**"想点子"占比最低，不是因为不重要，是因为它便宜。** 一个成熟的策划团队从不缺点子，缺的是判断哪个点子值得做、以及把它做完的能力。

## 6. 好策划和普通策划的差别

这一节是【行业口径】，来自从业者的普遍说法，但和本课的结构高度一致。好策划和普通策划的差别不在天赋，在下面几条可训练的习惯：

| 维度 | 普通策划 | 好策划 | 本课怎么训练 |
|---|---|---|---|
| 出发点 | 从机制出发："加一个 XX 系统" | 从体验出发："玩家在第 7 天应该感受到 XX，所以……" | 第 02~04 章 |
| 对规则的态度 | 规则写到"玩家能看懂"为止 | 规则写到"两个程序实现出同一个东西"为止 | 第 15、16 章 |
| 对系统的视野 | 只看自己的系统 | 先画耦合矩阵，知道改一条规则影响谁 | 第 06、15 章 |
| 对数字的态度 | 自己拍数字，或者全推给数值 | 说清楚要什么体验，让数值配；能看懂数值的模型 | 第 08 章 + game-numeric |
| 对反馈的态度 | "玩家不懂设计" | 玩家的行为永远是对的，错的是设计 | 第 20 章 |
| 对竞品的态度 | 抄机制 | 拆解到意图层，抄的是"为什么"不是"是什么" | 第 00 章 |
| 对自己想法的态度 | 捍卫 | 用最便宜的原型尽快证伪 | 第 14 章 |
| 对砍功能的态度 | 痛苦、拖延 | 用设计支柱判断，该砍就砍 | 第 27 章 |

其中最重要的是第一条和倒数第三条。**从体验出发**是整门课的第一性原理；**玩家的行为永远是对的**是玩法测试的第一纪律。工程师转过来的策划在第二、三条上通常有优势，在第一条和倒数第三条上需要刻意练习：你习惯了"逻辑自洽就是对的"，但体验不讲逻辑。

## 7. 策划的成长路径

一条典型的路径（【行业口径】）：

```
 执行策划 ──→ 系统策划 ──→ 资深系统策划 ──→ 主策 ──→ 制作人
 (配表、写活动案)  (独立负责系统)  (负责一条设计线、带人)  (设计愿景)  (项目负责)
      1~2 年          2~4 年            3~5 年              视机会
```

每一级的核心能力跃迁：

- **执行 → 系统**：从"照着做"到"独立设计"。分水岭是能不能写出一份不需要主策改的系统案
- **系统 → 资深**：从"设计一个系统"到"设计一组系统并让它们协同"。分水岭是能不能画出耦合矩阵并预判改动的连锁反应
- **资深 → 主策**：从"做设计"到"定方向和砍功能"。分水岭是能不能写出设计支柱并据此否决自己喜欢的功能
- **主策 → 制作人**：从"对好玩负责"到"对项目负责"。这一步本课不覆盖

本课的章节顺序大致沿着这条路径：阶段一和二对应执行 → 系统，阶段三和第 26 章对应系统 → 资深，第 27、28 章对应资深 → 主策。

**你的起点在哪**：你有工程背景，规则形式化和接口意识已经有了。你缺的是设计词汇（阶段一）和体验判断（第 20 章之后的所有实战）。合理的预期是：学完本课你能达到"系统策划"的文档水平，但"体验判断"需要真实项目的反馈才能建立，课程只能给方法。

## 8. 动手

### 8.1 读一份自己公司的案子

找一份你参与实现过的系统案（越是当时让你抱怨的越好）。用第 4 节的五种读者表逐节检查：

1. 它给程序的部分（规则、边界、异常）完整吗？你当时是不是自己补了边界？
2. 它给数值的部分是"体验要求"还是"直接拍的数字"？
3. 它有"成功标准"和"埋点"吗？上线后有人复盘过吗？
4. 它写了"删掉这个系统会怎样"吗？（几乎没有案子写这个，但从第 15 章起你的案子必须写）

把答案写进 `notes/作业/01-读案子.md`。这份笔记会在第 16 章用到。

### 8.2 思考题

1. 第 3 节的十二步里，你所在的团队通常在哪一步出问题？这个问题是"策划没做"还是"流程里没有这一步"？
2. 第 6 节的表里，你觉得自己作为工程师在哪几条上已经有优势、哪几条最需要补？（诚实地写下来，第 29 章回来看。）
3. "策划的核心产出是决定，不是想法"。用这句话重新解释一次：为什么"竞品有所以我们也要有"是一个坏的需求来源？

## 9. 常见误区

| 误区 | 为什么错 | 正确的想法 |
|---|---|---|
| "策划就是想点子的" | 点子是最廉价的输入，策划的工作是选择和形式化 | 策划交付的是决定和文档 |
| "策划不需要懂技术" | 不懂实现成本的策划做不出可行的取舍 | 不必会写代码，但必须知道什么贵什么便宜 |
| "系统案写得越详细越好" | 详细不等于清楚；把规则写成小说反而制造歧义 | 按读者分节，每节回答那个读者的问题 |
| "数值是数值策划的事" | 系统策划不说清楚体验要求，数值配出来的一定不对 | 系统策划负责"要什么体验"，数值负责"什么数字能给" |
| "评审就是挑毛病" | 没对齐目标的挑毛病是噪音 | 先问目标，再问系统，最后问规格（第 26 章） |
| "上线了就结束了" | 手游的设计工作一半在上线之后 | 第 12 步复盘是下一个案子的第 1 步 |
