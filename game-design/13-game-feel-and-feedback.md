# 13 - 游戏感、反馈与 juice

> **本章目标**：学完你应该能做三件事：说清楚"手感不好"到底坏在哪一层并给出可执行的修改项；把一个动作的反馈链拆到帧级别；以及给美术、音效、程序写出一份他们能直接照做的反馈需求（对应 `templates/system-spec.md` 第 6 节）。
> **前置**：[第 05 章](./05-decisions.md)（决策需要信息，反馈是信息的来源）、[第 09 章](./09-challenge-difficulty-skill.md)（技能与执行）。
> **边界**：界面的信息架构、导航深度、认知负荷、红点体系属于 UX，在 [第 19 章](./19-ux.md)。本章讲的是**"发生了什么，玩家有没有感觉到"**，第 19 章讲的是"玩家能不能找到东西、看不看得懂"。本章也**不做动作游戏专题**（战斗策划是一个专业分支），只把 3C 和打击感讲成你能在评审里使用的词汇。

## 1. 开场：同一份规则，两种手感

做一个思想实验。两款游戏的规则完全一样：点击屏幕，角色向前挥一次剑，命中敌人扣 100 点血，敌人血量 300，三下打死。数值一模一样，判定范围一模一样，服务端逻辑完全一致。

**A 版本**：点击 → 角色播放挥剑动画 → 敌人血条从 300 变成 200。没了。

**B 版本**：点击 → 角色身体先向后压 0.1 秒（前摇）→ 剑挥出，剑刃带一道白色拖尾 → 命中的瞬间，画面**停止 0.05 秒**（顿帧）→ 敌人闪白一帧、被推开一小段、播放受击动画 → 屏幕轻微震动 → 一个 `100` 的数字从命中点弹出并向上飘散 → 命中音效（金属 + 低频撞击两层）→ 敌人血条**先掉一截白色残影，再掉红色**。

**这两个版本，玩家会说 A "手感很飘"、B "打得很爽"。而你作为服务端开发，会说这两个版本的逻辑是同一个。你说的对，玩家说的也对。**

这就是本章要讲的东西：**游戏的规则和玩家对规则的感受之间，隔着一整层设计**。这一层有名字，叫游戏感（game feel），它的通俗说法叫"手感"、"打击感"、"juice"。它不属于数值，不属于逻辑，不属于美术资源本身，**它属于策划**——因为只有策划知道"这一刻玩家应该感觉到什么"。

而且这一层不是可有可无的装饰。**在核心循环里被重复几千次的那个动作，它的手感直接决定玩家愿不愿意重复第三千零一次。** 一款游戏可以有很好的系统、很平衡的数值，然后死在"点起来不舒服"上。

## 2. Swink 的三要素：游戏感由什么构成

Steve Swink 在《Game Feel》里给了游戏感一个可操作的定义【实证】，它由三部分构成：

| 要素 | 英文 | 含义 | 一个具体问题 |
|---|---|---|---|
| **实时控制** | real-time control | 玩家的输入被持续、即时地转化为游戏内的变化 | 我按下去到东西动，隔了多久？中途能不能改变主意？ |
| **模拟空间** | simulated space | 存在一个有物理关系的空间，物体在其中有位置、速度、碰撞 | 我的角色和世界的接触是"有实体的"吗？ |
| **润色** | polish | 一切强化前两者感知的表现层修饰：动画、特效、音效、震动 | 我做的事，被多少种感官同时确认了？ |

**先说清楚 Swink 原书是怎么摆这三者的关系的**：它们是**交叠的三个部分**，不是三个等级——游戏感是"在一个模拟空间里对虚拟物体的实时控制，并由润色强化其感知"，三者互相加强，缺一块整体就不成立。这里还有一个容易被忽略的边界：**按 Swink 的狭义定义，没有实时控制的游戏（回合制卡牌、挂机、大部分 SLG 界面）严格说不在 game feel 的讨论范围内。** 它们当然有"点起来舒不舒服"，但那是本课放宽后的**交互反馈感**，不是 Swink 说的那个东西。写文档时要知道自己在用哪一层意思，否则你会和读过原书的人吵一场没必要的架。

**【本课模型】** 在**诊断**"手感不好"的时候，我把这三者排成一个排查顺序：

```
   实时控制   ── 决定"我能不能操作"（延迟、响应、可打断）
       │
       ▼
   模拟空间   ── 决定"我在操作什么"（重量、惯性、碰撞、边界）
       │
       ▼
     润色     ── 决定"我的操作有多大声"（特效、音效、震动、镜头）

   润色只能放大前两层已有的东西，不能凭空创造它们。
```

**这个顺序是本课的排查顺序，不是 Swink 的分层**，它成立的理由只有最后那一行：润色是放大器。**但它是本章最重要的诊断工具。** 大量"手感不好"的项目，团队的第一反应是加特效、加震动、加音效（润色），但问题实际出在第一层（输入延迟、动作不可打断）或第二层（角色像在冰面上滑）。**在一个明显迟钝的动作上加屏幕震动，只会让它变成"迟钝并且很吵"。**

### 2.1 三要素在不同品类里的权重

| 品类 | 实时控制 | 模拟空间 | 润色 | 说明 |
|---|---|---|---|---|
| 动作 / 格斗 | 极高 | 高 | 高 | 三者都要，且实时控制是命门 |
| MOBA（王者荣耀） | 高 | 中 | **极高** | 有网络延迟，靠客户端预测、输入缓冲等**实时控制层**的手段去补偿，再用润色强化（见 5.3 节：这是两件事） |
| 卡牌 / 回合制 | 低（几乎无实时输入） | 低 | **极高** | **按 Swink 的狭义定义已经不算 game feel 了**；它的"手感"几乎全部落在润色上 |
| SLG | 极低 | 低 | 中 | 主要动作是点击界面，游戏感体现在界面反馈上 |
| 放置 / 挂机 | 极低 | 无 | 高 | 数值跳动本身就是主要的"手感" |

**这张表解释了一个常见困惑：为什么卡牌手游要在一次战斗上砸那么多特效？**【推导】因为它的实时控制和模拟空间都接近于零，**它能调的几乎只剩润色这一层**。买断制动作游戏可以靠操作本身提供满足感，卡牌游戏不行——它的爽感要么来自表现层，要么来自决策本身（构筑、出牌），而后者属于第 05 章的范围，不是本章说的"手感"。

## 3. 反馈的三层：功能、情绪、信息

Swink 的三要素回答的是"游戏感由什么构成"。但在实际写案子的时候，你需要一个更细的工具来判断"这个动作还缺什么反馈"。本课用下面这个三层模型：

| 层 | 它回答的问题 | 玩家没有它会怎样 | 典型手段 |
|---|---|---|---|
| **功能反馈** | **发生了什么？** 我的操作被系统接收了吗、结果是什么 | 玩家会重复点击、以为卡了、不确定自己做了什么 | 按钮按下态、动作播放、状态变更、数值变化、提示文字 |
| **情绪反馈** | **爽不爽？** 这件事有多重要、多厉害 | 玩家知道发生了什么，但没有感觉，重复动作变成劳动 | 特效强度、音效、震动、顿帧、镜头、演出 |
| **信息反馈** | **接下来我该怎么办？** 这个结果对我的下一个决定意味着什么 | 玩家看不懂局势，无法改进，把结果归因给运气 | 伤害数字、状态图标、进度条、战报、命中/未命中的区分 |

这三层的关系是：**功能反馈是底线，情绪反馈决定重复意愿，信息反馈决定玩家能不能变强。**

**三层缺一层的典型症状：**

| 缺什么 | 症状 | 常见于 |
|---|---|---|
| 缺功能反馈 | "我到底点没点上？"玩家反复点击、投诉卡顿 | 网络延迟大的操作、异步请求没有本地预表现 |
| 缺情绪反馈 | "能玩，但没意思。"操作准确但乏味 | 逻辑做完了但表现没排期的版本 |
| 缺信息反馈 | "我不知道我为什么输。"玩家归因给运气或不公平 | 自动战斗、挂机战斗、复杂 buff 系统 |

**【行业口径】"缺信息反馈"是手游里很普遍也很被低估的问题。** 一场自动战斗打完只显示"失败"，玩家能想到的改进方向就只剩"练度不够"，因为系统没给他别的线索。**【推导】信息反馈缺失会把一个本来有策略空间的系统，在玩家的感知里退化成一个纯数值系统**，这不是数值的锅，是反馈设计的锅。

反过来说，Doug Church 在《Formal Abstract Design Tools》里把"**可感知的后果（perceivable consequence）**"列为核心设计工具之一【实证】，说的就是这件事：**玩家必须能感知到自己行动的后果，否则他就无法形成意图，也就无法进行有意义的游戏。**

## 4. Juice 清单

"juice"这个说法被两场演讲广泛普及：Martin Jonasson 与 Petri Purho 的 *Juice It or Lose It*（2012）【实证】，以及 Jan Willem Nijman（Vlambeer）的 *The Art of Screenshake*（2013）【实证】。（它们是普及者，不是这个词的出处——独立游戏社区在此之前就在用它。）这两个演讲的做法是一样的：拿一个极简的游戏原型，一条一条地加表现层效果，让观众实时看到"同一套逻辑"如何变得越来越爽。

**这两个演讲值得你花一小时看完，它们是本章唯一无法用文字替代的部分。** 下面把它们涉及的手段整理成一张可以直接拿去写需求的清单。

### 4.1 通用 juice 手段清单

| 类别 | 手段 | 作用 | 用在哪 |
|---|---|---|---|
| **时间** | 顿帧 / hitstop（命中瞬间冻结几帧） | 强调冲击、给玩家确认命中的时间窗 | 打击、暴击、格挡 |
| | 慢动作 | 强调重要时刻 | 终结技、最后一击 |
| | 缓动 / easing（不做匀速运动） | 让一切运动有加速度，显得有重量 | UI 弹出、数值滚动、镜头 |
| **空间** | 屏幕震动 / screenshake | 传达力量 | 爆炸、重击、受击 |
| | 击退 / 位移 | 让打击有物理后果 | 命中 |
| | 挤压与拉伸（squash & stretch） | 让物体显得有弹性和质量 | 跳跃、落地、UI 元素 |
| | 镜头推近 / 拉远 / 抖动 | 引导注意力、放大情绪 | 大招、Boss 出场 |
| **视觉** | 命中闪白 | 明确命中判定 | 命中的第一帧 |
| | 粒子 / 特效 | 强化事件的存在感 | 几乎所有动作 |
| | 拖尾（trail） | 让快速运动可被追踪 | 挥砍、投射物 |
| | 残留物 / permanence（尸体、弹坑、血迹） | 让玩家看到自己造成的累积影响 | 战场 |
| **听觉** | 分层音效（高频"打击"+ 低频"冲击"） | 单层音效永远不够有力 | 命中 |
| | 音高随机化 | 避免重复听觉疲劳 | 高频重复的动作 |
| | 音效抢占与优先级 | 避免混战时音效糊成一团 | 群战 |
| **数值** | 跳字（伤害数字） | 信息 + 情绪双重作用 | 命中 |
| | 连击计数 | 累积感、节奏感 | 连续动作 |
| | 数值滚动（不直接跳到目标值） | 让"变多了"这个过程被看见 | 结算、经验条、战力 |
| **触觉** | 震动（手柄 / 手机马达） | 直接的物理确认 | 命中、UI 关键操作 |

### 4.2 关于 juice 的三条纪律

**纪律一：juice 是放大器，不是发生器。**

再说一遍第 2 节的顺序。屏幕震动会放大"我打中了"这个感觉，但如果玩家根本不确定自己有没有打中（功能反馈缺失），震动只会增加混乱。**先保证功能反馈存在且准确，再谈情绪反馈。**

**纪律二：过量 juice 是真实存在的问题，而且它的症状是"看不清"。**

juice 加过头的典型症状：

| 症状 | 原因 | 后果 |
|---|---|---|
| 屏幕上全是特效，看不到角色和敌人 | 特效层级和体量失控 | **玩家无法做决策**（第 05 章的"信息"要素被破坏） |
| 一直在震 | 每个动作都加了震动 | 震动失去了强调作用，且引起生理不适 |
| 音效糊成噪音 | 没有优先级与抢占规则 | 关键提示（技能就绪、受击）听不见 |
| 每次点击都有 0.3 秒的演出 | 把"重要时刻"的规格用在了高频动作上 | 高频操作变得拖沓，长期玩会烦 |

**过量 juice 的本质是"强调了一切等于没有强调"。** 反馈的强度必须和事件的重要性成正比，这是一条可以直接写进需求的原则：

```
   事件重要性 ──────────────────────────────────► 反馈强度

   普通攻击命中     ── 小特效 + 短音效 + 跳字
   暴击            ── 上述 + 顿帧 + 轻震动 + 不同颜色跳字
   击杀            ── 上述 + 死亡演出 + 击杀音效
   大招命中        ── 上述 + 镜头 + 强震动 + 慢动作
   Boss 击杀       ── 上述 + 全屏演出 + 停顿 + 音乐变化

   规则：高频事件用低规格反馈；低频事件才用高规格反馈。
   反过来做，高频事件会让人烦，低频事件会显得不够隆重。
```

**纪律三：可跳过与可关闭。**

任何超过 1 秒的演出，在一款玩家会重复上千次的手游里，都必须可以跳过或在设置里关闭（战斗特效强度、屏幕震动、自动战斗）。**"第一次看很爽"和"第五百次看很烦"是同一段演出的两个阶段**，设计时必须同时考虑这两个阶段。

## 5. 打击感的构成

"打击感"是国内战斗策划最常用的行话，它其实是上面这些工具在一个具体场景（近战命中）上的组合。把它拆开，是为了让你在评审时能说出具体位置，而不是"我觉得打起来不够爽"。

### 5.1 一次攻击的时间轴

```
  输入      前摇          命中帧      顿帧      后摇           可再次输入
   │─────────│─────────────│──────────│────────│──────────────│
   │         │             │          │        │              │
   │  响应   │  蓄力的可读性 │  判定发生 │ 冲击感  │  收招/硬直    │  连招窗口
   │  延迟   │  （对手能看懂）│          │        │              │

  ← 攻击方的体验：这一段的长度和可打断性决定"这把武器重不重"
```

| 阶段 | 设计参数 | 影响的体验 |
|---|---|---|
| **输入响应** | 从按下到动作开始播放的延迟 | 超过一定阈值就"迟钝"。这是实时控制层，**特效救不了** |
| **前摇** | 时长、动作幅度、是否可取消 | 长前摇 = 重武器 = 高风险高回报；也是给对手的信息（PvP 里前摇就是可读性） |
| **命中帧** | 判定框的位置、大小、持续时间 | 判定和视觉是否一致（**看起来打中了但判定没中，是最挫败的体验**） |
| **顿帧** | 冻结的帧数（攻方/受方可以不同） | 冲击力的主要来源；顿帧越长越"重"，但过长会打断流畅感 |
| **后摇** | 时长、可否被其他动作取消 | 决定连招节奏；能被取消 = 爽快，不能取消 = 有代价的攻击 |

**顿帧值得单独讲。** 它是打击感里最"廉价"也最有效的手段：在命中的那一瞬间把双方（或整个画面）冻结几帧。它的作用有三个：

1. **给玩家一个确认命中的时间窗**（功能反馈）
2. **模拟"打到实体"的物理阻力**（模拟空间）
3. **在动作衔接处制造节奏感**（情绪反馈）

【行业口径】常见做法是让轻攻击的顿帧短、重攻击长，并且把顿帧的长度作为一个可调参数交给战斗策划反复调，因为它对手感的影响非常大且非常主观。

### 5.2 受击方的反馈同样重要

新手最容易只设计攻击方。**但"打得爽"有一半来自受击方的表现**：

| 受击反馈 | 作用 |
|---|---|
| 受击动画 / 硬直 | 确认攻击生效；硬直时长决定能不能连击 |
| 闪白 / 变色 | 最便宜的命中确认，一帧就够 |
| 击退 / 浮空 / 倒地 | 让攻击有空间后果 |
| 血条变化（残影 / 分段） | 信息反馈；**残影（先掉白再掉红）让玩家看清扣了多少** |
| 受击音效 + 语音 | 区分"打中了"和"被格挡了" |
| 死亡表现 | 结束的仪式感 |

**一条实用检查：把攻击方的所有表现关掉，只看受击方，你还能不能判断出"发生了一次成功的攻击"？** 如果不能，说明受击反馈不足。

### 5.3 买断制对照：《黑神话：悟空》的重击

【推导】以《黑神话：悟空》这类单机动作游戏为对照，它的打击感构成和手游 PvP 有一个结构性差异：**它的判定和表现都在本地即时计算，因此前摇、命中帧、顿帧可以做得非常精确**（帧级别），并且可以用较长的前摇来换取"重"的体验。而手游 PvP 隔着网络，同样的动作在两端看到的时刻未必一致，"我明明躲了却还是被打到"就是从这里来的。

**但由此推出"手游 PvP 不太需要可读性"是反的。** 恰恰相反：**PvP 越依赖玩家的反应，命中之前的信息就越重要**——躲不掉的控制技能是竞技体验最直接的破坏者。正确的结论是：手游 PvP 要在更差的条件下把**三件不同层的事**同时做好，而它们经常被混为一谈：

| 要解决的事 | 属于哪一层 | 手段 |
|---|---|---|
| **延迟本身** | **实时控制**（不是润色） | 本地预表现（按下即播，服务端结果回来再校正）、输入缓冲、技能指示器本地即时响应、服务端的延迟补偿与回滚策略 |
| **命中之前的可读性** | 模拟空间 + 信息反馈 | 前摇动作要大而清晰、技能范围指示器、地面预警圈、投射物有可见的飞行时间。**这一块不能省，省了就是"被秒了都不知道怎么死的"** |
| **命中之后的确认** | 润色 | 顿帧、特效、震动、跳字 |

**【行业口径】手游技能特效普遍比单机夸张，常见的解释是"要在更小的屏幕、更短的时间窗里把'这一下很重'传达出去"。** 但它替代不了前两项：**预表现解决的是延迟，前摇和预警解决的是可读性，特效只负责确认。把第一件事叫成"润色"，是这一节最容易犯的错。**

## 6. 界面层的反馈：手游最主要的战场

对绝大多数手游来说，玩家的绝大部分操作发生在界面上而不是战斗里【行业口径】（自己算一遍：一次日常清完，点击次数里有多少落在战斗内？）。**界面反馈才是手游游戏感的主战场**，而它经常被当成"UI 的事"而不是策划的事。

### 6.1 界面反馈清单

| 元素 | 功能反馈 | 情绪反馈 | 信息反馈 |
|---|---|---|---|
| **按钮** | 按下态（视觉变化）+ 点击音 | 弹性缩放动画 | 不可用时的置灰 + 原因提示 |
| **进度条** | 数值变化 | 滚动动画（不直接跳）、满时的高光 | 距离下一档还差多少 |
| **红点** | 有新内容 | 无（红点不应该有情绪） | **红点的可消除性**（第 19 章详谈） |
| **资源变化** | 数字变化 | 飘字、图标飞入、数值滚动 | 变化量和来源 |
| **弹窗** | 出现 | 弹出缓动 | 层级（这是提示还是需要决策） |
| **加载 / 等待** | 有东西在转 | 进度可见 | 剩余时间 / 当前阶段 |

**"资源飞入"这个手段值得特别提**：领取奖励时，让金币图标从奖励框飞到界面顶部的金币数字上，然后数字滚动增加。这套动作的真实作用是**把一个瞬时的状态变更（数据库里 +1000）变成一个可被感知的过程**。它同时提供了功能反馈（我领到了）、情绪反馈（有东西飞过来）和信息反馈（飞到哪里去了，即这个资源存在哪）。

**一个反例**：领取奖励后只有一个"领取成功"的 toast，金币数字直接跳变。玩家经常不知道自己领到了什么、存在哪里。【推导】在新手期这类"我不知道自己拿到了什么"的时刻会累积成困惑，是新手引导走查（第 18 章）时该被抓出来的问题。

### 6.2 手游特有的三种反馈演出

**（1）数值跳字与战力提升**

手游的核心快感之一是"数字变大"。它的反馈设计有几个要点：

- **变化过程要可见**：战力从 12000 变成 13500，不能直接跳，要滚动，并且显示 `+1500`。
- **绿色向上箭头是行业通用语言**：玩家在半秒内就能读懂。
- **跨档位要有额外强调**：突破整数关口、突破段位、突破品质时，用更高规格的表现（这是第 4.2 节"强度与重要性成正比"的应用）。
- **要有对比对象**：`战力 13500（服务器同等级平均 11200）` 比孤零零的 13500 有意义得多。这是信息反馈。

**（2）抽卡演出**

【行业口径】抽卡演出常被认为是手游里**投入产出比很高的一类表现设计**，它是一个几乎纯粹为情绪反馈存在的系统。拆开看，它的结构是：

```
   投入（确认花费）
      │
      ▼
   ┌─────────────────────────────────────────┐
   │ 悬念段：一段固定长度的演出，此时结果已定    │  ← 结果在服务端早已确定，
   │  （光柱、动画、抽取过程）                  │    演出只是在"揭晓"
   └─────────────────────────────────────────┘
      │
      ▼
   ┌─────────────────────────────────────────┐
   │ 预告段：用颜色/特效等级暗示稀有度           │  ← 关键设计：
   │  （紫光 → 可能出金，金光 → 必出金）        │    在揭晓前先给一个概率信号
   └─────────────────────────────────────────┘
      │
      ▼
   揭晓段：角色出现 + 全屏特效 + 音乐 + 语音
      │
      ▼
   收束段：结果列表 + 再抽一次的按钮
```

【推导】**"预告段"是这套演出的核心设计**，它的作用是把一个瞬时的二值结果（出金 / 不出金）拉长成一段有起伏的情绪曲线：先给一个"可能有"的信号，制造几秒钟的期待，然后揭晓。**没有预告段的抽卡演出，情绪只有一个尖峰；有预告段的，情绪是一条上升曲线加一个尖峰。** 这也解释了为什么"紫光变金光"这种设计会被玩家反复讨论：它人为制造了一个反转时刻。

**必须说清楚的边界**：抽卡的概率数学、保底机制、期望值计算全部在 [game-numeric 第 13 章](../game-numeric/13-probability-systems.md)，本章只讲**同样的概率下，演出如何改变体验**。同时要注意伦理边界：**预告段不能给出与实际概率不符的暗示**（比如让紫光频繁出现但几乎不转金），那属于[第 21 章](./21-monetization-design.md)要讲的黑暗模式。

**（3）自动战斗的反馈困境**

自动战斗把玩家的实时控制降为零，于是：

- 功能反馈：无所谓（玩家没在操作）
- 情绪反馈：只剩下看特效，且看多了会烦 → 所以有"跳过战斗"和"倍速"
- **信息反馈：变得极其重要且极其缺乏**

**自动战斗最大的设计问题是玩家无法归因。** 打不过的时候，他不知道是阵容不对、站位不对、还是就是数值不够。解法是**战后的信息反馈**：伤害构成、每个角色的输出占比、关键时刻标记（"第 25 秒你的治疗死了"）、失败原因归类提示。

**做好战报，通常比给自动战斗加特效更值得投入。**【推导】因为前者让玩家有下一步可做（第 05 章：决策需要信息），后者只是让他多看几秒。

## 7. "感觉不好"的诊断表

这是本章最该被贴在工位上的一张表。当有人（包括你自己）说"这个操作感觉不对/不爽/怪怪的"时，按下面的顺序诊断：

| # | 症状 | 可能的原因 | 诊断方法 | 修改方向 | 属于哪一层（本课模型） |
|---|---|---|---|---|---|
| 1 | **迟钝**："我点了它才动" | 输入到响应之间有延迟（网络、动画启动、状态机切换、等待服务端确认） | 录屏逐帧数，从按下到第一帧变化有多少帧 | **本地预表现**（先播动画，服务端结果回来再校正）；缩短动作启动帧 | 实时控制 |
| 2 | **粘滞**："操作完了还要等" | 后摇过长且不可打断 | 测量动作结束到能进行下一次输入的时间 | 增加可取消窗口；缩短后摇 | 实时控制 |
| 3 | **飘**："打上去像打在空气上" | 缺顿帧、缺击退、缺受击反馈 | 关掉攻击方特效，只看受击方 | 加顿帧、闪白、位移 | 模拟空间 + 润色 |
| 4 | **无反馈**："我不知道点上没有" | 缺功能反馈（按钮无按下态、无音效、无状态变化） | 静音玩一遍，看能不能确认每次操作 | 补按下态、音效、状态变化 | 润色（但属于功能层） |
| 5 | **反馈错位**：反馈来了但对不上 | 音画不同步；特效播放点与判定点不一致；数字弹出位置离命中点太远 | 逐帧对齐音效、特效、判定三者的时间点 | 对齐时间轴；把跳字放在命中点 | 润色 |
| 6 | **反馈过量**："眼花，看不清" | 特效体量失控、震动泛滥、音效无优先级 | 找一个不熟悉这个游戏的人看一场战斗，问他"刚才谁赢了、为什么" | 建立反馈强度分级；给特效和音效定优先级与抢占规则 | 润色 |
| 7 | **不可归因**："我不知道为什么输" | 缺信息反馈 | 打完一局，让测试者说出三条改进方向，说不出就是缺 | 战报、伤害构成、关键时刻标记 | 信息层（三要素之外） |
| 8 | **重复疲劳**："第一次爽，第一百次烦" | 高频动作用了高规格演出 | 统计这个动作一天被触发多少次 | 降规格；加跳过/倍速/关闭选项 | 润色 |
| 9 | **判定与视觉不符** | 判定框与模型/特效不匹配 | 打开判定框显示，对比视觉 | 对齐判定与表现，**通常是让判定迁就视觉** | 模拟空间 |

**使用方法：从 1 号往下查，不要跳。** 因为 1、2 属于实时控制层，3、9 属于模拟空间层，只有 4~8 才是润色层。**在实时控制有问题的时候去调特效，是这一章最常见的浪费。**

## 8. 3C：你需要掌握的词汇

3C 是 **Character（角色）、Camera（相机）、Control（控制）** 的缩写，是动作/3D 游戏里描述"玩家操作体验"的标准词汇。Scott Rogers 在《Level Up!》里把它作为基础概念讲解【实证】。本章不做动作游戏专题，但你必须知道这三个词的含义，因为**评审时别人会用它们，而它们各自对应完全不同的问题**：

| C | 指什么 | 包含哪些设计决定 | 出问题时的症状 |
|---|---|---|---|
| **Character** | 玩家操控的对象本身 | 移动速度、加速度、转身速度、跳跃高度与滞空、动画状态机、碰撞体 | "角色像在冰上滑"、"转身太慢"、"跳跃不跟手" |
| **Camera** | 玩家的视角 | 视角距离、跟随的延迟与阻尼、锁定目标、碰撞（墙壁遮挡）、战斗时的推近 | "打起来看不到敌人"、"镜头晃得晕"、"被墙卡视角" |
| **Control** | 输入到行为的映射 | 按键映射、输入缓冲、连招窗口、可取消规则、辅助（吸附、容错） | "手感迟钝"、"连招接不上"、"经常按了没反应" |

**三者互相影响，这是 3C 最难的地方。** 一个常见例子：把角色移速调快（Character），结果玩家开始晕（Camera 跟随参数没跟着调）；再加大相机跟随的阻尼来缓解晕眩，结果操作感觉迟钝（因为视觉反馈慢于操作，被玩家感知成 Control 的问题）。

**给你的实用结论**：当玩家抱怨"手感不好"时，**先问是 C1、C2 还是 C3 的问题**。这一个提问就能把讨论从"我觉得不爽"推进到"相机跟随阻尼太大"。这就是词汇的价值。

关于 3D 动作游戏的具体技巧，大野功二的《游戏设计的 236 个技巧》里有大量日本一线开发者总结的具体做法【实证】，如果你的项目是动作向的，值得作为工具书。

## 9. 贯穿案例（上）：《王者荣耀》一次技能命中的完整反馈链

选一个具体的技能拆到细节。这里用**钟馗的二技能「湮灭之锁」（勾锁类技能：远程发射一个钩子，命中敌人后将其拖拽到自己身边）**作为样本，因为它同时涉及施法方、被命中方和旁观者三方的反馈，是反馈链最完整的一类技能。（钟馗的一技能是近身的范围伤害与减速，不是钩子——**技能编号和技能名在评审里说错，会让整段分析失去可信度**，这一点比它听起来重要。）

> **纪律提醒**：以下是从游戏表现中可观察到的反馈要素与时序结构，**具体的帧数、时长、参数不做数字断言**（你自己去录屏逐帧核实，这正是 11.1 的作业）；**设计意图一律【推导】**。

### 9.1 施法方（我）的反馈链

| 时刻 | 反馈 | 属于哪一层 | 【推导】为什么要有 |
|---|---|---|---|
| 手指按住技能键 | 出现指示器（方向/范围提示） | 信息反馈 | 让玩家在释放前知道会打到哪，这是决策需要的信息 |
| 拖动方向 | 指示器实时跟随 | 功能反馈（实时控制） | 确认输入被接收；且允许改变主意（可取消） |
| 松手 | 技能键进入 CD、角色播放施法动作、施法音效 | 功能反馈 | **确认技能真的放出去了**，这是最关键的一条 |
| 钩子飞行 | 投射物 + 拖尾 + 飞行音效 | 情绪 + 信息 | 让玩家追踪它、并在飞行期间产生"能不能中"的悬念 |
| 命中 | 命中特效、命中音效（区别于飞行音）、被拖拽的敌人产生位移 | 功能 + 情绪 | **这是整条链的高潮**：从悬念到确认 |
| 命中后 | 敌人被拖到身边、我方角色可以接后续技能 | 信息 | 告诉玩家"你可以打后续了" |
| 未命中 | 钩子飞到最大距离后消失 + 一个较弱的消散表现 | 功能反馈 | **失败也必须有明确反馈**，否则玩家不知道是没中还是技能没放出去 |

**【推导】这条链里最值得学习的是"未命中"也有明确表现。** 大量新手设计只做成功路径的反馈，结果玩家在失败时陷入"我是没打中，还是根本没放出去，还是被系统吞了"的困惑。**失败反馈的缺失会被玩家解读为"游戏有 bug"或"网络卡"，进而变成对游戏质量的整体不信任。**

### 9.2 被命中方（对手）的反馈链

| 时刻 | 反馈 | 【推导】为什么要有 |
|---|---|---|
| 对方施法时 | 能看到对方的施法动作和技能特效（前摇的可读性） | **PvP 的公平感建立在"我有机会反应"上**，前摇就是给对手的信息 |
| 钩子飞来 | 投射物可见、有飞行时间 | 给出躲避的操作窗口 |
| 被命中 | 受击表现、控制状态图标、屏幕边缘或角色身上的控制提示 | 告诉玩家"你现在被控了，操作会失效"，避免他以为是卡顿 |
| 位移过程 | 角色被拖拽的动画 + 镜头跟随 | 让玩家理解"我被拉走了"，而不是"我瞬移了" |
| 控制结束 | 明确的恢复提示 | 告诉玩家"你可以动了" |

**这一列是新手最容易忘的：被打的人也需要完整的反馈，而且他的反馈需求偏向"信息"而不是"情绪"。** 他需要知道：发生了什么、我现在能不能操作、什么时候能操作。**"被控制的时候不知道自己被控制了"是 PvP 里最招人恨的体验之一**，它会被直接归因为"这游戏卡"。

### 9.3 旁观者（队友）的反馈

- 小地图上的技能提示 / 击杀播报 / 团战信号
- 【推导】作用是把一个局部事件变成团队信息，服务于合作（[第 11 章](./11-social-design.md)）

### 9.4 从这条链提炼的四条通用规则

| 规则 | 内容 |
|---|---|
| **一个动作有三种观众** | 施法方、承受方、旁观方，各需要不同侧重的反馈（情绪 / 信息 / 信息） |
| **失败路径必须有反馈** | 未命中、被格挡、被免疫、超出射程，每一种都要能被区分 |
| **状态的开始和结束都要播报** | 只播报"你被控制了"不播报"控制结束了"，玩家会持续困惑 |
| **前摇是给对手的信息** | 在 PvP 里，攻击方的表现同时是防守方的决策依据。这是 PvE 和 PvP 反馈设计最大的差别 |

## 10. 贯穿案例（下）：抽卡演出作为"纯情绪反馈系统"的对照

把第 9 节的技能反馈链和一次十连抽的演出放在一起对照，能看清反馈设计的两个极端：

| 维度 | 技能命中（王者荣耀） | 抽卡演出（卡牌手游） |
|---|---|---|
| 实时控制 | 高（结果由操作决定） | **零**（结果在点确认时已经定了） |
| 玩家在演出期间的操作 | 需要持续决策 | 只能等待或跳过 |
| 功能反馈 | 关键（确认技能放出） | 简单（钱扣了、东西给了） |
| **情绪反馈** | 重要 | **几乎是全部**（这套系统的设计工作基本都在这里） |
| 信息反馈 | 关键（决定下一步） | 弱（结果列表） |
| 演出时长 | 必须极短（不能影响操作） | 可以较长，但**必须可跳过** |
| 反馈的目的 | 让玩家打得更好 | 让玩家感受到"值" |
| 重复次数 | 一局几十次 | 一个月几十次 |

**这个对照要说明的核心结论是：反馈设计没有统一标准，它由"这个动作在循环里的位置"决定。**

- 高频、需要决策的动作（技能、点击）→ **反馈要短、要准、要偏信息**
- 低频、代表重大投入的动作（抽卡、突破、开箱）→ **反馈可以长、要偏情绪、要有仪式感**

【推导】这也解释了一个现象：为什么很多手游的抽卡演出做得极其精致，而战斗反馈相对粗糙。因为对它们来说，**抽卡是核心付费动作，战斗是自动进行的过程**。反馈资源被投放在了商业上更重要的动作上。这是一个理性的分配，但它也决定了这类游戏的"手感"上限。

## 11. 怎么给美术、音效、程序写反馈需求

这一节是本章最直接落到工作上的部分。它对应 `templates/system-spec.md` 的**第 6 节：表现需求**。

### 11.1 反馈需求的坏味道

先看什么样的需求会被打回来：

| 坏需求 | 为什么坏 |
|---|---|
| "这个技能要打击感强一点" | 美术不知道该做什么；无法验收 |
| "参考某某游戏" | 参考可以有，但不能替代规格；对方会问"参考它的哪一部分" |
| "特效要炫酷" | 没有强度标准，做出来要么不够要么过量 |
| "命中的时候有反馈" | 哪一帧？什么反馈？谁能看到？ |

### 11.2 反馈需求的标准写法

一份可用的反馈需求，必须回答**五个问题**：

```
   1. 触发时机   —— 在哪一个精确的时间点（哪一帧、哪个事件）
   2. 反馈通道   —— 视觉 / 听觉 / 触觉 / 时间（顿帧）/ 镜头，各要什么
   3. 强度等级   —— 用项目统一的分级（见下），不要用形容词
   4. 受众       —— 施法方 / 承受方 / 旁观方，谁能看到/听到
   5. 例外情况   —— 未命中、被免疫、群体命中时的叠加规则、性能降级时砍哪个
```

**关于"强度等级"**：每个项目都应该建立一套**反馈强度分级表**，让所有人用同一套词。示例：

| 等级 | 用于 | 视觉 | 音效 | 顿帧 | 震动 | 镜头 |
|---|---|---|---|---|---|---|
| **L1 轻** | 高频普通操作 | 小特效，不遮挡 | 单层短音 | 无 | 无 | 无 |
| **L2 中** | 普通命中 | 中等特效 | 双层（打击+冲击） | 极短 | 无 | 无 |
| **L3 重** | 暴击 / 技能命中 | 大特效 | 三层 + 语音 | 短 | 轻 | 轻微推近 |
| **L4 极重** | 大招 / 击杀 | 全屏级 | 完整音效组 + 音乐变化 | 明显 | 强 | 明显运镜 |
| **L5 演出** | Boss 击杀 / 抽卡出金 | 独立演出 | 独立音乐 | 有停顿 | 强 | 独立镜头 |

**有了这张表，需求就可以写成"命中为 L2，暴击为 L3"，而不是"要爽一点"。** 这是本章送你的最实用的一个工具。

### 11.3 一份反馈需求的示例格式

```
【动作】近战普攻命中
【触发时机】命中判定成立的那一帧（事件：OnHit）

【视觉】
  - 攻击方：武器拖尾（持续到后摇结束）
  - 受击方：命中点小型冲击特效；模型闪白 1 帧
  - 世界：无
  - 强度：L2

【听觉】
  - 命中音（双层：高频金属 + 低频冲击），音高随机 ±5%
  - 优先级：中（可被大招音效抢占）

【时间】
  - 顿帧：极短（具体帧数由战斗策划调参，参数名 hitstop_light）

【镜头 / 震动】
  - 无

【数值表现】
  - 伤害跳字，从命中点弹出并向上飘散
  - 普通伤害白色，暴击黄色且字号放大

【受众】
  - 攻击方：全部
  - 受击方：闪白 + 受击动画 + 跳字
  - 旁观方：只有视觉，不播音效（避免群战音效爆炸）

【例外】
  - 未命中：武器拖尾照常，无命中特效，无音效，无跳字；改播"落空"轻音
  - 被格挡：换格挡特效（蓝色）+ 格挡音效，顿帧加长
  - 被免疫：显示"免疫"文字，无伤害跳字
  - 群体命中：命中特效每帧最多同时播放 N 个（性能上限，具体值与程序确认）
  - 低配机型降级顺序：先砍粒子数量 → 再砍拖尾 → 音效和顿帧最后砍
```

**注意最后一条"降级顺序"**：手游必须考虑低端机。**由策划来指定降级顺序，是因为只有策划知道哪些反馈是体验的核心、哪些是锦上添花。** 如果不写，程序会按性能开销从大到小砍，可能先把顿帧砍了，而顿帧恰恰是打击感的核心。

**这一段格式，就是 11.2 作业要写的东西。**

## 12. 常见误区

| 误区 | 为什么错 | 正确的想法 |
|---|---|---|
| "手感是美术和程序的事" | 只有策划知道"这一刻玩家应该感觉到什么"和"这个动作在循环里被重复多少次" | 反馈需求是系统案的第 6 节，是策划的产出物 |
| "手感不好就加特效" | 特效是润色层，救不了实时控制层的延迟和模拟空间的失重 | 按本课的三层排查顺序诊断：控制 → 空间 → 润色（这是诊断顺序，不是 Swink 的原始分层） |
| "网络延迟靠特效和演出去掩盖" | 本地预表现、输入缓冲、服务端校正属于实时控制层，不是润色 | 分开处理三件事：补偿延迟、做足命中前的可读性、做好命中后的确认（5.3 节） |
| "juice 越多越爽" | 强调一切等于没有强调；过量 juice 会破坏决策所需的信息 | 建立反馈强度分级，高频事件低规格 |
| "反馈就是让玩家爽" | 情绪反馈只是三层之一 | 功能反馈是底线，信息反馈决定玩家能不能变强 |
| "自动战斗不需要反馈设计" | 自动战斗最缺的是信息反馈，玩家无法归因 | 战报和伤害构成比战斗特效重要 |
| "只做成功路径的反馈" | 未命中、被格挡、被免疫没有区分，玩家会以为是 bug 或网络问题 | 失败路径的反馈必须能被区分 |
| "只考虑施法方的感受" | PvP 里被打的人也需要反馈，而且他更需要"信息"而不是"情绪" | 一个动作有三种观众 |
| "第一次看很爽就够了" | 高频动作会被重复几千次 | 任何超过 1 秒的演出都要可跳过/可关闭 |
| "写需求写'参考某游戏'就行" | 无法验收，且对方不知道参考哪一部分 | 按五要素（时机/通道/强度/受众/例外）写 |
| "低配降级让程序自己决定" | 程序按性能开销砍，可能先砍掉体验核心 | 策划指定降级顺序 |

## 13. 动手

### 13.1 拆解：《王者荣耀》一个技能的完整反馈链

**指定对象**：《王者荣耀》里任意一个**带控制效果或位移的技能**。下面按三种不同的机制各给一个例子，**它们的反馈需求完全不同，选之前先想清楚你要拆的是哪一类**（如果你不玩王者荣耀，换成你在玩的任意一款有实时战斗的手游里的一个技能，同样先归类）：

| 类型 | 例子 | 反馈的重点在哪 |
|---|---|---|
| **牵引**（把敌人拉过来） | 钟馗二技能「湮灭之锁」 | 投射物的飞行过程、命中/未命中的区分、被拖拽方的位移可读性 |
| **定身**（让敌人不能动） | 王昭君二技能「禁锢寒霜」 | 延迟生效期间的**预警**（地面范围提示）、控制开始与结束的播报 |
| **自身位移**（把自己送过去） | 张飞二技能「守护机关」 | 起跳与落地的时间感、落点提示、落地那一刻的功能反馈 |

（技能名与效果以你玩到的版本为准；**动手第一步就是自己去游戏里核对一遍**，不要信任何二手资料，包括本课。）

**方法**：**必须录屏并逐帧看**（手机自带录屏 + 任意可以逐帧播放的播放器）。这一条不能省，本章的东西不逐帧看是学不到的。

**回答下面这份清单，写进 `notes/拆解/13-反馈链-XX.md`：**

**A. 时间轴（事实，写帧数或毫秒）**

1. 从手指松开到角色开始播放施法动作，隔了多少帧？
2. 前摇有多长？前摇期间能不能取消？
3. 从技能释放到命中判定，中间有多长（投射物飞行时间）？
4. 命中的那一帧，画面有没有停顿？停了多久？
5. 后摇多长？后摇能不能被移动或其他技能取消？

**B. 反馈通道盘点（事实）**

6. 把这个技能命中时的所有反馈按通道列出来：视觉（分特效/闪白/位移/UI 提示）、听觉（分几层音）、时间（顿帧）、镜头、震动、数值跳字。**至少列出 10 项。**
7. 施法方、被命中方、旁观队友，三者各能看到/听到其中哪些？做一张三列的表。
8. **未命中**时，反馈有什么不同？把成功和失败两条路径的反馈并排对比。

**C. 三层反馈分析**

9. 把第 6 题列出的每一项，归到功能/情绪/信息三层里。哪一层的项目最多？哪一层最少？
10. 假设把所有情绪反馈全部去掉（只留功能和信息），这个技能还能用吗？玩家的操作准确率会变吗？

**D. 诊断（用第 7 节的表）**

11. 这个技能有没有第 7 节九种症状中的任何一种？如果有，指出是哪一种、你的判断依据是什么。
12. 如果没有，找一个**你觉得手感最差**的技能（同一款游戏里），用同样的方法诊断它，指出它坏在哪一层。

**E. 意图【推导】**

13. 这个技能的前摇为什么是这个长度？（提示：从"给对手的反应时间"和"技能强度"两个角度想）
14. 如果把顿帧完全去掉，玩家的体验会怎么变？如果把顿帧加长一倍呢？

### 13.2 写作作业：一份完整的反馈需求（按 system-spec 第 6 节格式）

**选题**：从下面三选一（或选一个你项目里真实的动作）：

- (a) 一次装备强化**失败**的完整反馈（这是最考验设计的：失败反馈既要让玩家知道失败了，又不能让他愤怒到退游）
- (b) 一次抽卡从点击到结果的完整反馈（含单抽和十连的差异）
- (c) 一次公会集结出兵成功 / 中途被取消的反馈

**产出**：写进 `notes/作业/13-反馈需求-XX.md`，**严格按第 11.3 节的格式**，并额外满足以下要求：

**第一部分：前置定义**

1. **这个动作在循环里的位置**：一天被触发多少次？属于高频还是低频？（这决定反馈规格）
2. **玩家在这一刻的情绪目标**：一句话。
3. **这个动作有几种结果**？把所有结果穷举出来（成功、失败、部分成功、超时、被打断、资源不足、网络异常……）。**这一条是本作业的重点**：绝大多数反馈需求写坏，都是因为只写了成功路径。

**第二部分：反馈强度分级表**

先给你的项目定一套 L1~L5 的强度分级表（可以直接改造第 11.2 节的示例），然后在后面的需求里只用等级不用形容词。

**第三部分：逐结果的反馈需求**

对第一部分穷举出的**每一种结果**，按五要素（触发时机 / 反馈通道 / 强度等级 / 受众 / 例外）写一份需求。要求：

- 至少覆盖 4 种结果，其中**必须包含至少 2 种失败或异常**。
- 每种结果都要写清楚：视觉、听觉、时间（顿帧/延迟）、镜头、数值表现、触觉，**没有的通道要显式写"无"**（写"无"和漏掉是两回事，前者是决定，后者是遗漏）。
- 每一条都要标注**受众**（谁能看到）。

**第四部分：三层自检**

对你写的每一种结果，回答：

- 功能反馈：玩家能确认"这件事发生了"吗？用哪一条？
- 情绪反馈：强度和事件重要性匹配吗？
- 信息反馈：玩家看完之后知道下一步该做什么吗？

**第五部分：降级与例外**

1. 低配机型的降级顺序（从先砍到最后砍，说明为什么这个顺序）。
2. 这个动作被玩家高频重复时（比如连续强化 50 次），有没有跳过/快速模式？跳过之后哪些反馈必须保留？（提示：功能反馈和信息反馈通常不能跳，情绪反馈可以）
3. 网络异常时的反馈是什么？（**本地预表现之后服务端返回失败，怎么回滚才不会让玩家觉得被欺骗？** 这是你作为服务端开发最有发言权的一题，认真写。）

### 13.3 思考题

1. 第 2 节说"润色不能创造实时控制和模拟空间"。但 MOBA 手游有几十到上百毫秒的网络延迟，玩家却普遍不觉得迟钝。它用了哪些手段？把这些手段逐个归到 5.3 节表格的三层里——有几个真的属于润色？（提示：先分清"补偿延迟"和"掩盖延迟"是两件事。）
2. 第 6.2 节说抽卡演出的"预告段"人为制造了一个反转时刻。请设计一个**不涉及概率暗示**、但同样能制造情绪起伏的抽卡演出结构。（提示：起伏不一定来自"可能出金"，也可以来自别的维度。）
3. 顿帧对攻击方和受击方可以设成不同的值。如果只给受击方顿帧、不给攻击方，体验会是什么样？反过来呢？这两种做法分别适合什么场景？
4. 本章说"信息反馈缺失会把策略游戏退化成数值游戏"。请找出你正在玩的手游里**一个信息反馈严重不足的战斗系统**，设计一份"战后信息面板"，说明它会让玩家的哪些新决策成为可能。
5. 假设你的项目要在低端机上砍掉 50% 的表现开销。请给出你的砍法优先级列表（至少 8 项，从先砍到最后砍），并为**最后三项**说明"为什么它们不能砍"。
