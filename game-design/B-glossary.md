# 附录 B - 术语表与资料地图

> **本附录干什么用**：三件事。①一张中英对照的术语表，让你在读英文资料、听 GDC 演讲、和外籍同事或发行方开会时能对上号，也让你在评审会上用词精确（很多设计争论其实是两个人在用同一个词说不同的东西）。②一张资料地图，告诉你哪本书该在什么时候读、读哪几章，以及怎么高效看 GDC。③一张贯穿案例索引，让你能按游戏回查——"我想再看看率土之滨的同盟到底在哪几章拆过"。
> **怎么用**：不要通读。术语表当字典查；资料地图在你想"接下来读点什么"的时候翻；案例索引在你复习或者写案子找参照时翻。

## 1. 中英对照术语表

**读这张表之前，先记住三对最容易被混用的词**，它们在下面的表里都有各自的条目，但值得先单独点出来：

| 容易混的一对 | 它们的关系 |
|---|---|
| **涌现 emergence** vs **递进 progression** | 这是一对**对立**的内容生成方式（Adams & Dormans 的划分）。涌现是"少量规则互相作用，产生设计者没有逐一排布过的局面"（围棋、旷野之息的野外、SLG 的服务器博弈）；递进是"设计者一段一段排好，玩家按顺序走过去"（关卡制主线、剧情章节）。涌现的内容成本几乎为零但不可控，递进的成本随内容量线性增长但完全可控。**绝大多数商业产品是"涌现内核 + 递进外壳"**，见[第 06 章](./06-systems-and-emergence.md) |
| **可供性 affordance** vs **信号 signifier** | affordance 是"这个东西**在物理上**支持什么操作"（一个突出的岩台可以站上去）；signifier 是"玩家**能不能看出来**它支持这个操作"（岩台上刷了一道黄漆）。**游戏里绝大多数"玩家不知道能这么干"的问题，是 signifier 缺失，不是 affordance 缺失**。见[第 19 章](./19-ux.md) |
| **元进度 meta-progression** vs **元循环 meta loop** | **不是一回事。** meta-progression 是 Roguelike 语境里的概念：一次 run 结束后被永久保留下来的东西（解锁、永久强化、剧情推进），它的作用是让"失败"也有收益（[第 25 章](./25-genre-openworld-narrative-roguelike.md)）。meta loop 是循环结构里的一层：跨会话的、以天或周为周期的那圈循环（日常任务 → 资源 → 养成 → 打更难的本），它的作用是让玩家明天还回来（[第 07 章](./07-loops.md)）。一个是"进度的归属"，一个是"循环的层级" |

### 1.1 设计基础：游戏、玩与框架

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 游戏设计 | game design | 设计的对象是**玩家的体验**，游戏只是制造体验的机器 | 01、02 |
| 体验目标 | experience goal | "玩家在这一刻应该感受到什么"。一切设计的判据，也是评审的第一个问题 | 02、15、26 |
| 魔法圈 | magic circle | Huizinga 的概念：游戏在时空里划出的临时边界，圈内规则暂时替代圈外规则。手游的难点在于它**故意把圈划破**（推送、社交、真钱） | 02 |
| 有意义的玩 | meaningful play | Salen & Zimmerman：玩家行动与系统结果的关系必须同时**可辨识**（我看得见我这一下产生了什么结果）且**整合**（这个结果会影响后面的进程，而不是当场蒸发） | 02、05 |
| 游戏态度 | lusory attitude | Suits：自愿接受低效率的规则，只为了让游戏成立（能用手拿球却偏要用杆打） | 02 |
| 前游戏目标 / 游戏手段 | prelusory goal / lusory means | 前者是不依赖规则也能描述的目标（球进洞），后者是规则允许的达成方式（只能用杆）。**规则的本质是禁掉高效手段** | 02 |
| 构成性规则 | constitutive rules | 定义游戏本身的规则，改了就变成另一个游戏 | 02 |
| 玩具 | toy | 有互动、没有目标。可以是游戏的组成部分（蛋仔的乐园），但本身不是游戏 | 02 |
| 谜题 | puzzle | 有唯一解，解开即消耗，重玩价值接近零 | 02 |
| 竞争 / 运气 / 扮演 / 眩晕 | Agon / Alea / Mimicry / Ilinx | Caillois 的四类玩。一款产品同时占几类，决定了它的用户结构 | 02 |
| MDA | Mechanics-Dynamics-Aesthetics | 机制（规则）→ 动态（运行时行为）→ 美学（玩家感受）。**设计者从 M 往 A 推，玩家从 A 往 M 看，方向相反** | 04 |
| 透镜 | lens | Schell 的方法：每个透镜是一组提问，不是一条答案 | 04、A |
| 四元素 | four elements | 机制 / 故事 / 美学 / 技术。任何一个元素的改动都会牵动另外三个 | 04 |
| 兴趣曲线 | interest curve | 玩家兴趣随时间的起伏。开头要有钩子，中段要有波峰，结尾要有最高点 | 04、17 |
| 内生价值 | endogenous value | 游戏里的东西有价值，仅仅因为游戏赋予了它价值。概念出自 Costikyan，Schell 做成了透镜 | 04 |

### 1.2 动机与体验

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 自我决定理论 | SDT (Self-Determination Theory) | Deci & Ryan：内在动机由三个需要驱动 | 03 |
| 自主 / 胜任 / 关联 | Autonomy / Competence / Relatedness | SDT 的三个需要。设计上分别对应：有真选择、能感到自己变强、有人在乎我 | 03 |
| PENS | Player Experience of Need Satisfaction | Rigby & Ryan 把 SDT 落到游戏上的模型 | 03 |
| 心流 | flow | Csikszentmihalyi：挑战与技能匹配时的忘我状态。**只覆盖"挑战型"体验，看风景和听剧情不归它管** | 03、09 |
| 心流通道 | flow channel | 难度必须跟着技能一起涨，否则掉进焦虑或无聊 | 03、09 |
| Bartle 四型 | Achiever / Explorer / Socializer / Killer | 成就者 / 探索者 / 社交家 / 杀手。**原始语境是 MUD/MMO**，套到单机或休闲手游上没有解释力 | 03、11 |
| 动机模型 | Gamer Motivation Model | Quantic Foundry 的十二动机模型，样本量大，可用来给品类定用户画像 | 03 |
| 四种乐趣 | 4 Keys 2 Fun | Lazzaro：Hard Fun（克服）/ Easy Fun（好奇）/ Serious Fun（改变自己）/ People Fun（和人一起） | 03 |
| 得意 | fiero | 克服困难那一瞬间的"我做到了"。Hard Fun 唯一能留住人的产物 | 03 |
| 乐趣即学习 | fun as learning | Koster：乐趣是大脑掌握新模式时的奖赏；模式学完就无聊 | 03、09、26 |
| 玩家表达 | player expression | 同一个系统里，不同玩家能打出可辨认的不同风格 | 09 |
| 沉没成本 | sunk cost | 已投入的东西让人不愿离开。既是留存工具，也是设计师自己最大的偏差来源 | 11、20、27 |
| 自定目标 | self-set goal | 玩家自己发明的目标（不用武器通关）。它需要四个前提：状态可见、路径多、不惩罚偏离、有观众 | 08 |

### 1.3 决策、系统与循环

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 有意思的决策 | interesting decision | Sid Meier："游戏是一系列有意思的决策。"有意思 = 有多个选项、有信息、有后果、有权衡 | 05 |
| 选项 / 信息 / 后果 / 权衡 | options / information / consequences / tradeoff | 决策的四个构件。缺任何一个，决策就退化成流程、抛硬币、噪音或清单 | 05 |
| 完全信息 / 隐藏信息 | perfect / hidden information | 全公开 → 变成算术题；全隐藏 → 变成抛硬币。**SLG 长线留人靠的就是精心切分的隐藏信息** | 05、10、23 |
| 伪决策 | fake choice | 表面多选，实际只有一个不亏的答案。手游里最常见的设计病 | 05 |
| 占优策略 | dominant strategy | 不管别人怎么做都更优的选项。它一旦存在，其他选项就是装饰 | 05、06 |
| 退化策略 | degenerate strategy | 玩家发现的、让整个玩法坍缩到一条路径上的解。**出现它先改规则，不要怪玩家** | 06 |
| 意图 / 可感知的后果 | intention / perceivable consequence | Doug Church 的两个工具：玩家能否形成一个计划，以及能否看清计划的结果。**看不清后果的系统学不会** | 05、08、13 |
| 系统 | system | 一组互相作用的部件 + 规则，运行起来会产生设计者没有逐条写下的行为 | 06、15 |
| 部件 / 循环 / 整体 | parts / loops / wholes | Sellers 的系统三层。看系统要同时看这三层，只看部件会漏掉全部有意思的东西 | 06 |
| 正反馈回路 | positive feedback loop | 领先者更容易继续领先。作用是**加速结束**，代价是拉大差距 | 06 |
| 负反馈回路 | negative feedback loop | 落后者更容易追上。作用是**延长悬念**，代价是让努力显得无效 | 06 |
| 橡皮筋 | rubber banding | 负反馈的一种直接实现（落后就变强）。做得太明显会被玩家识破并利用 | 06、09、23 |
| 涌现 | emergence | 少量规则互相作用，产生设计者没有逐一排布的局面 | 06 |
| 递进 | progression | 内容被一段一段排好，玩家按顺序走过。**与涌现是一对对立的内容生成方式** | 06 |
| 可能性空间 | possibility space | 规则允许的全部局面的集合。设计规则就是在雕刻这个空间的形状 | 06 |
| 耦合 / 耦合矩阵 | coupling / coupling matrix | 系统之间互相影响的关系；矩阵是把它显式画出来的工具。**手游的复杂度主要在耦合而不在单系统** | 15 |
| 核心循环 | core loop | 玩家反复做的那一小圈（做动作 → 得反馈 → 得资源 → 变强 → 做更好的动作） | 07 |
| 元循环 | meta loop | 跨会话那一圈，周期是天或周。**注意与 meta-progression 不是一回事** | 07 |
| 会话 | session | 一次连续游玩。设计会话就是设计"玩多久、为什么停、为什么回来" | 07 |
| 闸门 | gate | 限制循环速度的阀门：体力、次数、CD、冷却。**闸门恢复速度直接决定会话结构** | 07 |
| 弧 / 循环与弧 | arc / loops and arcs | Daniel Cook 的一对概念：**循环**是可重复的（负责持续），**弧**是一次性、有始有终的（主线、赛季、一次 run，负责新鲜）。健康的产品两者都有 | 07 |
| 技能原子 | skill atom | Daniel Cook：行动 → 模拟 → 反馈 → 建模，玩家学会一小块技能的最小单元 | 07、17 |
| 目标层级 | goal hierarchy | 即时（秒）/ 短期（分钟）/ 中期（天）/ 长期（周月）。**任一层断掉，玩家就会在那个时间尺度上流失** | 08 |

### 1.4 挑战、随机、社交、叙事与游戏感

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 难度 vs 挑战 | difficulty vs challenge | 难度是"通过所需的技能量"，挑战是"玩家感受到的被考验"。**难度是数字，挑战是体验，调数字调不出挑战** | 09 |
| 技能类型 | reaction / execution / strategy / knowledge | 反应 / 执行 / 策略 / 知识。**先说清考哪种技能，再谈难度** | 09 |
| 学习曲线 vs 难度曲线 | learning curve vs difficulty curve | 前者是玩家能力随时间的增长，后者是关卡要求随时间的增长。两条线的**间距**才是体验 | 09 |
| 技能地板 / 技能天花板 | skill floor / skill ceiling | 上手门槛 / 深度上限。理想是低地板 + 高天花板（easy to learn, hard to master） | 09、18 |
| 技能表达 | skill expression | 高手能不能把水平打出可见的差别。没有它，PvP 就只剩数值 | 09 |
| 动态难度 | DDA (Dynamic Difficulty Adjustment) | 系统根据玩家表现偷偷调难度。**被玩家发现的那一刻它就失效了** | 09 |
| 卡点 | progression wall | 玩家推不动、必须停下来养成的那个点。设计面在第 09 章，数值面见 [game-numeric 20](../game-numeric/20-long-term-pacing.md) | 09、24 |
| 不确定性 | uncertainty | Costikyan：随机只是不确定性的一种来源，还有对手、求解、隐藏信息、执行等 | 10 |
| 输入随机 | input randomness | 在玩家决策**之前**发生（发牌、地图生成、初始配置）。玩家要用决策去处理它，所以它制造玩法 | 10 |
| 输出随机 | output randomness | 在玩家决策**之后**发生（命中判定、暴击、掉落）。玩家无法处理，所以它制造情绪和收费点 | 10 |
| 保底 | pity | 达到一定次数后必定给。硬保底 / 软保底的概率数学见 [game-numeric 13](../game-numeric/13-probability-systems.md) | 10、21、24 |
| 伪随机分布（受控随机） | PRD (pseudo-random distribution) | 递增概率等让"感觉"比真随机更公平的受控随机；与 PRNG（伪随机数生成器）不是一回事。**公平感和数学公平是两件事** | 10 |
| 搭便车 | free rider | 合作系统里不出力却分收益的人。合作设计的第一个必须回答的问题 | 11、23 |
| 异步社交 | asynchronous social | 不要求同时在线的互动（留言、送体力、异步 PvP）。手游社交的主力形态 | 11 |
| 社交行动矩阵 | social action matrix | Amy Jo Kim：合作 / 竞争 / 表达 / 探索四种社交动作，用来体检社交设计是否偏科 | 11 |
| 毒性 | toxicity | 玩家之间的伤害性行为。**它通常是规则的产物而不是人品的产物** | 11 |
| 集结 | rally | 多人把兵力汇到一个发起者身上再打出去。SLG 组织度的核心机制 | 11、23 |
| 世界观 / 背景故事 / 剧情 / 玩家的故事 | setting / backstory / plot / player story | 叙事的四层。**手游真正无处不在的是第一层**（名词体系、UI 语言），不是主线剧情 | 12 |
| 作者叙事 / 涌现叙事 | embedded / emergent narrative | 前者是写好的，后者是玩家玩出来的。SLG 的战史属于后者，成本为零 | 12 |
| 环境叙事 | environmental storytelling | 用场景本身讲故事，不用文本 | 12、25 |
| 机制–叙事失调 | ludonarrative dissonance | Clint Hocking 提出：剧情说的和机制让你做的互相打架 | 12、24、25 |
| 三幕结构 / 起承转合 | three-act / kishōtenketsu | 西方与东亚的两种叙事骨架；后者不以冲突为轴，也被用作关卡的四步结构 | 12、17 |
| 展示而非讲述 | show, don't tell | 用玩家能看到、能做到的东西传达信息，而不是用文本告诉他 | 12、18 |
| 游戏感 | game feel | Swink：**实时控制 + 模拟空间 + 润色**三者合成的触感。同样的规则可以有完全不同的手感 | 13 |
| 实时控制 | real-time control | 输入被持续、即时地转成变化。看的是延迟、响应和可打断性 | 13 |
| 润色 | polish | 不改变规则、只改变感受的那一层（特效、音效、震动、缓动） | 13 |
| juice | juice | 用极低成本的表现堆出"手感很好"的总称。出处是 *Juice It or Lose It* | 13 |
| 顿帧 | hit stop | 命中瞬间双方短暂静止，把"打中了"这条信息压进几帧里。打击感最核心的一件事 | 13 |
| 屏幕震动 | screenshake | Vlambeer 的 *The Art of Screenshake* 让它成为通用手法。**过量会变成噪音** | 13 |
| 本地预表现 | client-side prediction | 先在本地播动画，服务端结果回来再校正。手游 PvP 掩盖延迟的标准做法 | 13 |
| 打击感 | —（中文行业术语） | 顿帧 + 震屏 + 音效 + 特效 + 受击反馈的合成结果，不是单一参数。英文里没有完全对应的词，说明时要拆成上面这几项 | 13 |

### 1.5 工作方法与文档

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 原型 | prototype | **一个原型只回答一个问题**。回答完就该扔掉，舍不得扔是这套方法失效的头号原因 | 14 |
| 纸面原型 | paper prototype | 用纸笔和骰子跑规则。适合验证决策结构、回合流程、经济方向，不适合验证手感 | 14、20 |
| Wizard of Oz 原型 | Wizard of Oz prototype | 界面是真的，背后由人假装成系统。用来在写代码之前验证交互与体验 | 14 |
| 灰盒 / 白盒 | greybox / whitebox | 只有几何体没有美术的关卡。**判据：换成灰色方块之后这一关还成立吗** | 14、17 |
| 垂直切片 | vertical slice | 一小段做到上线品质的完整体验（含美术、音效、UI），用来验证"做出来到底什么样" | 14、27、28 |
| 迭代循环法则 | rule of the loop | Schell：设计质量取决于**迭代次数**，所以优先降低单次迭代的成本，而不是提高单次的质量 | 14 |
| 风险优先 | risk-first | 先做你最不知道的那部分，而不是最容易做的那部分 | 14、28 |
| cabal | cabal | Valve 在《半条命》采用的跨职能小组设计法（Birdwell 1999）。设计不由一个人做 | 14、27 |
| 砍功能 | cut | 越早砍越便宜。砍不是二选一，是**分级**（砍到什么程度） | 14、27 |
| kill your darlings | kill your darlings | 最舍不得的那个功能往往正是该砍的那个 | 14、27 |
| 功能蔓延 / 范围蔓延 | feature creep / scope creep | 前者是功能越加越多，后者是整体范围越滚越大。**每个单看都很便宜，耦合和维护成本是叠加的** | 14、16、26 |
| 不做清单 | won't-do list | 明确写下"这个版本不做什么"。它比需求列表更能保护设计支柱 | 14、16、27 |
| 一页纸设计 | one-page design | Librande 的主张：一页里必须有一张图，图不是插图而是**检验装置**——画不出来说明还没想清楚 | 16、27、28 |
| 十页纸 | ten-pager | 一页纸之后、完整案子之前的中间形态（Rogers） | 16 |
| 设计文档 | GDD (Game Design Document) | **单一巨型 GDD 已经死了**，活下来的是文档家族：一页纸 / 概念案 / 系统案 / 关卡案 / 活动案 / 配置表 / 变更记录 | 16 |
| 系统案 | system spec | 本课最核心的产出物。九节结构见 `templates/system-spec.md` | 15、16 |
| 配置表 | config table | 案子定结构和体验要求，表定数字。**表头设计是策划的活，不是程序的活** | 16 |
| 变更记录 | changelog | 文档与实现分叉的唯一解药。改了什么、为什么改、谁拍的板 | 16 |
| 埋点 | telemetry / instrumentation | 案子里必须自己写清楚要埋什么，否则上线后无法验证设计假设 | 16、20 |
| 幂等 | idempotent | 同一个请求重复执行结果不变。策划写规则时要主动交代重复触发怎么办 | 15、16 |
| 走查 | walkthrough | 拿着案子或关卡逐步骤走一遍，检查每一步玩家看到什么、能做什么 | 14、17、20 |
| 出声思考 | think-aloud | 让被试边玩边说自己在想什么。**用来找"他为什么这么想"，不是用来找 bug** | 14、20 |
| RITE | Rapid Iterative Testing and Evaluation | 微软游戏用户研究提出：发现问题当场改、当场再测，不攒到测试结束 | 20 |
| 知识的诅咒 | curse of knowledge | 你知道了就再也想象不出不知道是什么感觉。设计师最难摆脱的偏差 | 20 |
| 设计假设 | design hypothesis | 把设计目标写成**可证伪**的命题，再翻译成可观测指标 | 20 |

### 1.6 关卡、引导与 UX

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 关卡 | level | 空间 + 规则 + 目标 + 节奏。四者缺一就不是关卡，是场景 | 17 |

| 节奏 | pacing | 强度随时间的起伏。**平的节奏比难的节奏更劝退** | 17、22 |

| 理性关卡设计 | rational level design | 育碧体系：把关卡拆成可量化的元素与技能考点，让关卡可批量生产（McMillan） | 17 |
| 四步教学结构 | — | 引入 → 发展 → 变化 → 结论。出自林田宏一 2012 年接受 Gamasutra 采访时对马里奥关卡结构的讲解，Mark Brown 的视频普及了它；是启发式模板，不是硬规则 | 17、18 |
| Boss 阶段 | phase | Boss 的核心结构是阶段：每阶段考一件新东西，并给玩家一次"我看懂了"的机会 | 17 |

### 1.7 商业化与运营

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 免费游玩 | F2P (Free to Play) | 付费发生在体验过程中，因此每个设计决定都要回答"这会不会被商业化污染" | 21 |
| 内购 / 广告变现 | IAP / IAA | 前者卖道具，后者卖玩家的注意力。IAA 数值面见 [game-solo](../game-solo/README.md) | 21 |

| 软付费墙 / 硬付费墙 | soft / hard paywall | 前者可以用时间绕过，后者不能。硬墙对留存的伤害是结构性的 | 18、21 |
| pay-to-win 连续谱 | pay-to-win spectrum | 不是"是/否"而是一条谱。**品类容忍度由"别人的强度会不会让我输"决定** | 21、24 |

| 版本节奏 | release cadence | 多久一个大版本、之间怎么填。节奏一旦建立，玩家会按它安排生活 | 22 |

### 1.8 品类专题

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 策略经营 | SLG (Simulation Game，中文行业指策略类手游) | 地图 + 时间 + 联盟。**时间是核心资源**，付费本质是买时间 | 23 |
| 率土-like | 赛季制 SLG | 连续大地图、领地必须连通、赛季 2~3 个月后重置、行动力不可买 | 23 |

| 树状分支 / 分支汇合 | branching / branch & bottleneck | 叙事分支的两种结构。后者定期收束，成本可控，是商业叙事的主流做法 | 25 |

### 1.9 评审与领导

| 中文 | 英文 | 一句话说明 | 章节 |
|---|---|---|---|
| 设计评审 | design review | 三层顺序：**目标 → 系统 → 规格**。顺序不能反，第一层没过就不该看第三层 | 26 |
| 设计批评 | critique | 对着**目标**说事，不是对着喜好说事。"我不喜欢"和"这不符合目标"是两句话 | 26、27 |
| 设计愿景 | design vision | 一个画面，不是一句口号。它要能让人在脑子里看见玩家在干什么 | 27 |
| 设计支柱 | design pillars | 愿景的可执行版本。**好支柱的判据是它能否否决一个看起来不错的功能** | 27 |
| 多即是好 | more is better | 第 1 号设计谬误。检验：加了之后玩家每天多做的那个决定是什么 | 26 |
| 抄而不解 | cargo cult | 抄了机制，没抄它解决的问题。检验：原作里这条规则解决了什么问题，我们有这个问题吗 | 26、28 |
| 为系统而系统 | — | 系统的存在理由落在另一个系统上，而不是落在玩家体验上 | 26 |
| 把问题推给数值 | — | 数值能调**程度**，不能调**结构**。没有决策的系统配任何数字都不对 | 26 |
| 把复杂当深度 | complexity vs depth | 复杂度 = 规则和状态的数量；深度 = 有意义决策的数量。**两者可以完全无关** | 26 |
| 把新鲜当好玩 | novelty vs fun | Demo 惊艳、三个月后没人玩。检验：玩家第 20 次在想什么 | 26 |
| 幸存者偏差 | survivorship bias | "《XX》就是这么做的"——你看不见用同样做法死掉的一百个 | 26 |
| 集中的酷 | concentrated coolness | Rob Pardo（GDC 2010）：与其做十个平庸功能，不如把一个做到让人记住 | 24、27 |
| 易学难精 | easy to learn, hard to master | 低技能地板 + 高技能天花板的口号版本，同样出自暴雪的设计哲学 | 09、27 |
| 立项 | greenlight | 决定一个项目是否开始。评审关心四个问题：为什么是你们、为什么是现在、最大风险验证了没、失败代价多大 | 28 |
| 提案 | pitch | 先讲体验不讲功能；用一个玩家故事开场；主动承认最大的风险 | 28 |
| 差异化 | differentiation | 体验差异 > 结构差异 > 题材差异。**题材差异最容易被抄走** | 28 |
| 里程碑 | milestone | 每个里程碑应该是一个**决策点**（继续还是停），不是一个交付点 | 28 |

## 2. 资料地图

**先说这张地图的编制原则**，因为它决定了你能不能信任它：**本附录只收录编者核实过存在的资料。** 游戏设计领域最泛滥的一类内容是"某某大神在某某演讲里说过……"，其中相当一部分演讲名、年份甚至作者都是以讹传讹。所以本课有一条硬规矩：**宁可描述现象不署名，也不编造出处。** 你在正文和这里看到的每一个书名、演讲名、作者名都是可查的；凡是不确定的地方，本课的写法是"有一种流行说法是……"而不是给你一个看起来很权威的标题。

另一件事也要说清楚：**这是一张"够用"的清单，不是"完整"的清单。** 它只收本课用到的资料。你在别处看到的好东西完全可能更好，那只说明这张地图有边界。

### 2.1 书单：按本课的依赖顺序

排序原则是"读了它，本课的哪几章会突然变得容易"。**不要按顺序全读**——后面会给"只读三本"和"只读一本"的建议。

| 21 | **The Art of Computer Game Design**（Chris Crawford, 1984） | 最早的系统性游戏设计著作。**读它的历史价值大于实用价值**，但会让你意识到很多"新概念"四十年前就有了 | 01、02 |

| 23 | **Game Balance**（Ian Schreiber & Brenda Romero, 2021） | 平衡的教科书。**本课不展开，它属于姊妹课程** [game-numeric](../game-numeric/README.md) 的范围 | 见 game-numeric 04、05、16 |

**如果你只读三本**：Schell（框架）+ Sylvester（最贴你的思维方式）+ Sellers（系统）。这三本覆盖本课阶段零到阶段二的绝大部分理论。

**如果你只读一本**：Sylvester 的《体验引擎》。理由是它讲的东西和你写服务端的思维方式最接近，读起来不需要翻译。

**一条阅读纪律**：**每读完一本，立刻拿它去拆一款你正在玩的游戏。** 读书本身不产生设计能力，用它的词汇重新描述一个你熟悉的系统才会。

### 2.3 中文资源

中文资料的价值是**它讲的正是你要做的那种产品**——英文资料里几乎没人认真分析率土之滨的同盟或明日方舟的养成线。风险是**证据强度普遍更低**：大量"拆解报告"是作者玩了两周之后的推测，读起来却很像内部资料。

| 来源 | 是什么 | 怎么用 |
|---|---|---|
| **腾讯游戏学堂 GWB**（`gwb.tencent.com`） | 一线从业者的方法论文章与公开课，覆盖系统、数值、关卡、UX | **质量最稳的中文来源。** 它的文章通常有具体项目背景，可信度高于匿名拆解 |
| **GameRes 游资网**（`gameres.com`） | 产品拆解报告的主要集散地，SLG 和卡牌手游的深度分析大多在这里 | **看结构，不看数字。** 拆解里的具体配比、概率、投放量几乎都是反推的，误差可能很大 |
| **机核 GCORES** | 偏游戏文化、主机与叙事的播客和长文 | 补第 12 章（叙事）和第 25 章（开放世界/叙事驱动）的体感。**它不是方法论来源** |
| **indienova** | 独立游戏视角的设计文章与开发日志 | 看"小团队怎么在约束下做设计"，对第 14、28 章有用 |
| **B 站的 GMTK 等设计频道中文字幕搬运** | Mark Brown 等英文设计频道的字幕版 | 当成每章的"视频版"补充。**两个注意事项**：字幕质量参差，关键术语建议对照原视频；视频的发布时间可能很早，里面的游戏版本已经变了 |
| **知乎「游戏设计」「游戏策划」话题** | 从业者笔记与大量业余讨论混杂 | **只用来找线索，不用来定结论。** 看到有价值的说法，回到一手来源去验证 |

**中文资料的三条使用纪律**：

1. **先分辨作者位置。** 做过这个品类的人写的、和玩过这个游戏的人写的，价值差一个量级。看作者有没有说"我们当时……"。
2. **拆解报告看结构不看数字。** 这条和姊妹课程 [game-numeric 附录 B](../game-numeric/B-glossary.md) 的结论一致。结构（有哪些系统、怎么连的、闸门在哪）可以从外部观察到，数字不能。
3. **警惕"因为所以"式的意图归因。** "《原神》这么做是为了拉长留存"——作者不可能知道，他在推测。推测本身没问题，把推测写成事实才有问题。

### 2.4 怎么高效看 GDC

GDC 是这个行业公开资料密度最高的地方，但它对新人极不友好：一年几百场，标题写得像广告，而且好的和差的混在一起。下面是一套可执行的方法。

**第一，先搞清楚免费的部分在哪。**

| 渠道 | 内容 | 说明 |
|---|---|---|
| **GDC Vault**（`gdcvault.com`） | 历年演讲的视频与 slides | **有免费与付费两部分。** 每年都有一批被官方设为免费，slides（PDF）的免费比例通常高于视频 |
| **GDC 官方 YouTube 频道** | 大量完整演讲的免费视频 | **新人应该从这里开始。** 官方会持续把往年的重要场次放上来，包括本附录 2.2 节里的多数演讲 |
| **演讲者个人页面 / 博客** | 讲者自己放的 slides 与讲稿 | 找不到视频时，直接搜"讲者名 + slides"往往有 |

**第二，按设计师名字追踪，而不是按标题搜索。** 这是本节最重要的一条。标题是为了吸引现场听众写的，检索价值很低（"重新思考 XX"这类标题一年有几十个）。但**一个把某件事讲透过一次的人，通常会持续讲这件事**。你的做法应该是：读到一场让你有收获的演讲 → 记下讲者名字 → 去搜这个人的其他演讲、他的博客、他参与过的项目 → 顺着他引用的人再往外走一层。三四轮之后你会得到一张属于自己的"这个领域谁值得听"的地图，这张地图比任何书单都有用。

起点就用 2.2 节里的名字：系统与经济找 Daniel Cook，决策找 Sid Meier，关卡找 Mark Brown 和林田宏一，游戏感找 Vlambeer 和 Steve Swink，文档找 Stone Librande，数据驱动的设计找 Slay the Spire 的 Anthony Giovannetti。

**第三，看之前先翻 slides，看的时候用倍速。** 一场 60 分钟的演讲，slides 五分钟翻完，翻完就知道值不值得看完整版、该重点看哪一段。真正需要逐帧看的只有游戏感、动画、关卡演示这类必须看画面的内容。

**第四，看完写一页纸笔记。不写等于没看。** 三天之后你只会记得一个模糊的印象，而模糊的印象不能用来设计。笔记模板固定四栏，控制在一页以内：

```
标题 / 讲者 / 年份 / 链接
1. 他要解决的问题是什么？（用一句话，不许抄标题）
2. 他的解法是什么？（机制层面，具体到规则）
3. 可迁移的那一条是什么？（"如果我做 XX，我会……"）
4. 我不同意 / 我觉得在手游里不成立的是哪一条？为什么？
```

第 4 栏是最重要的一栏，也是最容易被跳过的一栏。**一场演讲里没有任何一条让你想反驳，通常说明你没有真的在想。**

**第五，知道 GDC 的系统性偏差。** 三条：①**幸存者偏差**——上台的都是成功的项目，用同样方法失败的人不会被邀请去讲；②**事后合理化**——讲者在讲一条整理过的因果链，真实过程通常混乱得多；③**语境差异**——大量演讲来自买断制、主机、欧美市场，它的结论迁移到国内 F2P 手游时，第三层（动态）经常会变。这正是第 26 章"抄而不解"那条谬误要防的东西。

### 2.5 关于具体游戏设计意图的资料：一个诚实说明

**这是整张地图里最需要你警惕的一块。**

设计原理有公开的、可引用的来源；但**一款具体游戏"为什么这么设计"几乎从不公开**。你在网上看到的绝大多数"《XX》为什么这么做"都是外部推测，包括本课程里的那些。区别只在于推测者有没有把它标出来。

按证据强度排一个阶梯，从强到弱：

| 档 | 类型 | 为什么可信 / 为什么要打折 | 本课怎么标 |
|---|---|---|---|
| 1 | **开发者一手访谈、官方设计说明、开发者博客、公开专利** | 设计者本人说的。**仍要打折**：他可能在做公关，也可能在事后合理化，但至少"他说过这句话"是事实 | 【实证】，并写明来源 |
| 2 | **GDC / 其他会议的开发者演讲** | 同样是设计者本人，但经过了更多筛选和包装：只讲成功、只讲能讲的部分、商业敏感的东西一律略过 | 【实证】，并写明演讲与年份 |
| 3 | **行业拆解报告（含中文拆解、数据机构报告）** | 作者是专业的、看过很多产品，但他和你一样在外面看。**结构部分较可信，意图与数字部分是推测** | 【行业口径】或【推导】 |
| 4 | **玩家社区推测、攻略组结论、"业内朋友说"** | 有时候极准（攻略组的数据挖掘），有时候完全是想象。**关键是它不可追溯** | 【推导】，且尽量不引用 |

**本课的具体做法**：正文里凡是描述一款游戏的**规则**（能在游戏里观察到的），不加标注，因为那是事实；凡是解释一款游戏**为什么这么设计**，一律标【推导】，除非有第 1、2 档的来源，那就写明"某某在某某演讲里说过"。你会在第 12、21、23、24、25 章看到大量这样的标注——那不是编者在推卸责任，是在教你区分"我看到的"和"我猜的"。

**为什么值得单独写一节**：因为**新人最常见的缺陷不是不懂理论，是把推测当事实用**。评审会上说"率土是这么做的所以我们也这么做"，追问一句"率土为什么这么做"就答不上来——这就是第 26 章的"抄而不解"。养成标注的习惯是防它的唯一办法。

### 2.6 可靠性三档标注（本课的定义，再列一次）

| 标注 | 含义 | 你该怎么对待 |
|---|---|---|
| **【实证】** | 有公开的一手来源可查：论文、书、GDC 演讲、官方开发者访谈、公开专利。**本课会写明来源名** | 可以直接引用，但要自己去看一眼原文——转述总会丢东西 |
| **【行业口径】** | 从业者普遍的说法、经验法则。**没有严格证据，而且会随时代和品类变化** | 当成"先验"用：作为起点假设可以，作为结论不行。用之前问一句"这条在我这个品类、这个年份还成立吗" |
| **【推导】** | 本课程从公开表现反推出来的判断，主要是"某款游戏为什么这样设计"。**可能是错的** | 当成一种**读法**而不是一个答案。重点看推导过程（从哪条规则推到哪个结论），过程比结论有用 |
| （无标注） | 教科书级共识 | 直接用 |

**一条给你自己写文档的建议**：把这三档标注搬进你自己的案子和拆解笔记里。写"【推导】我认为竞品这么做是因为……"和写"竞品这么做是因为……"，在评审会上会得到完全不同的对待——前者是一个可以被讨论的假设，后者是一个可以被打脸的断言。

### 3.3 本课虚构的两个案例项目

这两个名字**在现实中不存在**，是本课为了完整演示流程而虚构的，请不要去搜索：

| 名称 | 出现章节 | 用途 |
|---|---|---|
| **《归墟》** | 27、28 | 一款虚构的战棋卡牌手游。用来演示：设计支柱怎么写、怎么用支柱否决一个看起来不错的功能、以及从一次拆解一路推到立项文档的完整链条 |
| **《铁血三国》「同盟红包」** | 26 | 一份虚构的、有代表性缺陷的系统案。用来演示三层评审（目标 → 系统 → 规格）怎么走，以及一份完整的评审记录长什么样 |

另外，第 14、15、16、20 章围绕**一个公会 / 公会战系统**反复出现：第 15 章从零设计它，第 16 章拿它演示怎么消歧义，第 14 章走它从一页纸到上线的七个阶段，第 20 章给它写测试计划。**这条线是本课"工作方法"部分的隐藏主轴**，如果你想集中看"一个系统的完整生命周期长什么样"，按 15 → 16 → 14 → 20 的顺序读这四段。

### 3.4 怎么用这张索引做复习

三种用法：

1. **按游戏纵读。** 挑一款你在玩的游戏，把它出现的所有章节按顺序读一遍，你会看到同一款游戏在决策、循环、社交、商业化几个视角下被切开的样子——**这正是拆解能力的核心**。
2. **按对照横读。** 每一行的手游和买断制对照是刻意配对的：明日方舟 ↔ 传送门（关卡）、原神 ↔ 哈迪斯（商业化）、率土同盟 ↔ 动物森友会（社交）、阴阳师 ↔ 杀戮尖塔（随机）。**把配对的两段连着读，差异会自己跳出来。**
3. **找你自己的替换样本。** 表里的游戏你不一定都玩过。用第 00 章的拆解模板，把你真正在玩的那款填进对应的位置——**本课的案例是可替换的，方法不是**。
