# 19 - UX 与界面

> **本章目标**：学完你应该能用认知心理学的框架诊断一个界面出了什么问题（是没看见、没记住、还是不知道能点）；能给一款手游画出信息架构图并指出层级错位；能写出 UI/UE 拿到就能开工的界面需求，而不是一句"照竞品那样做"。

## 1. 一个功能都对但没人用的系统

想象这样一件事，你大概率经历过：

团队花了三个月做了一个新系统。规则设计得很完整，程序实现没有 bug，QA 全部通过，数值也配好了。上线两周后拉数据，发现**只有 4% 的玩家进过这个系统的界面**，其中一半在 10 秒内退出了。

复盘会上有三种典型的解释：

1. "玩家不喜欢这个玩法" —— 但 96% 的人根本没看过，谈不上喜不喜欢。
2. "引导没做好" —— 引导做了，完成率 98%。
3. "入口太深" —— 入口在主界面右下角的"更多"里，点进去是一个九宫格，这个功能在第七格。

第三条是真的，但它只说对了一半。**真正的问题是：这个系统从设计的第一天起，就没有人回答过"玩家凭什么会想点它、点了之后凭什么看得懂"。** 系统案里写满了规则、状态、接口、数值，唯独第 2 节（玩家视角的流程）只有一句"进入界面后可以进行 XX 操作"。

这就是 UX 在游戏开发里的位置：**它不是"把界面做好看"，它是"让你设计的东西真的被玩家用到"**。一个没被用到的系统，等于没做。

作为服务端开发，你对这件事其实有天然的直觉：一个接口设计得再优雅，如果调用方不知道怎么用、参数含义靠猜、错误码没有说明，它就是个坏接口。**界面就是玩家调你的系统时用的那个 API。**

## 2. Hodent 的框架：玩家的大脑不是设计者的大脑

Celia Hodent 曾在育碧、LucasArts 从事游戏 UX 工作，后来担任 Epic Games 的 UX 总监；《The Gamer's Brain》是把认知心理学系统地引进游戏 UX 的那本书。她的框架有两根支柱【实证】：

```
                   游戏 UX
                      │
        ┌─────────────┴─────────────┐
        │                           │
   可用性 (Usability)          吸引力 (Engage-ability)
   "玩家能不能顺利地用"        "玩家愿不愿意投入"
        │                           │
   建立在大脑的硬约束上：      建立在动机与情绪上：
   感知 / 注意力 / 记忆        动机 / 情绪 / 游戏流
```

两根支柱的分工很重要：**可用性问题通常能被判定为"错"**（有明确的失败标准：找不到、点不到、看错了、不知道点了会怎样）；**吸引力问题一般只能被判定为"强/弱"**。一个按钮玩家找不到，这是 bug 级别的错误，没有辩护空间；一个系统玩家看得懂但不想玩，那是设计问题，要回到[第 03 章](./03-why-players-play.md)（动机）和[第 08 章](./08-goals-progression-rewards.md)（目标）去解。这个二分是**操作上的方便，不是绝对的**：可用性也带主观成分（对新手不好用还是对老玩家不好用？），吸引力也能用参与率、留存去逼近。这一章主要讲第一根支柱，因为它可以被系统性排查。

### 2.1 五个认知约束和它们在界面里的表现

| 约束 | 大白话 | 在游戏界面里长什么样 | 设计对策 |
|---|---|---|---|
| **感知（Perception）** | **你以为玩家看到了，其实他没看到。** 视觉系统是有选择的，它只处理它认为重要的东西 | 重要提示放在角落、和背景对比度不够、红绿区分（约 8% 男性有色觉障碍） | 关键信息用**位置 + 大小 + 对比度**三重强调；颜色永远不是唯一的信息载体，必须配形状或文字 |
| **注意力（Attention）** | **注意力是单通道且极其稀缺的。** 玩家专注于一件事时，视野里的其他变化根本不会被察觉（变化盲视） | 战斗中弹出的提示没人看见；玩家专注于抽卡动画时，旁边的资源扣减完全没注意到 | 一次只强调一件事；在玩家有余裕的时刻（结算界面、待机界面）呈现信息，而不是在高强度时刻 |
| **记忆（Memory）** | **工作记忆一次只装得下很少几样东西，而且很快遗忘。** "识别"远比"回忆"容易 | 让玩家记住某个道具在仓库第几页、让玩家记住三天前教过的规则 | **识别优于回忆**：把选项摆出来让玩家认，而不是让他想起来。所有教过的规则要能随时查到 |
| **动机（Motivation）** | 玩家做一件事需要理由，界面要让理由可见 | 一个入口没有任何"进去有什么好处"的暗示 | 入口上显示收益（"可领取 3 个"）而不只是名字 |
| **情绪（Emotion）** | **情绪会放大或掩盖一切可用性问题。** 玩家挫败的时候，一个平时无感的小卡顿会被当成"这游戏真烂" | 连输三把之后的返回按钮做得难点 | 在失败、等待、损失这些负面情绪节点上，把可用性做到最好 |

**第二条和第五条是工程师最容易低估的。** 你在冷静状态下测试界面，永远测不出"玩家连输三把之后找不到重试按钮"这种问题。这是为什么必须做真实玩家测试（[第 20 章](./20-playtesting-and-validation.md)）。

### 2.2 UX 领域最重要的一句话

> **设计者对自己的界面是"已经知道答案的人"，所以他判断不了"找不到"这一类问题。**

这和[第 17 章](./17-level-design.md)"设计者走查发现不了设计问题"是同一条原理：你知道那个按钮在哪，所以你永远不会体验到"找不到"。

**但"只能靠真实玩家测试才能发现问题"是说过头了。** 实际工作是两步：**内部评审 / 启发式检查**（让没参与这个界面的同事对照一份清单逐条走，本章第 10 节那张表就能当清单）能筛出大部分可用性问题——可点性不明、状态缺失、返回路径不一致、极值没设计、反馈缺失；它发现不了的是玩家的真实动机、真实情绪下的行为、以及团队共有的盲区，那些要靠**真实玩家测试**（think-aloud + 任务完成率，见[第 20 章](./20-playtesting-and-validation.md)），后者同时告诉你每个问题的**真实影响有多大**。

**顺序是：内部评审先筛掉便宜的问题，真实玩家测试验证影响、排优先级。** 界面走查成本极低（拉个同事看 30 秒，问他"你觉得这个界面能干什么"），但绝大多数团队连这一步都不做。

## 3. 认知负荷与信息密度

认知负荷的三种类型（内在 / 外在 / 相关）在[第 18 章](./18-onboarding.md)已经讲过理论，这里不重复定义，只给界面这一侧的对策——同一个概念在教学和界面上的对策完全不同：

| 类型 | 界面上的例子 | 界面上的对策 |
|---|---|---|
| **内在负荷**（东西本身就复杂） | 一件装备 8 条属性、一个角色 4 条养成线 | 只能**分组和分层**，不能删：用格式塔分组原则（靠近的、同色的、同框内的被视为一组），用渐进披露把次要信息折起来 |
| **外在负荷**（呈现方式造成的浪费） | 术语没解释、数字没量级（`1234567` 而不是 `123.5万`）、同一功能两个入口、按钮位置每个界面都不一样 | **全力砍掉。这部分是纯浪费，也是最容易改的部分** |
| **相关负荷**（真正在理解时用掉的） | 玩家在权衡"这次抽卡还是攒着" | **保护它**：把省下来的注意力留给真正的决策 |

### 3.1 手游界面的信息密度问题

手游主界面的信息密度普遍是失控的。一个典型的卡牌手游主界面上可能同时有：8~15 个功能入口、3~6 种货币、2~4 个活动 banner、一个跑马灯公告、十几个红点、一个战力数字、一个头像和等级条。

为什么会变成这样？**因为界面是被"加"出来的，从来没有人被授权"减"。** 每个新系统上线都要一个入口，每个运营活动都要一个 banner，每个入口的负责人都认为自己那个很重要。没有人负责整体，于是主界面变成了所有人的公告栏。

三个可以立刻用的对策：

**一、渐进披露（progressive disclosure）。** 默认只显示玩家此刻需要的，其余折起来。例子：装备详情默认显示 3 条主属性 + 一个"展开全部"，而不是一次铺 8 条。

**二、按玩家的动作序列组织，而不是按系统清单组织。** 玩家今天打开游戏要做的事是有顺序的：领日常 → 打本 → 养成 → 公会。界面就该按这个顺序排，而不是按"我们有 12 个系统"来排。

**三、给主界面设一个入口预算，并且是硬预算。** 例如"主界面第一层最多 9 个入口"，新系统要上，就得有一个老系统下去或者合并。**这条规则的价值不在于 9 这个数字，在于它强迫团队每次都做一次优先级判断。** 没有预算的地方，熵一定会增长。你对这一点应该很有共感 —— 这就是"接口不能只增不减"。

## 4. 可供性与信号

这是界面设计里最实用的一组概念，来自工业设计：

- **可供性（affordance）**：一个东西**实际上能做什么**。门把手可以拉，平板可以推。
- **信号（signifier）**：一个东西**看起来能做什么**的视觉线索。门把手的形状在告诉你"拉我"，平板的形状在告诉你"推我"。

游戏界面里的问题几乎都是这两者**不一致**：

| 症状 | 问题类型 | 例子 | 修法 |
|---|---|---|---|
| 能点，但看不出能点 | 有可供性，缺信号 | 一段文字其实是链接、一个数字其实能点开详情、立绘其实可以互动 | 加视觉线索：按钮化、加下划线、加箭头、加轻微动效 |
| 看起来能点，其实不能 | 有信号，无可供性 | 装饰性的图标做得像按钮、灰掉但仍然高亮的按钮 | 去掉误导性样式；不可用的东西要"看起来就不可用" |
| 能点，但不知道点了会怎样 | 信号不完整 | 一个"确认"按钮，不知道确认的是什么 | 按钮文案写动词+宾语（"消耗 20 体力开始"而不是"确认"） |
| 点了不知道有没有生效 | 缺反馈 | 点了按钮界面没变化 | 见[第 13 章](./13-game-feel-and-feedback.md)：任何操作 100ms 内必须有可见反馈 |

**一条实操规则：界面上的每一个元素，玩家应该在半秒内知道它属于三类中的哪一类 —— 可点的、只是信息的、装饰的。** 三类混在一起、样式互相借用的界面，玩家会用"到处乱点"来试探，然后累了就退出。

**手游有一个特有的信号问题：图标同质化。** 一排十个入口，全是同样风格、同样配色、同样带一点金光的圆角方形图标，上面画着略有差异的箱子/剑/旗帜。玩家分辨它们靠的是**位置记忆**而不是**图标识别**，一旦运营调整了顺序，玩家就全找不到了。**判断方法：把图标全部去掉文字，你自己还认得出几个？** 认不出五个以上，这套图标就是失败的。

## 5. 信息架构与导航深度

**信息架构（Information Architecture, IA）** 决定了游戏里所有内容怎么分组、怎么命名、怎么嵌套。

**它归谁，依团队而异。** 有专职 UX 的团队通常把信息架构算进 UX 的职责（Hodent 公开讲的职责框架就是这么划的）；没有专职 UX 岗的手游团队里，它落在系统策划和 UI/UE 身上。**准确的说法是：它是策划、UX、UI/UE 三方协作的产物，而策划掌握着另两方拿不到的输入——每个系统的重要性、使用频率、玩家在什么场景下需要它。** 所以不管怎么分工，**你都不能把这件事整个丢出去**：你不给频率和优先级，别人只能靠猜或靠视觉平衡来排。

### 5.1 导航深度：一条被误用的经验法则

手游和网页行业都流传着同一条经验法则【行业口径】：

> **任何常用功能，从主界面出发的点击次数不应超过三次。**

**这条法则的流行版本（"三次点击法则"）站不住。** 它出自早期网页设计的口头传统，后来被反复检验过：**点击次数本身并不能预测用户会不会放弃**（NN/g 等机构专门写过文章说明这一点）。真实机制是：**玩家放弃是因为"不知道自己走对了没有"，不是因为多点了一下。** 一条五步但每步都在收窄目标的路径，体验好过一条两步但每步都要猜的路径。

所以它**只能当作粗糙的复杂度预警**：层级变深通常伴随入口更不显眼、路径更容易断。但**层级数不是判据，指标才是**：

| 指标 | 怎么测 | 说明什么 |
|---|---|---|
| **任务完成率** | 给一个任务（"把这个角色升一级"），记录多少人无提示独立完成 | 最硬的指标，完不成就是错 |
| **首次完成耗时** | 完成任务的秒数，新手老玩家分开统计 | 路径可不可理解 |
| **错误率 / 走错次数** | 中途点错界面、返回了几次 | 哪一层的命名或图标有歧义 |
| **路径可理解性** | think-aloud："你觉得点这个会去哪" | 他从哪一步开始猜 |

方法细节在[第 20 章](./20-playtesting-and-validation.md)。**在拿到这些数据之前，"三层"只是提醒你去测的信号，不是能用来否决方案的规则。**

层级预算仍然有用，但它的价值和第 3.1 节的入口预算一样，**在于强迫团队做优先级判断，不在于"3"这个数字**：

```
  第一层：主界面     ← 玩家每次登录必看，最贵的资源
  第二层：系统主界面 ← 一个玩法/系统的入口页
  第三层：具体操作页 ← 编队、强化、购买的实际操作
  ────────────────────
  更深的层级：默认只放"低频 + 深度"的内容（图鉴详情、设置子项、历史记录）；
             要往下面放常用功能，就得拿完成率和耗时的数据来证明它没问题
```

回到开头那个 4% 使用率的系统：**它的问题不是"第四层"这个数字**，而是玩家在第一层没理由点那个"更多"、进去在九宫格里也认不出哪一格是它——**每一步都要猜**。同样四层，如果每步都有明确指向（比如从战斗结算界面直接跳过去），到达率完全不同。

**注意"常用"这个限定。** 不是所有功能都要浅，是**常用**功能要好走。区分标准就是下一节的矩阵。

### 5.2 用频率 × 重要性给入口分级

这是给主界面做减法的标准工具。把所有入口放进这个矩阵：

```
              ▲ 重要性高
              │
  ┌───────────┼───────────┐
  │  B 区      │  A 区      │
  │ 低频高价值 │ 高频高价值 │
  │ 放二层，   │ 主界面     │
  │ 但要有触发 │ 最显眼处   │
  │ 提醒       │           │
──┼───────────┼───────────┼──→ 频率高
  │  D 区      │  C 区      │
  │ 低频低价值 │ 高频低价值 │
  │ 三层以下   │ 主界面，   │
  │ 或者删掉   │ 但要小、   │
  │           │ 或做成一键 │
  └───────────┼───────────┘
              │
```

四个区各自的处理原则：

| 区 | 特征 | 处理 | 典型错误 |
|---|---|---|---|
| **A：高频高价值** | 核心玩法入口、主要养成入口 | 主界面最显眼的位置，最大 | 被活动 banner 挤到边上 |
| **B：低频高价值** | 赛季结算、公会战报名、剧情 | 放二层，但**在需要的时候主动提醒**（这类入口最依赖红点和推送） | 埋太深，玩家错过了关键节点 |
| **C：高频低价值** | 领日常奖励、签到、免费抽 | 主界面要有，但应该**做成一键批量**而不是十个独立入口 | 每一个都做成一个大按钮，占满主界面 |
| **D：低频低价值** | 设置、图鉴、历史记录、公告 | 三层以下，收进"更多" | 也放在主界面上，因为"负责人觉得重要" |

**C 区是主界面拥堵的最大来源。** 领奖、签到、免费领这类东西频率极高（每天都做）但价值极低（不需要任何决策），团队本能地把它们做得很大很显眼。正确做法是**做成一个"一键领取全部"**，把省下来的空间还给 A 区。

**D 区里那些"负责人觉得重要"的入口是最难砍的，因为砍它是政治问题不是设计问题。** 这时候需要的是数据（入口点击率）和一条明确的入口预算规则（第 3.1 节），而不是争论。

## 6. 手游 UI 的四个层级

手游界面可以分成四层，**每一层有不同的设计规则，混用会出问题**：

| 层 | 是什么 | 特点 | 设计规则 |
|---|---|---|---|
| **1 主界面** | 玩家的"家"，每次登录第一眼 | 常驻、不可关闭 | 回答"我现在该干什么"；入口有硬预算；布局长期稳定不随意改（玩家靠肌肉记忆） |
| **2 系统入口 / 二级页** | 一个玩法或系统的主页 | 可以返回 | 返回路径必须一致；层级尽量浅（要往深处放常用功能，得拿完成率和耗时的数据说话）；空状态要设计 |
| **3 弹窗** | 打断式的信息或选择 | **抢占注意力，代价极高** | 见下方规则；必须排队和限流 |
| **4 红点 / 角标** | 状态提示，不打断 | 廉价但会通胀 | 见第 7 节 |

### 6.1 弹窗的规则

弹窗是界面里最强的武器，也是最容易被滥用的。它的成本是**打断**：玩家正在做的事被强行中止。

**弹窗的三条硬规则：**

1. **弹窗必须是"需要玩家立刻做决定"的时候才用。** 只是通知（"活动开始了"），用非打断的方式（banner、红点、跑马灯）。
2. **弹窗必须排队、限流、有优先级。** 登录时连弹七个窗是最经典的坏体验：前六个玩家都在无脑点关闭，第七个（可能是真正重要的那个）也被顺手关掉。**规则：登录后的连续弹窗不超过 2 个，其余降级为红点或 banner。**
3. **弹窗的关闭方式必须一致且明显。** 有的右上角 X、有的点空白关闭、有的必须点底部按钮，这会让玩家养成"到处乱点"的习惯。

弹窗排队这件事在工程上就是一个优先级队列 + 限流器，实现毫无难度。**但它必须在系统案里被写出来**：每个系统的策划都只关心自己那个弹窗，没有人负责全局的弹窗预算。这个全局规则应该由主策或者 UX 负责人定，写成一份跨系统的规范。

## 7. 红点：一个被用坏的好机制

红点（badge）是手游最有效也最被滥用的一个 UI 机制。值得单独一节，因为**它的设计面主要落在系统策划身上**，UI 只是画个圆点。

### 7.1 红点是什么

从设计上讲，**红点是把系统内部的状态变化推送到入口上的一个信号**。它替代了"玩家必须自己逐个点进去检查"。

从工程上讲（这个类比对你最直接），**红点的最小模型是一棵树**：

```
  主界面
   ├── 角色 ●            ← 子节点有红点，父节点就有
   │    ├── 升级 ●        ← 有角色的升级材料够了
   │    └── 技能 ○
   ├── 任务 ●
   │    ├── 日常 ●        ← 有可领取的奖励
   │    └── 成就 ○
   └── 商店 ○

  规则：父节点红点 = OR(所有子节点红点)
  消除：只有叶子节点的"已读/已处理"事件能消除红点
```

**这是"最小模型"。** 它够你写第一版系统案，但真实项目里至少四个地方会突破它，每一个都要在案子里补掉：

| 突破点 | 现象 | 要补什么 |
|---|---|---|
| **多入口** | 同一个可领奖励能从主界面、任务面板、活动页三处进入 | 结构其实是 **DAG 不是树**。要么指定"主挂载点"，要么允许多挂载但保证跨路径去重 |
| **去重** | 同一件事被算两次（"活动"和"任务"下各亮一个），清了一处另一处还在 | 红点源要有**唯一 id**；父节点聚合去重后的集合，而不是子节点数之和 |
| **状态 vs 事件** | 有的是"发生了一件事"（新邮件），有的是"当前满足某条件"（材料够了） | 两类消除逻辑完全不同，见 7.2 |
| **聚合阈值与权限** | 一个入口下 200 条可领取，角标要不要显示数字？未解锁的子节点该不该让父节点亮？ | 定清楚：角标上限（"99+"）、未解锁不参与聚合、父节点只统计**当前玩家可见**的子节点 |

所以更完整的说法是：**红点是一张（可能多挂载的）聚合图，每个叶子是一个带唯一 id 的红点源，每个源自己是一个小状态机。**

**这个结构必须在系统案里定义清楚，否则会出现两类经典 bug：**

- **消不掉的红点**：某个叶子节点的消除条件没定义（比如"有新邮件"的红点，玩家读了邮件但没删，红点还在）。
- **假红点**：父节点的红点条件被单独写了一套逻辑，和子节点不一致，玩家点进去发现什么都没有。

**这两类问题在玩家眼里都是"这游戏的红点是骗人的"，而一旦玩家形成这个判断，所有红点就同时失效了。**

### 7.2 什么该有红点

红点的判断标准是三条**同时**满足：

| 条件 | 说明 | 反例 |
|---|---|---|
| **玩家一定想处理** | 是真的收益或真的进展，不是运营想让他看的东西 | "新活动上线"不该有红点，它是运营的诉求不是玩家的收益 |
| **处理成本低** | 点进去几秒就能处理完 | "你的战力落后了"不该有红点，玩家没法"处理"它 |
| **处理后一定消失** | 有明确的消除规则，且重复计算的结果一致（幂等） | 找不到消除条件的红点是最坏的 |

按这个标准，红点可以分成三类，**只有前两类该有红点**：

| 类型 | 例子 | 该不该有 |
|---|---|---|
| **可领取**（有东西白拿） | 日常奖励、邮件附件、活动奖励 | **该有**。这是红点最正当的用法 |
| **可操作**（资源够了，能推进一步） | 材料够升级了、有免费抽次数 | **该有**，但它是**状态派生**的：条件成立就亮、条件不再成立就灭，"玩家看过了"不能消除它。见下方 |
| **纯运营**（新活动、商店上新、公告） | 新版本内容、限时礼包 | **不该有**。用 banner、跑马灯、一次性弹窗 |

**两类红点源，两套消除逻辑——这是系统案里最容易漏的一段：**

| 红点源类型 | 触发 | 消除 | 例子 | 写漏了会怎样 |
|---|---|---|---|---|
| **事件型** | 一次性事件发生 | 玩家的一次**确认动作**（读了/领了/点开了）。这个动作要落库、要幂等 | 新邮件、新解锁的角色、赛季结算通知 | 只记在本地 → 换设备又冒出来；没定义确认动作 → 永远消不掉 |
| **状态型** | 某个条件**当前**成立 | 条件不再成立时**自动**消除，不需要玩家确认 | 材料够升级、有免费抽次数 | 误当成事件型做了"已读" → 玩家看过一次后，材料再次够了也不亮，红点永久失效 |

**注意："资源不足"是状态不是事件。** 所以"材料够了"这类红点的正确实现是**每次查询时重新计算当前条件**，而不是在"材料变够"那一刻写一条待处理记录。写成事件会同时产生两个 bug：材料花掉了红点还在，以及玩家点开过之后再也不亮。

**还有一个中间态必须显式定义：已确认但条件仍成立。** 玩家点进"免费抽"看了没抽，红点该不该灭？这是设计决定不是实现细节：**灭**（要定义重新点亮的时机，比如跨天）或**不灭**（代价是持续打扰）。**案子里不写，不同系统会各选一个。**

### 7.3 红点疲劳

**红点疲劳（badge fatigue）的机制很简单：当界面上永远有红点、且玩家永远清不完的时候，红点从"有新东西"退化成了界面装饰，玩家不再看它。**

一旦到了这一步，红点这个机制就永久失效了，你再也无法用它通知玩家任何重要的事。而 B 区（低频高价值）的那些入口正是最依赖红点的 —— 赛季结算、公会战报名，这些错过了就真错过了。**红点通胀的最终受害者是最重要的那些提示。**

防止通胀的规则：

1. **红点必须能被清空。** 至少要保证：玩家把该做的事都做完之后，界面是干净的。注意状态型红点会让这一点变难（材料够了但玩家就是不想升，红点会一直在），所以这类要么允许玩家手动忽略，要么只在"新变得可操作"的那段时间里亮。如果你的游戏在任何时刻都不可能红点全清，说明红点已经被滥用了。
2. **给红点分级。** 至少两级：普通红点（小圆点）和强提示（数字角标 / 带感叹号 / 会呼吸）。强提示的数量要有硬上限。
3. **纯运营诉求不许用红点。** 这条要写进规范，否则每次活动都会有人来要一个。
4. **提供"关闭某类红点"的设置。** 深度玩家会感激你。

**手游对照，买断制里的红点**：几乎没有。《哈迪斯》《杀戮尖塔》里没有一个红点。原因不是它们更克制，而是**它们不需要把玩家从"离开状态"拉回来**。红点本质上是留存工具，它属于 F2P 的工具箱。理解这一点，你就能判断什么时候该用它、什么时候只是在污染界面。

## 8. 主界面是一个目标生成器

[第 08 章](./08-goals-progression-rewards.md)讲过"养成系统是目标生成器"。到了界面这一层，这句话变成：

> **主界面唯一的职责，是在 3 秒内回答玩家的一个问题："我现在该干什么？"**

一个玩家打开游戏，他的心理状态是空的。主界面要在他形成"好像没什么可做的"这个念头之前，给他一个明确的下一步。做不到这一点的主界面，无论多好看都是失败的。

界面上生成目标的手段有三种，**它们互相竞争，同时全开等于全关**：

| 手段 | 心理机制 | 例子 | 滥用的后果 |
|---|---|---|---|
| **进度条** | 未完成的东西让人不适（接近完成时最强） | 经验条差一点满、活动进度 8/10 | 满屏进度条会让玩家感到永远做不完 |
| **红点 / 角标** | 未读信息的处理冲动 | 可领奖励 | 见第 7.3 节 |
| **倒计时** | 损失厌恶 | 限时活动还剩 2 小时 | 满屏倒计时制造焦虑，玩家的应对方式是**关掉游戏** |

**注意最后一格。** 手游最常见的一个误判是"制造紧迫感能提升活跃"。少量的紧迫感能，**过量的紧迫感会让玩家整体退出，因为退出是消除焦虑最有效的方式**。这是[第 21 章](./21-monetization-design.md)黑暗模式话题的界面版本。

一个可用的主界面自检：**让一个玩了三天的玩家打开主界面，问他"你现在最想点哪个"**。如果他答不出来，或者答的是"不知道，看看有什么红点"，主界面就没有在生成目标，只是在展示系统。

## 9. 贯穿案例：一个手游主界面的信息架构走查

**说明**：下面用一个**示意性的主界面**做走查——它不是任何一款游戏的截图，而是把常见卡牌 / 塔防手游主界面的共同结构抽出来的复合例子。这样做是有意的：入口的命名、数量和位置随版本变动极快，"某游戏第 N 个入口在左侧第几格"这类描述几个月就失效，而**结构性的问题不会**。你要学的是这套走查方法，然后拿它去走你手上那一版的真实界面——**一切以你手上版本的实际界面为准**。下面关于设计意图的判断一律【推导】。

### 9.1 结构描述（事实层）

假设某手游的主界面大致是这样：

```
 ┌──────────────────────────────────────────────────┐
 │ [资源条：体力 / 软通货 / 硬通货]      [邮件][公告] │  ← 顶部状态区
 ├────────────┬─────────────────────────────────────┤
 │            │                                      │
 │ ▓▓▓▓▓▓▓▓▓  │                                      │
 │ ▓ 战斗    ▓ │          角色 / 场景展示区           │  ← 左侧主入口列
 │ ▓▓▓▓▓▓▓▓▓  │        （可点击互动，无功能）          │     + 中右侧展示区
 │ ┌────────┐ │                                      │
 │ │ 产出   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 抽卡   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 角色   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 商店   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 背包   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 任务   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 社交   │ │                                      │
 │ ├────────┤ │                                      │
 │ │ 图鉴   │ │                                      │
 │ └────────┘ │                                      │
 ├────────────┴─────────────────────────────────────┤
 │ [活动 banner]                            [设置]  │
 └──────────────────────────────────────────────────┘
```

几件值得先记下来的事（在很多手游上都成立）：

- **主入口是一列带文字的纵向列表，不是纯图标九宫格**——有文字就绕开了第 4 节末尾那个"去掉文字还认得出几个"的问题。
- **"战斗"入口面积明显大于其他**，是唯一的一级视觉重点。
- 面积最大的一块给了**没有直接功能的展示区**。
- 层级很浅：核心操作点两到三下能到。

### 9.2 频率 × 重要性分析（判断层）

把入口逐个放进第 5.2 节的矩阵。**下面这一列频率是示意值**；你自己走查时，这一列必须填你的真实使用数据（或者更好：埋点数据）。

| 入口 | 使用频率（示意） | 重要性 | 当前位置 | 评价【推导】 |
|---|---|---|---|---|
| 战斗 | 每次登录必用 | 核心 | 一层，最大 | **[好]** A 区，位置正确 |
| 产出（资源产出玩法） | 每天 2~4 次 | 高（主要资源来源） | 一层 | **[好]** A 区，正确 |
| 角色（编队 / 养成） | 每天 1 次 | 高 | 一层 | **[好]** A 区 |
| 任务 | 每天 1 次（只为领奖） | 低（无决策） | 一层 | **[待改]** **典型 C 区**：高频零决策，理想形态是"一键领取"而不是独立入口 |
| 抽卡 / 商店 | 每天 1~3 次 / 每周 1~2 次 | 中 | 一层 | **[待改]** 偏 C 区，可合并或下沉 |
| 背包 / 社交 | 每天 0~1 次 | 低~中 | 一层 | **[待改]** 多为被动查看，真正需要它们的时刻在别的流程里（见错位一） |
| 图鉴 / 档案 | 极低 | **如果叙事是这款游戏的差异化，就是高价值** | 一层最下 | **[风险]** 典型 B 区，见错位二 |
| 设置 | 极低 | 低 | 二层 | **[好]** D 区，正确 |

### 9.3 三类常见的层级错位【推导】

这三类不是某款游戏的三个 bug，是**手游主界面上反复出现的三种结构性错位**。走查你自己那款游戏时先找这三类。

**错位一：按"数据实体"组织入口，而不是按"玩家的任务"组织。** 典型症状是：**玩家真正需要某个东西的那一刻，他不在那个东西的入口里。**

几乎所有养成手游都有的例子：玩家在**角色升级界面**发现材料不够。他此刻的任务是"去把材料弄到手"，界面却只说"材料不足"，他得自己退出去、回想这材料在哪掉落、再点进去。**正确做法是在缺口处直接给跳转。** 这和第 12 节"第一步"那份问题清单是同一件事。

同类变体很多，判断方法都一样——**问"这个功能被需要的时刻，玩家在哪个界面"**：

| 功能 | 被需要的时刻 | 错位的做法 | 内嵌的做法 |
|---|---|---|---|
| 查材料获取途径 | 养成界面发现缺料时 | 只提示"材料不足" | 点缺失材料 → 获取途径 → 跳转 |
| 借用他人的助战单位 | 为某一关编队时 | 要求先退出编队、去社交界面、再回来 | **直接在编队流程里给出助战选择位**——多数塔防 / 卡牌手游已经这么做，这是内嵌做对了的样子 |
| 查关卡敌人属性与克制 | 编队选阵容时 | 只能在关卡详情页看，编队时靠记 | 编队界面直接显示本关敌人构成（"识别优于回忆"） |
| 补充体力 | 体力不足挡住操作时 | 弹一句"体力不足"就结束 | 就地给出恢复途径与代价 |

**这类错位极其普遍，原因很清楚：入口清单往往是从系统清单直接翻译过来的。** 有"好友系统"就给一个"好友"入口，有"背包系统"就给一个"背包"入口。**系统清单按数据实体组织，玩家的脑子按任务组织。**

**但不要一刀切**：实体入口本身没错——玩家确实会有"我想管理一下好友"这种任务。**错的是只有实体入口、没有任务发生处的内嵌。** 两者应该并存。

**错位二：B 区（低频高价值）功能按频率被下沉，且没有任何主动触达。**

叙事内容（剧情回顾、角色档案）最典型：频率确实低，按频率排就该下沉；但如果叙事是这款游戏的差异化卖点，它的价值极高。**B 区的正确处理不是"往上提"，而是"放在合理位置 + 在合适的时机主动触达"**——打完一章主线后主动提示"本章剧情已解锁回顾"，比把入口做大有效得多。同类的还有赛季结算、公会战报名：**这些错过了就是真错过了，它们才是最依赖红点和推送的入口**（第 7.3 节说的"红点通胀的最终受害者"就是这一类）。

**错位三：屏幕面积最大的一块给了没有直接功能的展示区。**

从纯效率的角度这是"浪费"。但要给一个不同的判断：**这块面积买的不是功能，是"这是一个有角色的世界"这件事。** 界面不只服务可用性，也服务 engage-ability（第 2 节的第二根支柱）。**这是设计取舍不是错误——但它必须是被有意识做出来的取舍，而不是"因为立绘好看就放上去了"。**【推导】

判断方法：**把这块面积换成三个功能入口，体验会更好还是更差？** 对一款卖角色的二次元游戏多半更差，它的核心卖点里有很大一块就是角色本身；对纯数值向的 SLG 就很难成立——那里玩家打开游戏是来处理事务的，换成"待处理事项"价值高得多。**同一个设计，在不同的付费标的下答案不同**（和[第 12 章](./12-narrative.md)第 9.3 节"叙事投入取决于付费标的"是同一个逻辑）。

### 9.4 对照：《杀戮尖塔》和《哈迪斯》的极简界面

**《杀戮尖塔》** 的战斗界面上只有：手牌、能量点数、抽牌堆/弃牌堆的数量、遗物栏、药水栏、玩家血量护甲、敌人血量护甲，以及**敌人头顶的意图图标（intent）**。

意图图标是这个界面最值得学的一处设计：**敌人下一回合要做什么，直接画在它头上** —— 一把剑加数字"12"表示它下回合攻击 12 点，一个盾表示它要加护甲，一个箭头表示它要给自己加 buff。

它的设计意义远超"方便"：

> **同样一套战斗规则，显示 intent 和不显示 intent 是两个不同的游戏。** 不显示，玩家要靠记住每种敌人的行动模式来玩，这游戏考的是**记忆**；显示了，所有信息都摆在桌面上，这游戏考的是**基于完全信息的决策**。

这是本章最重要的一个例子，因为它证明了：**UI 不是玩法的外壳，UI 决定了玩法考验玩家的哪一种能力。**（Mega Crit 的 Anthony Giovannetti 在 GDC 2019 的演讲 *Slay the Spire: Metrics Driven Design and Balance* 里分享过他们用数据驱动平衡的做法【实证】；上面这段关于 intent 设计意图的分析是本课程的【推导】。）

**《哈迪斯》** 值得学的是另一处：**它把"选择"放在了空间里，而不是菜单里。** 房间的门上直接画着下一个房间会给什么奖励（血、金币、能力），玩家在走向门的过程中就完成了决策，不需要打开任何界面。

这两个例子对手游的启发不是"要做得一样简"（手游的系统数量决定了它做不到），而是两条可迁移的原则：

1. **把决策需要的信息全部前置到决策发生的地方。** 玩家在编队界面做决策，那么关卡的敌人属性、克制关系就应该在编队界面能看到，而不是要求他记住上一个界面看到的东西（第 2.1 节的"识别优于回忆"）。
2. **能放进世界/流程里的信息，就不要放进菜单里。**

## 10. 反面案例清单

评审界面需求时逐条对照：

| 反面案例 | 症状 | 根因 | 修法 |
|---|---|---|---|
| **弹窗轰炸** | 登录后连弹 5~8 个窗 | 没有全局弹窗预算和优先级队列 | 登录弹窗上限 2 个，其余降级；建一个跨系统的弹窗优先级规范 |
| **入口过深 / 路径难走** | 常用功能的任务完成率低、首次耗时长、中途走错多 | 入口按系统清单排，没做频率×重要性分级；路径上每一步都要玩家猜 | 画信息架构图、做矩阵分级；用完成率和耗时验证，而不是数点击次数 |
| **图标无法识别** | 十个图标风格一致，靠位置记忆 | UI 追求视觉统一，牺牲了辨识度 | 去掉文字自测；让图标在**形状轮廓**上就有差异 |
| **状态不可见** | 玩家不知道自己今天做没做过某事、某个东西有没有满 | 只显示"能做什么"，不显示"当前状态" | 每个入口显示进度（3/5）而不只是名字 |
| **反馈延迟或缺失** | 点了没反应，玩家连点三次，触发三次请求 | 网络请求期间没有本地即时反馈 | 点击 100ms 内必须有可见反馈（按下态、loading）；按钮请求期间置灰 |
| **破坏性操作无确认** | 一键卖掉了想留的东西 | 只想着效率 | 不可逆操作必须二次确认 + 显示"将失去什么"；**但要注意别走到另一个极端**（什么都要确认，玩家会形成无脑点确认的习惯，反而更危险） |
| **数字没有量级** | 显示 `1234567` | 直接把服务端字段贴上去 | 按量级格式化（123.5万）；同一游戏内格式统一 |
| **极值没设计** | 名字太长撑破布局、数字太大超出框、列表为空时一片空白 | 只按"正常情况"给了 UI 稿 | 界面需求必须写**空状态、极值状态、加载中、错误状态** |
| **一个功能多个入口且行为不一致** | 从 A 进和从 B 进看到的东西不一样 | 不同版本不同人加的 | 收敛入口；确实需要多入口的，行为必须完全一致 |
| **返回路径不一致** | 有的地方返回上一级，有的直接回主界面 | 没有统一的导航规范 | 定死规则：返回永远回上一级；回主界面用独立的"主页"按钮 |

**这份清单里有七条是"没有全局负责人"造成的。** 弹窗预算、入口预算、导航规范、图标规范、数字格式 —— 每一条单独看都很简单，但没有人被指定负责，就一定会失控。**在你成为主策之前，先做那个提出"我们需要一份界面规范"的人。**

## 11. 策划、UE、UI 的分工

这是本章最需要写清楚的一件事，因为它是团队冲突的高发区。

| 角色 | 决定什么 | 产出物 | **不该决定什么** |
|---|---|---|---|
| **系统策划** | **信息清单与优先级**、玩家的任务流程、状态与规则、哪些操作需要强反馈。**信息架构和 UX/UE 共同定，但频率、重要性、使用场景这三个输入必须由他给** | 系统案第 2 节、信息清单（带优先级）、流程图、**丑的线框草图** | 具体布局、控件样式、配色、字体、动效风格；也不该单方面拍板信息架构 |
| **UE / 交互设计师**（有专职 UX 的团队里，信息架构常由 UX 主导） | 交互流程、控件选择、手势、状态转换、界面层级的落地形态、动效逻辑 | 交互稿 / 可点原型 | 玩法规则、信息的优先级 |
| **UI 设计师** | 视觉层级、配色、图标、字号、氛围、资源规范 | 视觉稿、切图与规范 | 信息架构、哪些信息该出现 |
| **程序** | 实现方案、性能、多分辨率适配 | | 上述任何一项（但有否决权：说清楚什么代价太高） |

### 11.1 最常见的三种冲突和处理

**冲突一：策划画了一版界面草图，UI 说"这个布局不好看"。**

处理：**策划的草图只承诺"有哪些信息、优先级是什么"，不承诺布局。** 交草图的时候就要明说这句话，否则 UI 会把它当成设计稿来反驳，双方吵的是两件事。一个好习惯是**故意把草图画丑**（手绘、方框、不上色），用形式明确它的性质。

**冲突二：UI 为了视觉统一，把三个不同重要性的入口做成了一样大。**

处理：这是**信息优先级被视觉统一覆盖**了，属于策划该守住的边界。提意见的正确方式不是"这个不好看"，而是"这三个入口的使用频率是 10:3:1，视觉权重应该体现这个差异"。**用数据和优先级说话，不要用审美说话** —— 审美你辩不过 UI，优先级他辩不过你。

**冲突三：交互设计师改了策划设计的流程，理由是"这样点击次数更少"。**

处理：多数时候应该接受，交互是他的专业。**但有一类不能接受：改动减少了玩家做决策的停顿。** 有些"多余"的一步是设计上刻意的（比如抽卡前的确认、不可逆操作的预览），把它优化掉会破坏体验。这时候策划要说清楚"这一步的设计目的是什么"，而不是说"我就要这么做"。

## 12. 怎么写界面需求

系统案模板 `templates/system-spec.md` 的第 2 节（玩家视角的流程）就是界面需求的位置。多数策划这一节写得最差，因为不知道该写什么。下面是可以直接照做的七步。

**第一步：写"玩家在这个界面要回答的问题"清单，而不是"要显示什么字段"。**

这一步的顺序至关重要。字段清单是从系统出发的，问题清单是从玩家出发的。举例，一个角色养成界面：

| **[差]** 字段清单（错误起点） | **[好]** 问题清单（正确起点） |
|---|---|
| 显示：等级、经验、攻击、防御、生命、技能等级、突破材料、装备槽 | 1. 我现在能不能升级？<br>2. 如果不能，缺什么、去哪拿？<br>3. 升了之后会变强多少？<br>4. 这个角色值不值得练（和我别的角色比）？<br>5. 我练完之后能打哪一关？ |

问题清单会直接暴露出字段清单的漏洞：上面那份字段清单**回答不了第 2、3、5 题** —— 缺"材料在哪里获取"的跳转、缺"升级后属性变化的预览"、缺"和关卡需求的关联"。**这三条恰恰是玩家最需要、也最常被漏掉的信息。**

**第二步：给每条信息标优先级。** P0（不看就没法做决定）/ P1（帮助做更好的决定）/ P2（锦上添花）。这是给 UI 的视觉权重依据。**没有优先级的信息清单会被 UI 平均处理，结果就是重要信息被淹没。**

**第三步：画流程图，不是界面图。** 玩家从哪个界面来 → 在这里做什么 → 去哪。特别要标出**决策点**在哪一步。

**第四步：画线框草图。** 丑的、手绘的、只有方框和文字。目的是表达"哪块大哪块小、什么在一起"。交付时明说这是信息优先级不是布局。

**第五步：列出所有状态。** 这是策划最常漏、程序最痛恨的一节：

| 状态 | 例子 | 漏掉的后果 |
|---|---|---|
| **空状态** | 好友列表一个人都没有、背包空的、还没有任何角色 | 玩家看到一片空白，以为坏了。**空状态是新手一定会遇到的状态** |
| **加载中** | 请求未返回 | 玩家连点 |
| **错误** | 网络失败、条件不满足 | 玩家不知道发生了什么 |
| **极值** | 名字 20 个字、数字 10 位、列表 999 条 | 布局撑破 |
| **权限 / 条件不满足** | 等级不够、未解锁 | 要写清楚是"隐藏"还是"置灰"（第 18 章第 8 节讨论过这个选择） |

**第六步：写反馈要求。** 哪些操作必须有强反馈（[第 13 章](./13-game-feel-and-feedback.md)的三层反馈）。至少写清楚：成功的反馈、失败的反馈、以及不可逆操作的确认方式。

**第七步：写埋点。** 界面的最小埋点集：

| 事件 | 回答什么问题 |
|---|---|
| 界面进入（带来源） | 玩家从哪个入口进来的、哪个入口是主要来源 |
| 界面停留时长 | 是不是有人进来就走（看不懂） |
| 界面内各按钮点击 | 哪些功能根本没人用 |
| 界面退出（带退出时的状态） | 玩家是完成了任务才走的，还是放弃了 |

有了第一和第四条，开头那个 4% 使用率的系统就能被诊断出来：**是没人进来（入口问题），还是进来了就走（界面问题）。** 这两种问题的解法完全不同，没有埋点就只能靠开会猜。

## 13. 常见误区

| 误区 | 为什么错 | 正确的想法 |
|---|---|---|
| "UX 就是把界面做好看" | 好看是 UI 的事；UX 是"玩家能不能顺利地用、愿不愿意投入" | UX 有两根支柱：可用性（可判定对错）和吸引力（只能判定强弱） |
| "我觉得这个界面很清楚" | 你知道答案，所以你永远体验不到"找不到" | 设计者无法评价自己的界面，必须找不知道的人试 |
| "信息架构是 UI 的活"（或者反过来，"信息架构完全是策划说了算"） | UI 决定长什么样；但信息架构是策划、UX、UI/UE 共同的产物，只有策划掌握频率和重要性这两个输入 | 策划必须交出带优先级的信息清单和任务流程（系统案第 2 节），架构本身和 UX/UE 共同定 |
| "入口都放主界面上，玩家才找得到" | 主界面面积是最贵的资源，全放上去等于全都不显眼 | 用频率×重要性矩阵分级；给主界面设硬入口预算 |
| "加个红点就有人用了" | 红点会通胀，通胀之后所有红点一起失效 | 红点三条件：一定想处理、成本低、处理后必然消失；分清事件型和状态型的消除逻辑；纯运营诉求不许用红点 |
| "多做点倒计时能提升活跃" | 少量紧迫感有效，过量紧迫感让玩家用"关掉游戏"来消除焦虑 | 三种目标生成手段（进度条/红点/倒计时）要控总量 |
| "界面需求就是列出要显示的字段" | 字段清单从系统出发，会漏掉玩家真正需要的信息 | 先写"玩家在这里要回答哪些问题"，再倒推字段 |
| "空状态、极值这些程序自己看着办" | 这些是设计决定，不是实现细节；而且空状态是新手必经的状态 | 界面需求必须写全五种状态 |
| "点击次数越少越好"／"常用功能不能超过三次点击" | 点击次数本身不预测放弃；有些停顿还是刻意设计的（确认、预览、决策的呼吸感） | 用任务完成率、耗时、走错次数衡量；减少无意义的点击，保留承载决策的那一步 |
| "极简界面更好" | 极简是手段不是目标；系统数量决定了手游做不到杀戮尖塔那样简 | 目标是"每个信息都在它该出现的地方"，不是"信息越少越好" |

## 14. 动手

### 14.1 拆解：一款手游主界面的信息架构

选一款你玩了至少一周的手游，**打开它、按当前版本的实际界面走查**（第 9 节那个示意界面只是方法演示，不要拿它当答案）。用 [templates/deconstruction.md](./templates/deconstruction.md)，回答：

1. 画出主界面的结构草图（ASCII 或手绘拍照），标出所有可点击的区域。
2. 把主界面上的入口全部列出来（包括角标、banner、跑马灯）。总共几个？
3. 对每个入口填三列：**你过去一周的实际使用次数**（凭记忆估，不许美化）、你认为的重要性（高/中/低）、当前所处的层级。
4. 把它们画进第 5.2 节的频率×重要性矩阵。A/B/C/D 四个区各有几个？
5. **找出至少三处层级错位**，每处写清楚：现状、为什么是错位、应该在哪。至少有一处必须是"按数据实体组织而不是按玩家任务组织"这一类的错误（第 9.3 节错位一那种）。
6. 找一个没玩过这款游戏的人，给他三个任务（对应你最常用的三个功能），**不给任何提示**，记录四件事：有没有独立完成、各花多少秒、中途点错或返回几次、从哪一步开始犹豫。点击次数只作参考，这四个数才是结论。
7. 统计红点：登录后主界面上有几个红点？其中几个属于"可领取"、几个"可操作"、几个"纯运营"？逐个判断它是**事件型**还是**状态型**（第 7.2 节），并检查有没有同一件事在两个入口下各亮一次。你能把它们全部清空吗？（真的去试一次。）
8. 登录后连续弹出几个弹窗？你读了第几个？
9. 这个界面在 3 秒内回答了"我现在该干什么"吗？它用的是进度条、红点还是倒计时？三种各有多少个？
10. 【推导】这个主界面上占面积最大的、但没有功能的区域是什么？它买到了什么？这个取舍成立吗？

### 14.2 写作：信息架构图 + 一版重组方案

**题目**：给 14.1 里那款手游的主界面，画一张信息架构图，并提出一版重组方案。

**第一部分：信息架构图。** 用缩进列表或 ASCII 树画出从主界面到第三层的完整结构，标注每个节点的**频率**和**重要性**。格式参考：

```
主界面
├── [A] 主线关卡        频率:每次  重要性:核心   层级:1
│   ├── 章节选择                                层级:2
│   └── 关卡详情 → 编队 → 开始                 层级:3,4  **[风险]** 编队时看不到敌人属性
├── [C] 日常任务        频率:每天  重要性:低     层级:1
...
```

**第二部分：重组方案。** 要求：

- 给出**重组后的信息架构图**，格式同上。
- **必须遵守硬约束**：主界面第一层入口数量必须比现在少至少 3 个；每一个 A 区功能都要写出**验收指标的目标值**（新玩家任务完成率、首次完成耗时、走错次数各定一个目标），并说明你打算怎么测。**不许用"点击次数不超过三次"作为验收标准。**
- 每一处改动写清楚三件事：**改什么、为什么（用本章的概念）、代价是什么**。代价那一栏不许写"没有代价" —— 每一次下沉都会降低那个功能的使用率，你要说清楚你愿意牺牲谁。
- 至少包含以下四类改动各一处：
  1. 一处**合并**（把多个 C 区入口合成一键操作）
  2. 一处**下沉**（把低频入口移到二层以下）
  3. 一处**流程内嵌**（把一个独立入口塞进它真正被需要的流程里，如第 9.3 节错位一里"材料不够时的就地跳转"）
  4. 一处**主动触达**（一个 B 区低频高价值功能，不提升层级，改用时机性提醒）
- 附一份**红点规范**：列出重组后哪些入口允许有红点，每个红点标明**它是事件型还是状态型**，并写成"触发：… / 消除：…"的形式（事件型要给出幂等的确认动作，状态型要给出重新计算的条件）；再说明多入口时怎么去重、"已确认但条件仍成立"这个中间态你选哪种处理。
- 附一份**弹窗优先级表**：登录后可能出现的所有弹窗，按优先级排序，说明前 2 个是哪两个、其余怎么降级。

放进 `notes/作业/19-信息架构-xxx.md`。这份作业在[第 29 章](./29-end-to-end-lab.md)会作为你那款游戏的界面方案基础。

### 14.3 思考题

1. 第 9.4 节说"显示 intent 和不显示 intent 是两个不同的游戏"。在你玩的手游里，找一处**同类的 UI 决定** —— 某个信息是显示还是隐藏，直接改变了这个玩法考验玩家的哪种能力。如果把它反过来（隐藏的显示出来，或反之），游戏会变成什么样？
2. 红点是 F2P 的留存工具，买断制游戏几乎不用。那么：一款**买断制单机游戏**如果加入红点，会带来什么好处和什么代价？你能想出一种它成立的情况吗？
3. 第 11 节说策划应该"故意把草图画丑"。这个做法背后的原理是什么？你在写服务端接口文档时，有没有一个功能类似的习惯？
