# 03 - 设计哲学：一条公理，五个推论

> 本章目标：把整个 borrow checker 压缩成**一条可以背下来的公理**，并从它推导出五个推论。
> 学完这章，你应该能对着任何一个借用错误说出："它在保护公理的哪一半"。
> 这是全课程**信息密度最高**的一章，建议读两遍。
> 预计用时：2 小时。

## 1. 公理

> ## **Aliasing XOR Mutability**
> ### 对任意一份数据，在任意一个程序点上：
> ### **要么它可以被多处访问（但没人能改它），要么它可以被改（但只有一处能访问它）。**
> ### 二者不可兼得。

Rust 用类型系统机械地执行这条公理：

| | 别名（多条访问路径） | 可变（能写） |
|---|---|---|
| `&T` | ✅ 任意多个 | ❌ |
| `&mut T` | ❌ 恰好一个 | ✅ |
| `T`（拥有） | ❌ 恰好一个所有者 | ✅ |

**没有第四种组合。** 整个借用检查器就是在证明"程序的每个点上，这张表没有被违反"。

> **命名的历史遗留问题**：`&mut T` 的正确读法**不是**"可变引用"，而是**"独占引用"**（exclusive reference）。
> `&T` 的正确读法不是"不可变引用"，而是**"共享引用"**（shared reference）。
> Rust 社区多年来一直想改这个名字（RFC 曾提议 `&uniq`/`&shr`），但兼容性成本太高。
> 你在读 rustc 源码和 RFC 时会看到 `Mutability::Mut` 和 `BorrowKind::Unique` 并存——
> **请在心里把 `&mut` 念成"独占"**，很多困惑会当场消失（比如"为什么 `&Cell<T>` 能改数据"——
> 因为规则从来不是关于"可变"的，是关于"独占"的）。

## 2. 为什么是这一条？——局部推理

公理本身不难理解。真正的问题是：**为什么这条规则能换来内存安全？**

答案是四个字：**局部推理（local reasoning）**。

### 2.1 局部推理是什么

看这个函数：

```rust
fn process(data: &mut Vec<i32>, config: &Config) {
    let len = data.len();
    helper(config);              // ← 这里会不会改 data？
    data.truncate(len - 1);      // 我能假设 len 还有效吗？
}
```

**在 Rust 里，答案是确定的**：`helper(config)` 绝对不可能改 `data`。
因为你手上有 `&mut data`（独占），所以在这个借用活着的期间，
**宇宙中不存在第二条访问 `data` 的路径**——`helper` 不可能拿到它。

对比 C++：

```cpp
void process(std::vector<int>& data, const Config& config) {
    size_t len = data.size();
    helper(config);              // config 里可能藏着一个 data 的指针！
    data.resize(len - 1);        // len 可能已经失效
}
```

C++ 里你**必须读 `helper` 的实现**才能回答这个问题。而 `helper` 又调用别的函数……
最终你需要读整个程序。**这就是"非局部推理"的成本，它随程序规模超线性增长。**

对比 Go：

```go
func process(data []int, config *Config) {
    n := len(data)
    helper(config)               // config 里可能存了 data 的切片
    data = data[:n-1]
}
```

Go 和 C++ 一样：**没有任何类型信息告诉你 `config` 里有没有藏着 `data` 的别名**。
你靠的是"应该不会吧"和 code review。

### 2.2 局部推理的三个受益者

| 受益者 | 具体好处 |
|---|---|
| **你（读代码的人）** | 看函数签名就知道它能碰什么、不能碰什么。不用读实现 |
| **编译器（优化器）** | `&mut T` 天然是 `noalias`，LLVM 可以做 C 里只有 `restrict` 才敢做的优化 |
| **借用检查器自己** | **每个函数可以独立检查**。这是 Rust 能做全局内存安全但只做函数级分析的原因 |

第三条尤其关键。**borrow checker 从不跨函数分析**——它只看函数签名。
所以第 14 章那些 problem case 的根源都是"签名表达能力不够"，而不是"分析算法不够聪明"。

### 2.3 一个立即可用的推论

> **当你看到一个借用错误时，先看函数签名，别急着看函数体。**
>
> 90% 的借用错误可以从签名层面解释：
> - "这个函数借了整个 `self`，但我只需要一个字段" → 签名表达力问题（第 12 章）
> - "这个函数返回的引用绑定到了参数的生命周期" → 省略规则的结果（第 06 章）
> - "闭包捕获了 `&mut`，但我还想在外面用" → 捕获也是一种签名（第 12 章）

## 3. 推论一：所有权 = 谁负责 drop

公理说"可变必须独占"。**销毁是最彻底的可变**（第 01 章第 2 节）。
所以：**每份数据必须有且仅有一个所有者，销毁的责任归它。**

这一条推论直接消灭了：
- double free（不可能有两个所有者）
- use-after-free（销毁前必须证明没有引用还活着）
- 内存泄漏中的"忘了 free"那一类（作用域结束自动 drop）

**并且它是零开销的**：没有引用计数，没有 GC，`drop` 的调用点在编译期就确定了。

> **Go 对照**：Go 的 `defer f.Close()` 是所有权的手工版本——你用纪律保证"谁打开谁关闭"。
> Rust 的 `Drop` 把这条纪律变成类型规则。所以 Rust 里没有 `defer`——**不需要**。

## 4. 推论二：生命周期 = 借用有效性的证明

公理里有"在任意一个程序点上"这句话。要检查它，编译器必须知道
**每个借用在哪些程序点上是活的**。

这就是生命周期的全部作用：**它不是"数据活多久"，是"借用在哪些点有效"的证明载体**。

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str
```

这个签名在说：**"我返回的引用，其有效点集不超过 `a` 和 `b` 有效点集的交集。"**
它是一个**契约**，调用方和实现方各自独立地验证自己那一半——又是局部推理。

**关键认知（第 06 章展开）**：
- 生命周期标注**不改变**任何运行时行为，它不延长也不缩短任何东西的存活
- 它只是**把一个约束写进签名**，让编译器能在调用点检查
- 所以"加个 `'static` 让它编译过"通常是错的——你不是在延长数据寿命，你是在**要求**数据永生

## 5. 推论三：并发安全是免费的

这是 Rust 最漂亮的一步棋，值得单独讲。

**数据竞争的定义**：两个线程并发访问同一内存，至少一个是写，且没有同步。

把它和公理对照：

```
数据竞争 = 别名（两个线程都能访问） + 可变（至少一个在写）
         = 违反 Aliasing XOR Mutability
```

**它们是同一件事。**

所以 Rust **不需要为并发安全设计任何新机制**——只需要保证借用规则在跨线程时仍然成立。
这就是 `Send` / `Sync` 两个 auto trait 的全部内容（第 22 章）：

| trait | 含义 | 一句话 |
|---|---|---|
| `Send` | 可以把**所有权**移到另一个线程 | "这东西换个线程用是安全的" |
| `Sync` | 可以把 `&T` 给另一个线程 | 等价于 `&T: Send` |

`Rc<T>` 不是 `Send`，因为它的引用计数是非原子的——两个线程同时改计数就是数据竞争。
`Arc<T>` 是 `Send`，因为它用原子操作。**这不是特例规则，是同一条公理的直接应用。**

> **这就是"无畏并发（fearless concurrency）"这个口号的真实含义**：
> 不是"Rust 有很棒的并发库"，而是"**并发安全是内存安全的一个免费副产品**"。
>
> 反过来说：如果一门语言没有别名控制，它就不可能静态保证无数据竞争——
> Go 只能提供 `-race`（运行时抽样检测，会漏），Java 只能提供 `synchronized`（靠你记得用）。

## 6. 推论四：soundness > completeness（宁可错杀）

### 6.1 不可判定性

判定"一个程序在运行时是否违反公理"是**不可判定**的：

```rust
let i = complicated_computation();      // 编译期不可知
let a = &mut v[i];
let b = &mut v[j];                      // i == j 吗？
```

要回答这个问题，编译器得能算出 `complicated_computation()` 的结果——等价于停机问题。

所以任何静态检查器必须在两条里选一条：

|  | 定义 | 后果 |
|---|---|---|
| **unsound（不健全）** | 可能接受违反公理的程序 | 安全承诺作废，整个系统失去意义 |
| **incomplete（不完备）** | 可能拒绝不违反公理的程序 | 有些正确代码写不出来，用户骂街 |

**Rust 坚定地选了 incomplete。** 这不是妥协，是**唯一可能的选择**——
因为 unsound 意味着 `unsafe` 之外的代码也可能有 UB，那 Rust 就什么都不是了。

### 6.2 这条选择解释了你 90% 的痛苦

```rust
// 运行时百分之百安全，但编译器拒绝（lab/13）
fn f(v: &mut Vec<i32>) { let a = &mut v[0]; let b = &mut v[1]; *a += *b; }
```

编译器不知道 `0 != 1` 吗？知道。但 `Index`/`IndexMut` 是**普通的 trait 方法**，
签名是 `fn index_mut(&mut self, i: usize) -> &mut T`——它借了**整个** `self`。
编译器只看签名（局部推理，第 2.2 节），签名里没有"我只碰第 i 个元素"这个信息。

**正确的解法不是抱怨，是给编译器提供它缺的那个信息**：

```rust
fn f(v: &mut Vec<i32>) { let (l, r) = v.split_at_mut(1); l[0] += r[0]; }
```

`split_at_mut` 的签名是 `fn split_at_mut(&mut self, mid: usize) -> (&mut [T], &mut [T])`——
**它在类型层面声明了"我把独占权分成了两份不相交的"**。
它的实现内部用了 `unsafe`，但它把"这两半确实不相交"这个证明**封装成了一个安全 API**。

> ### 这是整个 Rust 生态的核心工作模式
> **少量 `unsafe` 代码，把编译器无法推导的不变量证明一次，然后包装成安全 API 供所有人使用。**
>
> `Vec`、`split_at_mut`、`Cell`、`Mutex`、`Rc` 全都是这个模式。
> 你写业务代码时几乎不需要 `unsafe`——因为标准库已经替你付了这笔钱。

### 6.3 什么时候该怀疑编译器

**判断流程**（本课程最实用的一张流程图）：

```
借用错误
   │
   ├─ 问1：运行时真的有两条路径同时访问同一份数据，且至少一条在写吗？
   │        │
   │        ├─ 有 ─────────────────────────► 编译器是对的。改设计（第 18 章）
   │        │
   │        └─ 没有
   │             │
   │             ├─ 问2：这个"不相交"的事实，能从函数签名推出来吗？
   │             │        │
   │             │        ├─ 能 ──► 这是精度问题。试 Polonius（第 16 章）；
   │             │        │         或用第 18 章的手法重排代码
   │             │        │
   │             │        └─ 不能 ──► 签名表达力不足。需要：
   │             │                    · 换一个签名更精确的 API（split_at_mut）
   │             │                    · 或索引/ID 代替引用
   │             │                    · 或运行时检查（RefCell）
   │             │                    · 或自己写 unsafe 封装（最后手段）
```

**新手 vs 大师的差别就在于走这个流程的速度。** 新手在"问1"就卡住（不知道自己的代码有没有别名），
大师 30 秒走完全程。

## 7. 推论五：`unsafe` 不是逃生门，是责任转移

### 7.1 `unsafe` 到底做了什么

极其常见的误解："`unsafe` 关闭了 borrow checker"。**完全错误。**

`unsafe` **只**解锁五件事：
1. 解引用裸指针 `*const T` / `*mut T`
2. 调用 `unsafe fn`
3. 实现 `unsafe trait`（如 `Send`/`Sync` 的手动实现）
4. 访问/修改 `static mut`（2024 edition 起已基本禁止，改用 `SyncUnsafeCell`）
5. 访问 `union` 的字段

**在 `unsafe` 块内部，借用检查器照常工作。** 下面这段在 `unsafe` 里依然报错：

```rust
unsafe {
    let a = &mut v[0];
    let b = &mut v[1];    // ❌ E0499，unsafe 救不了你
    *a += *b;
}
```

### 7.2 责任转移

`unsafe` 的真实含义是：

> **"编译器，这段代码的安全性由我证明。我保证它不违反公理。"**

注意"**不违反公理**"——`unsafe` **不允许**你违反 Aliasing XOR Mutability，
它只是不再帮你检查。如果你用裸指针制造了两个 `&mut` 指向同一处，那是 **UB**，
即使编译通过、即使跑起来没崩。

**这就是 Stacked Borrows / Tree Borrows 的由来**（第 26 章）：它们是"公理在裸指针层面的精确定义"，
Miri 用它们在运行时检查你的 `unsafe` 代码有没有说谎。

### 7.3 安全边界

```
┌─────────────────────────────────────────┐
│  safe 代码（你写的 99%）                  │
│  编译器保证：不可能有 UB                   │
│  ┌───────────────────────────────────┐  │
│  │  unsafe 块（标准库 + 少量你的代码）  │  │
│  │  你保证：不违反公理                  │  │
│  │  Miri 帮你验证                      │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
        ↑
   这条边界叫 "soundness boundary"
   一个库如果能让 safe 代码触发 UB，就叫 "unsound"，是最严重的 bug 类别
```

## 8. borrow checker **不**保证什么

这一节和前面同样重要。很多人对 Rust 有过高预期，然后失望。

| 不保证 | 说明 |
|---|---|
| **不保证不泄漏内存** | `mem::forget` 是 **safe** 函数；`Rc` 循环引用会泄漏。泄漏不是内存**不安全** |
| **不保证不死锁** | lab/18、19 号案例就是死锁，编译得很开心（第 25 章） |
| **不保证没有竞态条件** | data race ≠ race condition。TOCTOU、逻辑时序 bug 一概不管（第 23 章） |
| **不保证不 panic** | 数组越界、`unwrap()` on None、除零，都是运行时 panic |
| **不保证没有整数溢出** | debug 下 panic，release 下回绕（wrapping） |
| **不保证逻辑正确** | 它只管别名，不管你算错了 |
| **不保证 `Drop` 一定被调用** | `mem::forget`、`Rc` 环、进程 abort、`panic = "abort"` 都会跳过 |

> **`mem::forget` 是 safe 的**——这件事在 1.0 之前引发过一场著名争论（"leakpocalypse"）。
> 起因是有人发现 `Rc` 循环 + `thread::scoped`（当时的 API）可以在**没有 unsafe** 的情况下
> 制造 use-after-free。最终结论：**Rust 放弃"drop 一定会执行"这个保证**，
> `thread::scoped` 被移除（十年后以 `thread::scope` 的形式带着正确的设计回来，见 lab/23）。
>
> 这个历史很重要，因为它说明：**"析构一定发生"和"内存安全"必须二选一，Rust 选了后者。**
> 所以任何依赖 "Drop 一定会跑" 的安全性设计都是 unsound 的——第 24 章讲 async 取消安全性时会再遇到它。

## 9. 和其他哲学的对照

| 语言 | 别名可变问题的解法 | 检查时机 | 代价 |
|---|---|---|---|
| **C** | 不解决 | 无 | UB 满天飞 |
| **C++** | RAII + 智能指针（约定） | 无（编译器不理解） | 约定可以被绕过 |
| **Java/Go** | GC 解决"释放"这一半，另一半不解决 | 部分运行时（`ConcurrentModificationException`、`-race`） | 运行时开销 + 漏检 |
| **Swift** | ARC + exclusivity enforcement | 主要运行时，部分编译期 | 运行时开销 |
| **Rust** | 类型系统全解 | **编译期** | 学习曲线 + 不完备 |
| **Mojo / Val(Hylo)** | 借鉴 Rust，加"可变值语义" | 编译期 | 更新，未成熟 |
| **C++ Profiles / Safe C++** | 提案中，试图给 C++ 加类似检查 | 编译期 | 兼容性包袱巨大 |

**Rust 的取舍**：把成本从"运行时"和"生产环境事故"，前移到"编译期"和"学习曲线"。

这个取舍**不总是划算的**。写一个跑三次的脚本？Python。写一个 CRUD 服务，团队没人会 Rust？Go。
写一个要跑十年、有并发、有性能要求、bug 代价高的系统？Rust 的账算得过来。

## 10. 心法：三个思维习惯

学完全部 27 章之后，你会内化这三个习惯。现在先记住它们，后面每章都在训练它们。

### 习惯 1：先画数据流，再写代码

写函数之前问三个问题：
1. **这份数据是谁的？**（谁 drop 它）
2. **它要活多久？**（比调用者短？一样长？永生？）
3. **同一时刻有几个人要碰它？几个要改？**

想清楚这三个问题，签名自然就出来了。想不清楚就直接写，一定会和编译器打架。

### 习惯 2：把 `&mut` 念成"独占"

再说一遍。念成"独占"之后，这些困惑会当场消失：

- "为什么 `&Cell<i32>` 能改值？"→ 因为规则是关于独占的；`Cell` 保证了不会泄漏内部引用，所以共享改写是安全的
- "为什么 `&mut self` 方法调用期间不能读别的字段？"→ 因为你把整个 `self` 独占出去了
- "为什么 `&mut T` 不能 Copy？"→ 因为复制一份就有两个了，那还叫什么独占

### 习惯 3：错误信息的第二段比第一段重要

```
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> src/main.rs:5:13                     ← 第一段：冲突发生在哪
  |
3 |     for x in &v {
  |              --  immutable borrow occurs here          ← 谁先借的
5 |             v.push(99);
  |             ^^^^^^^^^^ mutable borrow occurs here      ← 谁后借的
6 |         }
7 |     }
  |     - immutable borrow later used here                 ← ★ 关键：先借的那个在哪里"最后被用"
```

**最后一行才是解题的钥匙**。因为借用的终点由"最后一次使用"决定（NLL），
所以解法往往是"**把最后一次使用挪到前面**"或"**把冲突的操作挪到后面**"。
第 18 章的第一个手法就是这个。

## 11. 动手实验

### 实验 1：局部推理的价值（对着 Go 想）

在 Go 里写一个函数，签名是 `func Process(data []int, cfg *Config)`。
**只看签名**，回答：`Process` 会不会修改 `data`？会不会把 `data` 存到 `cfg` 里长期持有？

答案是：**不知道**。现在看 Rust 的三个签名：

```rust
fn a(data: &[i32], cfg: &Config);              // 不会改 data；可能读 cfg
fn b(data: &mut Vec<i32>, cfg: &Config);       // 会改 data；且改的时候没人能看 data
fn c(data: Vec<i32>, cfg: &Config);            // data 归它了，调用后你不能再用
fn d<'a>(data: &'a [i32], cfg: &mut Config<'a>); // ★ 可能把 data 的引用存进 cfg！
```

**第四个签名里的 `'a` 就是在警告你"存进去了"**。这个信息在 Go 里完全不存在。

### 实验 2：把公理用在自己的代码上

找一段你写过的 Go 代码（或任何语言），画出：
- 每份重要数据的**所有者**
- 每个函数持有的**引用**及其**有效期**
- 有没有"两处能访问且至少一处会写"的时刻

如果有，问自己：现在是怎么保证它安全的？靠锁？靠"调用顺序不会变"？靠注释？
**那些地方就是你未来的 bug**。

## 13. 常见坑

| 误解 | 事实 |
|---|---|
| "`&mut` 是可变引用" | 是**独占**引用。可变性是结果，独占性是原因 |
| "`unsafe` 能绕过借用检查" | 只解锁五件事，借用检查照常。想绕过必须用裸指针，而那需要你自己保证不违反公理 |
| "编译器应该能看出 `v[0]` 和 `v[1]` 不冲突" | 它只看 `IndexMut` 的签名，签名里没这个信息。这是**设计**，不是缺陷 |
| "加 `'static` 能解决生命周期错误" | 通常只是把错误推到调用点。`'static` 是**更强的要求**，不是"关掉检查" |
| "Rust 保证没有内存泄漏" | 不保证。`mem::forget` 是 safe 的 |
| "Rust 保证并发正确" | 只保证**无数据竞争**。死锁、竞态条件、逻辑错误一概不管 |
| "borrow checker 是为了帮我写对代码" | 它是为了**证明**你的代码不违反一条特定的公理。它对你的业务逻辑毫无兴趣 |
