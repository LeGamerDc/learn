# 13 - 自动化平衡测试

> **本章目标**：把第 03~12 章的所有判据变成**可执行的断言**，接进 CI。
> **本章有模型**：`models/s13_auto_playtest.py`——**这一个是可以直接抄进你项目的**。
> **本章最重要的部分不是套件本身，是"检查项本身也需要测试"**（§3）。

## 2. 三个"已知坏版本"

套件不只跑基线，还跑三个**故意做坏的配置**：

| 病例 | 改了什么 | 应该触发哪一项 |
|---|---|---|
| **A：单道具超模** | 把 5 号道具价值从 ~1.0 提到 1.85 | 07 无 dominant |
| **B：同维乘法** | 叠加规则从软上限改成乘法 | 08 分配决策有价值 |
| **C：广告注入过量** | 注入 1.0→3.0，重抽 2→8 | 03 内容寿命 + 05 IPU |

## 3. 元测试：检查项本身可靠吗

```
版本                预期报警                    实际报警
------------------------------------------------------------------
基线                （无）                     （无）                        ✅
病例A：单道具超模     07 无 dominant            06 中位通关率、07 无 dominant   ✅
病例B：同维乘法       08 分配决策有价值           08 分配决策有价值               ✅
病例C：广告注入过量   03 内容寿命、05 IPU        03 内容寿命、05 IPU            ✅
```

**这一段在问一个元问题："我的检查项，真的能抓到问题吗？"**

[第 07 章](./07-build-diversity.md)证明过：**选取率基尼**和**最高选取率**这两个"看起来很合理"的指标，**都抓不到单道具超模**。

> **如果没有病例 A 这样的固定用例，你会一直以为自己有监控——直到线上出事。**

> **⭐ 平衡测试套件里必须常驻"已知坏版本"。每加一个检查项，就配一个能触发它的病例。**
>
> **没有失败用例的断言，等于没有断言。**

**关于"额外报警"**：病例 A 同时触发了通关率检查——**这不是误报，是真实的溢出效应**（[第 09 章](./09-randomness.md)：一个改动会溢出到别的系统）。**额外报警恰恰是套件在帮你发现关联。**

## 4. 这套东西被自己的元测试抓到过两次

**这两次都是我写这一章时真实发生的，比套件本身更值得记。**

### 4.1 观察性指标有选择偏差

[第 07 章](./07-build-diversity.md)用的"边际胜率"是**观察性**指标：

```
边际胜率 = 含它的构筑通关率 − 不含它的构筑通关率
```

**它在病例 A 上漏报了。**

> **因为那件道具强到几乎每局必选，"不含它的构筑"根本没有样本——对照组是空的。**

**修法：换成干预性指标。**

```python
def ban_scan(cfg, base_win, top_k=6):
    """把某件道具从池子里拿掉，重跑，看通关率掉多少"""
```

```
基线      最大跌幅 -4.9%
病例A     最大跌幅  8.5%    ← 干净地分开了
```

**干预不受选择偏差影响。代价是要多跑 top_k 次仿真——值得。**

> **⇒ 这条规律超出游戏数值：任何"越强的东西样本越有偏"的场景，观察性指标都会低估它。**
> **你在后端做 A/B 分析时踩的是同一个坑。**

### 4.2 报警时的默认假设应该是"系统错了"

第一版的重抽逻辑写成"**选中的道具低于中位数就重抽**"，结果**池子的下半部分永远不会被选中**——废卡检查立刻报了 **12 张**。

**我的第一反应是"检查项太严了，放宽阈值吧"。那是错的。**

正确的做法是去看被测系统——**重抽应该只在"整组都很差"时触发**，否则它会把随机性和半个道具池一起删掉（[第 09 章 §4.1](./09-randomness.md) 的另一种形态）。

> **⇒ ⭐ 检查项报警时，默认假设是"系统错了"，不是"阈值太严了"。**
> **改阈值是最后手段，而且要写清理由。**

## 5. 接进 CI

**分两层跑**（和后端测试金字塔一样）：

```
┌─ 每次提交：冒烟测试   python s13_auto_playtest.py --quick
│    局数少、2 秒出结果
│    抓的是"改配表改出了明显的低级错误"
│
└─ 每天 / 每次发版：全量   python s13_auto_playtest.py
     跑满局数 + 所有病例 + 元测试
     抓的是"数值漂移"和"检查项失效"
```

**退出码约定**：全部通过 → 0；有未通过项或元测试漏报 → 1。

```yaml
- name: 数值平衡体检
  run: python models/s13_auto_playtest.py --quick
```

### 5.1 四条实践建议

| | |
|---|---|
| **把 `TARGET` 单独放一个文件，纳入 code review** | 改目标区间是**产品决策**，不该混在配表改动里悄悄过去 |
| **每次调数值，先看哪些检查项的"实测值"动了** | 它比 diff 更能告诉你这次改动的影响面 |
| **失败时打印实测值，不要只打印 pass/fail** | 表里"实测/目标"两列就是为了让你一眼看出"差多远" |
| **仿真要固定种子** | 否则你分不清"数值改动"和"随机波动"。本套件所有 `default_rng` 都带固定 seed |

### 5.2 一条给后端出身的人的提醒

**你会想把这套东西做得很完备。别。**

平衡测试的边际收益递减得很快：

- **前 5 个检查项**抓住了 80% 的低级错误
- **第 10 个之后**基本只在抓噪声
- **而每个检查项都要配一个病例来维护**

> **判断标准：这个检查项，能抓到一个"上线后会让我半夜起来改"的问题吗？**
> 不能的话就别加。

## 6. 它抓不到什么

> **⚠️ 这套东西能告诉你"哪个 build 胜率异常"，但告诉不了你"这局好不好玩"。**

| 能抓 | 抓不到 |
|---|---|
| 某个道具无敌 / 废掉 | 数值都对，但玩起来很闷 |
| 通关率漂出健康带 | 节奏点位置不对（[第 02 章](./02-session-pacing.md)） |
| 内容寿命不够 | 广告弹得太硌人 |
| IPU 掉出区间 | **失败归因不清**（[第 09 章](./09-randomness.md)） |

**自动化测试是下限保障，不是设计工具。**

> **它防的是"上线后发现某个道具无敌"，防不了"数值都对，但玩起来很闷"。**
> **后者只能靠玩。**

## 7. 动手

### 7.1 改模型

**任务 A：加一个病例，再加一个检查项。** 造一个"废卡过多"的版本（比如把一半道具的价值降到 0.5），**先确认现有检查项能不能抓到**。抓不到的话，你需要加什么？

**任务 B：验证 §4.1 的选择偏差。** 把 dominant 检查换回观察性的 `outlier_z(d["lift"])`，跑病例 A。**它漏报了吗？** 再把超模值从 1.85 降到 1.4（选取率没那么极端），**这次呢？**

<details>
<summary>你会看到什么</summary>

超模不那么极端时，观察性指标反而能抓到——**因为对照组还有样本**。
**这正是选择偏差最阴险的地方：问题越严重，观察性指标越抓不到。**
</details>

**任务 C：加"贪心探针人群"。** `simulate` 里已经留了 `player="greedy"` 参数。用它跑一遍所有检查，**哪些指标的值变了？变化说明了什么？**

**任务 D：控制运行时间。** 全量模式现在跑几秒。加检查项时它会线性增长。**写一个 `--parallel` 用 `multiprocessing` 并行跑不同版本**，看能压到多少。

**任务 E：接你自己的游戏。** 把 `simulate()` 换成调用你真实的战斗/经济代码（或者通过 subprocess 调你的 Go 服务）。**这是本章真正的作业。**
